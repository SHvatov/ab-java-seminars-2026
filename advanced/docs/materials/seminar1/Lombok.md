# Lombok

---

## 1. Что это и какую проблему решает

Класс, описывающий сущность с несколькими полями, обрастает кодом, механически выводимым из объявления этих полей:
геттеры, конструкторы, `equals`/`hashCode`, `toString`. Такой код не содержит логики предметной области, но требует
ручной поддержки — добавление нового поля означает необходимость синхронно обновить все производные методы, и
компилятор не подскажет, если где-то забыли.

**Lombok** переносит эту работу на этап компиляции: аннотации над классом или полем инструктируют annotation
processor — специальный плагин, встраивающийся в компилятор, — сгенерировать соответствующий байт-код. Исходный файл
остаётся компактным, а результат компиляции содержит полноценные методы, неотличимые от написанных вручную.

## 2. Подключение

### 2.1. Maven

```xml
<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <version>1.18.36</version>
    <scope>provided</scope>
</dependency>
```

Область `provided`: библиотека нужна только для генерации кода на этапе сборки, в итоговый артефакт она не попадает —
сгенерированные методы к этому моменту уже часть скомпилированных `.class`-файлов.

Отдельно нужно зарегистрировать Lombok как annotation processor для компилятора:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
                <version>1.18.36</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
```

### 2.2. IntelliJ IDEA

IDE разбирает исходный код независимо от компилятора Maven — без дополнительных шагов она не будет понимать, откуда
берутся методы, которых нет в тексте файла, и подчеркнёт их использование как ошибку (хотя `mvn compile` при этом
пройдёт без проблем — процессы независимы):

1. Settings → Plugins → установить плагин **Lombok**, перезапустить IDE.
2. Settings → Build, Execution, Deployment → Compiler → Annotation Processors → включить **Enable annotation
   processing**.

## 3. Основные аннотации

| Аннотация | Генерирует |
|---|---|
| `@Getter` / `@Setter` | геттер/сеттер для поля (или всех полей класса) |
| `@ToString` | `toString()` на основе полей |
| `@EqualsAndHashCode` | согласованную пару `equals`/`hashCode` |
| `@NoArgsConstructor` | конструктор без аргументов |
| `@RequiredArgsConstructor` | конструктор для `final`-полей и полей с `@NonNull` |
| `@AllArgsConstructor` | конструктор со всеми полями, в порядке объявления |

```java
@RequiredArgsConstructor
public class Instrument {
    private final String ticker;
    private final String name;
}
```

Составные аннотации комбинируют несколько из перечисленных:

- **`@Data`** = `@Getter` + `@Setter` (на все поля) + `@ToString` + `@EqualsAndHashCode` + `@RequiredArgsConstructor`.
- **`@Value`** — неизменяемый аналог: поля становятся `private final`, сеттеры не генерируются, класс — `final`.
- **`@Builder`** — генерирует паттерн Builder: пошаговое конструирование с именованными вызовами вместо длинного
  списка позиционных аргументов конструктора.

## 4. Где Lombok не заменяет ручной код

**Валидация инвариантов.** `@AllArgsConstructor`/`@RequiredArgsConstructor` лишь присваивают переданные значения
полям — никакой проверки корректности они не выполняют. Конструктор, который должен отклонять некорректные
аргументы (например, пустой тикер), по-прежнему нужно писать руками: генерация полей и защита инвариантов —
принципиально разные задачи, и Lombok решает только первую.

**`@Data` и инкапсуляция.** Автогенерированные сеттеры позволяют менять состояние объекта в обход какой бы то ни было
проверки. Для классов, у которых есть контракт на согласованность полей, предпочтительнее точечные аннотации
(`@Getter` без `@Setter`, `@RequiredArgsConstructor`) вместо огульного `@Data`.

**Отладка и чтение кода.** Сгенерированный код не виден в исходном файле; большинство IDE умеют показать
деломбокированное представление класса — полезно держать в голове при первом знакомстве с библиотекой.

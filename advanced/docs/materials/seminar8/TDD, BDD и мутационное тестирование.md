## 1. TDD: red-green-refactor

Test-Driven Development меняет порядок: тест пишется раньше кода. Цикл повторяется маленькими шагами:

1. **Red.** Написать тест на желаемое поведение. Он падает (или не компилируется) — кода ещё нет. Это фиксирует
   требование.
2. **Green.** Написать **минимальный** код, чтобы тест прошёл, — без обобщений «на будущее».
3. **Refactor.** Улучшить код при зелёных тестах; они страхуют от регрессий.

Разберём на реальной фиче — удаление из watchlist (изначально `Watchlist` умеет только добавлять).

```java
// Red — метода remove ещё нет, тест падает
@Test
void removeУбираетТикерНезависимоОтРегистра() {
    Watchlist watchlist = new Watchlist();
    watchlist.add("SBER");

    assertTrue(watchlist.remove("sber"));
    assertFalse(watchlist.contains("SBER"));
}
```

```java
// Green — минимальная реализация в Watchlist
public boolean remove(String ticker) {
    return tickers.remove(ticker.toUpperCase());
}
```

Тест зелёный. На шаге **refactor** тем же циклом наращивается CLI: сначала тест на `watch --remove TICKER`, затем флаг в
`WatchCommand`. Каждый шаг оставляет проект в рабочем, покрытом тестами состоянии.

## 2. Что даёт TDD и где его границы

TDD ценен не ритуалом «тест сначала», а следствиями: тест формулирует требование до реализации, код по построению
получается тестируемым (нельзя написать непроверяемый метод, если тест уже есть), а набор тестов растёт вместе с кодом,
а не «когда-нибудь потом». Побочный эффект — дизайн: чтобы тест был простым, зависимости приходится выносить за интерфейс
(как `QuoteSource`).

Границы: TDD плох для исследовательского кода, где требования ещё не ясны (тест нечего фиксировать), и не заменяет
проектирования — он направляет реализацию, но не архитектуру. Слепое следование «100% через TDD» даёт много хрупких
тестов на тривиальный код.

## 3. BDD: Given-When-Then

Behavior-Driven Development смещает акцент с «тестируем метод X» на «описываем поведение системы» в терминах, близких к
требованию: **Given** (предусловие) — **When** (действие) — **Then** (ожидаемый результат). В JUnit 5 это выражается
вложенными классами `@Nested` и человекочитаемыми `@DisplayName` — отдельный фреймворк не нужен:

```java
@DisplayName("QuoteService")
class QuoteServiceBddTest {

    @Nested
    @DisplayName("когда котировка уже в кеше")
    class WhenCached {

        @Test
        @DisplayName("тогда повторный запрос не идёт к источнику")
        void неХодитКИсточникуПовторно() {
            // Given — источник вернёт котировку один раз
            QuoteSource source = mock(QuoteSource.class);
            when(source.fetch("SBER")).thenReturn(Optional.of(sberQuote));
            QuoteService service = new QuoteService(source);

            // When — запрашиваем дважды
            service.quoteFor("SBER");
            service.quoteFor("SBER");

            // Then — к источнику обратились ровно один раз
            verify(source, times(1)).fetch("SBER");
        }
    }
}
```

Отчёт JUnit при таком оформлении читается как спецификация: «QuoteService → когда котировка уже в кеше → тогда повторный
запрос не идёт к источнику». Тест становится документацией поведения.

## 4. BDD-инструменты

Для полноценного BDD, где сценарии пишутся на естественном языке (в том числе не-разработчиками), существуют
Cucumber и синтаксис Gherkin (`Given/When/Then` в текстовых `.feature`-файлах, привязанных к шагам-методам). Это тяжелее
и оправдано на сценариях уровня требований бизнеса. Для модульных тестов достаточно применять идеологию Given-When-Then
в чистом JUnit — без дополнительной инфраструктуры.

## 5. Мутационное тестирование: идея

Покрытие строк (line coverage) показывает, какие строки исполнились, но не то, проверены ли они. Тест без единого ассерта
даёт полное покрытие и нулевую ценность. Мутационное тестирование измеряет силу тестов напрямую.

Инструмент вносит в код мелкие изменения — **мутации** — и после каждой прогоняет тесты:

- арифметика: `+` → `-`, `*` → `/`;
- условия: `>` → `>=`, `==` → `!=`, инверсия `if`;
- возвраты: вернуть `null`/`0`/`false` вместо результата;
- убрать вызов метода.

Каждая мутация — искусственная ошибка. Упал хоть один тест — мутант **убит** (тесты поймали). Все прошли — мутант
**выжил**: изменение поведения незаметно для тестов, значит есть дыра. Доля убитых (mutation score) — честная мера
качества набора тестов.

## 6. PIT: подключение и отчёт

**PIT** (`pitest`) — инструмент мутационного тестирования для Java. Плагин Maven, запуск —
`mvn org.pitest:pitest-maven:mutationCoverage`; результат — HTML-отчёт с процентом убитых мутантов и списком выживших
(строка + вид мутации).

```xml
<plugin>
    <groupId>org.pitest</groupId>
    <artifactId>pitest-maven</artifactId>
    <version>1.20.4</version>
    <configuration>
        <targetClasses><param>academy.backend.market_pulse.*</param></targetClasses>
        <targetTests><param>academy.backend.market_pulse.*</param></targetTests>
    </configuration>
</plugin>
```

PIT перед мутациями прогоняет тесты «начисто» (мутанты имеют смысл только при зелёных тестах) и для скорости мутирует
лишь строки, покрытые тестами.

---

## 7. Покрытие против мутаций

Выживший мутант — точное указание на слабое место. В `Stock.getDividends` (`price * yield / 100`) PIT заменит `*` на
`/`. Если тест проверяет только знак результата, мутант выживет — тест не отличает умножение от деления. Ассерт на точное
значение (`assertEquals(new BigDecimal("25.00"), ...)`) убивает мутанта.

Итог: покрытие отвечает «исполнили ли код», мутационное тестирование — «проверили ли его». Второе дороже (тесты гоняются
многократно, по разу на мутацию), поэтому его запускают не на каждый коммит, а периодически и на критичном коде — там,
где цена незамеченной ошибки высока.

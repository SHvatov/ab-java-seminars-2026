## 1. Обзор и иерархия интерфейсов

Java Collection Framework (JCF) отделяет контракт структуры данных от её реализации. Интерфейсы `List`, `Set`, `Queue`
описывают поведение; классы `ArrayList`, `HashSet`, `ArrayDeque` его реализуют с конкретными характеристиками
операций. Такое разделение позволяет объявлять поля и параметры через интерфейс (`List<Instrument>`) и подменять
реализацию, не трогая клиентский код.

Корень иерархии коллекций — `Iterable` (обеспечивает перебор) → `Collection` (общий предок `List`/`Set`/`Queue`).
`Map` стоит вне этой иерархии: она хранит пары «ключ-значение», а не отдельные элементы, поэтому не наследует
`Collection` и не имеет `iterator()`. Перебор `Map` идёт через три её представления — `keySet()`, `values()`,
`entrySet()`, — каждое из которых само является `Collection`.

## 2. List под капотом: ArrayList, LinkedList и локальность памяти

`List` — упорядоченная последовательность с доступом по индексу и допустимыми дубликатами. Две основные реализации
устроены противоположным образом.

### ArrayList

Внутри — Java-массив `Object[] elementData` и счётчик `size`. Массив держит запас под будущие добавления, поэтому его
длина обычно больше `size`.

- **`add` в конец.** Есть свободная ячейка — запись за `O(1)`. Массив заполнен — **grow**: аллоцируется массив
  примерно в 1.5 раза больше, элементы копируются через `Arrays.copyOf`. Разовое расширение `O(n)` амортизируется по
  множеству добавлений до `O(1)` в среднем.
- **`get(i)`** — прямое обращение к ячейке, `O(1)`.
- **`contains`/`indexOf`** — линейный перебор, `O(n)`.
- **`add(i, e)`/`remove(i)` в середину** — сдвиг хвоста через `System.arraycopy`, `O(n)`.

Если итоговый размер известен, `new ArrayList<>(capacity)` устраняет промежуточные расширения.

### LinkedList

Двусвязный список: каждый элемент обёрнут в узел `Node` со ссылками `prev`/`next`; список хранит ссылки на голову и
хвост.

- **Вставка/удаление с концов или через позиционированный итератор** — `O(1)` (перестановка ссылок).
- **`get(i)`** — проход по ссылкам от ближайшего конца, `O(n)`.
- **`contains`** — `O(n)`.

### RandomAccess — маркерный интерфейс быстрого доступа

Разница в стоимости `get(i)` формализована в системе типов маркерным интерфейсом `java.util.RandomAccess` — пустым,
без единого метода. Его реализуют списки с эффективным (как правило `O(1)`) доступом по индексу — `ArrayList`, `Vector`,
список из `Arrays.asList`; `LinkedList` его **не** реализует. По типу-параметру `List<E>` обобщённый алгоритм не может
узнать, дешёв ли индексный доступ, поэтому соглашение — проверить `instanceof RandomAccess` и выбрать стратегию обхода:

```java
void example(List<String> list) {
    if (list instanceof RandomAccess) {
        for (int i = 0; i < list.size(); i++) {  // дёшево: get(i) — O(1)
            process(list.get(i));
        }
    } else {
        for (String e : list) {                  // дёшево: обход через Iterator
            process(e);
        }
    }
}
```

Так поступает и сам JDK: `Collections.binarySearch`, `shuffle`, `fill`, `copy`, `reverse` внутри переключаются между
индексным и итераторным доступом по наличию `RandomAccess`. Практическое следствие — ловушка: обход `LinkedList` по
индексу (`for (i) list.get(i)`) даёт `O(n²)`, потому что каждый `get(i)` — сам по себе `O(n)`; тот же цикл на
`ArrayList` — `O(n)`. `RandomAccess` — формальный признак того, какой из двух способов обхода корректен для конкретной
реализации. Это тот же приём маркерного интерфейса, что `Serializable` или `Cloneable`: тип ничего не добавляет к API,
но несёт метаинформацию, на которую опирается библиотечный код.

### Локальность памяти — почему ArrayList почти всегда быстрее

Асимптотика — не вся правда. `ArrayList` хранит ссылки подряд в одном массиве: обход последователен, процессорный кеш
подтягивает соседние элементы наперёд (prefetch), промахов по кешу мало. `LinkedList` разбрасывает узлы по куче, каждый
переход `next` — потенциальный промах кеша, плюс на каждый элемент приходится накладной объект-узел с двумя ссылками
(лишняя память, которую на семинаре про раскладку объектов видно через JOL). На практике `ArrayList` обгоняет
`LinkedList` даже в сценариях, где асимптотика формально в пользу списка, — за исключением узкого случая частых вставок
и удалений с концов, где и для этого обычно берут `ArrayDeque`.

## 3. Set: обзор, сложность, когда использовать

`Set` — множество уникальных элементов; повторное добавление игнорируется, `add` возвращает `false`.

| Реализация | add / contains / remove | Порядок обхода |
|------------|-------------------------|----------------|
| `HashSet` | `O(1)` в среднем | не определён |
| `LinkedHashSet` | `O(1)` в среднем | порядок добавления |
| `TreeSet` | `O(log n)` | отсортированный |

`HashSet` реализован поверх `HashMap` (элементы — ключи, значение-заглушка общее), поэтому наследует его требования к
`equals`/`hashCode` и поведение при коллизиях. `LinkedHashSet` дополнительно связывает элементы в список порядка
добавления. `TreeSet` держит элементы в красно-чёрном дереве по порядку сравнения и даёт навигационные запросы
(`first`, `ceiling`, `headSet`).

```java
void example() {
    Set<String> tickers = new LinkedHashSet<>();
    boolean added = tickers.add("SBER"); // true
    boolean again = tickers.add("SBER"); // false — множество не изменилось
}
```

**Когда использовать.** Нужна уникальность и/или быстрая проверка принадлежности — `HashSet` по умолчанию,
`LinkedHashSet` при важности порядка, `TreeSet` при необходимости сортировки или запросов по диапазону.

## 4. Queue: обзор, сложность, когда использовать

`Queue` — очередь с дисциплиной обработки, чаще FIFO. Два набора методов различаются поведением на границе:

| Операция | Не бросает исключение | Бросает исключение |
|----------|-----------------------|--------------------|
| В хвост | `offer(e)` → `boolean` | `add(e)` |
| Из головы | `poll()` → `null` | `remove()` |
| Посмотреть голову | `peek()` → `null` | `element()` |

`ArrayDeque` (кольцевой буфер поверх массива) — реализация общего назначения: операции с обоими концами `O(1)`,
накладных расходов меньше, чем у `LinkedList`; работает и как FIFO-очередь, и как LIFO-стек, предпочтительнее
устаревшего `Stack`.

```java
void example() {
    Queue<String> pending = new ArrayDeque<>();
    pending.offer("SBER");
    pending.offer("GAZP");
    String next = pending.poll(); // "SBER"
}
```

**Когда использовать.** Обработка по мере поступления, буфер между «положить» и «обработать», обход в ширину, замена
стека.

## 5. HashMap под капотом

`HashMap` — хеш-таблица «ключ → значение»; понимание её устройства объясняет и `O(1)`, и требования к ключам.

### Бакеты и хеширование

Внутри — массив бакетов `Node[] table`. При `put`:

1. вычисляется `hashCode()` ключа, его старшие биты подмешиваются к младшим (`h ^ (h >>> 16)`) — чтобы плохие
   хеш-функции реже давали коллизии по младшим битам, определяющим бакет;
2. индекс бакета — `hash & (table.length - 1)`; поэтому длина таблицы всегда степень двойки (побитовое `И` заменяет
   деление по модулю);
3. в бакет кладётся узел `(hash, key, value, next)`.

`get` идёт тем же путём: бакет по хешу, затем внутри бакета сравнение ключей по `equals`. При равномерном распределении
в бакете единицы элементов, и операции — `O(1)` в среднем.

### Коллизии и treeification

Разные ключи, попавшие в один бакет, связываются в список; поиск перебирает его, сравнивая ключи. Длинный список
деградирует к `O(n)`. С Java 8 бакет с числом узлов ≥ 8 (при `table.length` ≥ 64) преобразуется в красно-чёрное дерево,
и поиск в переполненном бакете идёт за `O(log n)`. При уменьшении числа узлов дерево обратно вырождается в список.

### Load factor и resize

Load factor (по умолчанию `0.75`) задаёт порог заполнения: при `size > table.length × loadFactor` таблица
расширяется вдвое, и все пары **перехешируются** по новым бакетам — разовая `O(n)`-операция. Известный заранее размер
и `new HashMap<>(capacity)` избавляют от промежуточных resize.

### equals/hashCode ключа

- равные по `equals` ключи **обязаны** иметь равный `hashCode` — иначе значение ищется не в том бакете и «теряется»;
- разные по `equals` ключи могут иметь равный `hashCode` — это допустимая коллизия.

Переопределяя `equals`, всегда переопределяют `hashCode` согласованно. Ключ должен быть эффективно неизменяемым: если
`hashCode` объекта изменится после помещения в `Map`, узел останется в старом бакете и станет недостижим. Поэтому
хорошие ключи — `String`, обёртки примитивов, `record`. `String` чувствителен к регистру, поэтому для
регистронезависимого поиска ключ нормализуют в одном месте.

```java
void example() {
    Map<String, String> byTicker = new HashMap<>();
    byTicker.put("SBER".toUpperCase(), "Сбербанк");
    String name = byTicker.get("sber".toUpperCase()); // "Сбербанк"
}
```

## 6. Другие реализации Map: LinkedHashMap и TreeMap

`LinkedHashMap` наследует `HashMap` и связывает записи в двусвязный список порядка добавления (либо порядка доступа —
режим `accessOrder`, база для LRU-кеша). Сложность та же `O(1)`, обход предсказуем.

`TreeMap` — красно-чёрное дерево по порядку ключей (`Comparable`/`Comparator`); операции `O(log n)`, доступны
навигационные и диапазонные запросы (`firstKey`, `floorKey`, `subMap`).

| Реализация | get / put | Порядок обхода |
|------------|-----------|----------------|
| `HashMap` | `O(1)` в среднем | не определён |
| `LinkedHashMap` | `O(1)` в среднем | порядок добавления/доступа |
| `TreeMap` | `O(log n)` | отсортированный по ключу |

## 7. Выбор структуры: асимптотика, константа, кеш

Асимптотика указывает, как операция масштабируется с ростом данных, и это первый критерий: если основная операция —
поиск по ключу, hash-структура (`O(1)`) не зависит от объёма, тогда как линейный поиск в `List` (`O(n)`) деградирует.
Но при близкой асимптотике решают константа и поведение в кеше: `ArrayList` с его локальностью обгоняет `LinkedList`,
а `HashMap` платит за `O(1)` вычислением хеша и возможными коллизиями. Правильная методика — обосновать выбор
асимптотикой, а на горячем пути подтвердить замером (JMH), а не полагаться на интуицию о «быстром» и «медленном».

Типовая ошибка — держать данные в `List` и постоянно искать в нём линейно. Если поиск идёт по некоторому ключу, данные
индексируют в `Map` по этому ключу.

## 8. За пределами java.util: Guava, Vavr, Apache Commons, примитивные коллекции

Стандартный JCF закрывает большинство задач, но экосистема даёт специализированные коллекции.

**Guava.**

```java
void example() {
    Map<String, Quote> seed = ImmutableMap.of("SBER", sberQuote, "GAZP", gazpQuote);

    Multimap<Currency, Instrument> byCurrency = ArrayListMultimap.create();
    byCurrency.put(Currency.RUB, sber);
    byCurrency.put(Currency.RUB, gazp);
    Collection<Instrument> rub = byCurrency.get(Currency.RUB);
}
```

`ImmutableMap`/`ImmutableList` — по-настоящему неизменяемая копия, в отличие от `Collections.unmodifiableMap`, который
лишь оборачивает изменяемый оригинал (тот за обёрткой всё ещё может измениться). `Multimap` заменяет ручной
`Map<K, List<V>>` с инициализацией списка при первом добавлении.

**Vavr.**

```java
void example() {
    io.vavr.collection.List<String> watchlist = io.vavr.collection.List.of("SBER", "GAZP");
    io.vavr.collection.List<String> extended = watchlist.append("LKOH");
    // watchlist остался List(SBER, GAZP); extended — List(SBER, GAZP, LKOH)

    io.vavr.collection.Map<String, Integer> weights = io.vavr.collection.HashMap.of("SBER", 40);
    io.vavr.collection.Map<String, Integer> updated = weights.put("GAZP", 60); // старый map неизменен
}
```

Vavr идёт дальше иммутабельности Guava: его коллекции *персистентны*. `ImmutableMap` — неизменяемая, но одноразовая
копия (менять нельзя вообще); коллекция Vavr на каждую «модификацию» (`append`/`put`) возвращает новую версию, а
старая продолжает существовать, и обе дёшево делят общие внутренние узлы (structural sharing — не полное копирование).
Это тот же безопасный от побочных эффектов стиль, что и `Optional`/`Try`, но для коллекций: значение нельзя изменить
незаметно для владельца ссылки.

**Apache Commons Collections.**

```java
void example() {
    Collection<String> both = CollectionUtils.intersection(watchlistA, watchlistB);

    Bag<Currency> counts = new HashBag<>();
    counts.add(Currency.RUB);
    counts.add(Currency.RUB);
    int rub = counts.getCount(Currency.RUB); // 2
}
```

`CollectionUtils` даёт теоретико-множественные операции (`union`, `intersection`, `subtract`); `Bag` — мультимножество,
считающее вхождения; `MultiValuedMap` — аналог Guava `Multimap`.

**Примитивные коллекции (fastutil, Eclipse Collections, Trove).**

```java
void example() {
    // double[] под капотом — без обёрток Double и boxing на каждый элемент
    DoubleArrayList prices = new DoubleArrayList();
    prices.add(250.00);
    double last = prices.getDouble(prices.size() - 1); // примитив, без unboxing

    // ключ хранится как int[], а не как Integer[]
    Int2ObjectMap<Instrument> byId = new Int2ObjectOpenHashMap<>();
    byId.put(1, sber);
}
```

Стандартные коллекции хранят объекты, поэтому `int` превращается в `Integer` (boxing) — лишняя память и
разыменование. Примитивные коллекции хранят `int`/`long`/`double` напрямую, экономя память и повышая локальность;
выигрыш особенно заметен на больших объёмах и виден на раскладке объектов через JOL. Цена — дополнительная зависимость
и специализированный API; на малых коллекциях выигрыша нет.

Вывод: внешняя коллекция оправдана под конкретную нужду (иммутабельность, мультиотображение, экономия памяти), а не
как замена `java.util` по умолчанию.

## 9. Итераторы, fail-fast и ConcurrentModificationException

`Iterator` — объект обхода с `hasNext()`, `next()`, `remove()`. Цикл for-each — синтаксический сахар над ним.

Коллекции JCF — **fail-fast**: структурная модификация увеличивает счётчик `modCount`; итератор запоминает его при
создании (`expectedModCount`) и сверяет на каждом `next()`. Расхождение — изменение в обход итератора — даёт
`ConcurrentModificationException`. «Concurrent» не про многопоточность: прямой `remove` по коллекции внутри for-each в
одном потоке уже нарушает инвариант.

```java
void example(List<String> tickers) {
    for (String ticker : tickers) {
        if (ticker.startsWith("T")) {
            tickers.remove(ticker); // ConcurrentModificationException на следующем шаге
        }
    }
}
```

`Iterator.remove()` удаляет последний возвращённый `next()` элемент и синхронно обновляет `expectedModCount`, поэтому
обход остаётся согласованным:

```java
void example(List<String> tickers) {
    Iterator<String> it = tickers.iterator();
    while (it.hasNext()) {
        if (it.next().startsWith("T")) {
            it.remove();
        }
    }
}
```

`remove()` допустим только после `next()` и не более раза на каждый `next()` — иначе `IllegalStateException`. Для
«удалить всё по условию» — `removeIf(predicate)` (Java 8+), внутри использующий тот же итератор. Важно: fail-fast — не
гарантия, а диагностическое средство (`modCount` не volatile), поэтому полагаться на него для обнаружения гонок в
многопоточном коде нельзя; для конкурентного доступа существуют отдельные потокобезопасные коллекции.

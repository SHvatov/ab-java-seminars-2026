# Вспомогательные средства для работы с коллекциями

Стандартный `java.util` закрывает большинство задач, а служебный класс `java.util.Collections` даёт типовые операции
(сортировка, `min`/`max`, `frequency`, неизменяемые представления). За его пределами экосистема предлагает
специализированные коллекции и утилиты, которые либо выразительнее стандартных, либо эффективнее на конкретном профиле
нагрузки. Здесь разобраны четыре библиотеки: Apache Commons Collections, Guava, Vavr и fastutil — что каждая добавляет
к стандартной библиотеке, какой ценой и когда её выбор оправдан.

Координаты и версии (Maven): `org.apache.commons:commons-collections4:4.4`, `com.google.guava:guava:33.4.0-jre`,
`io.vavr:vavr:1.0.1`, `it.unimi.dsi:fastutil:8.5.15`.

## Содержание

1. Apache Commons Collections — утилиты и мультиструктуры
2. Guava — иммутабельные коллекции и `Multimap`
3. Vavr — персистентные коллекции
4. fastutil — примитивные коллекции
5. Сводка: что выбирать и когда достаточно `java.util`

## 1. Apache Commons Collections — утилиты и мультиструктуры

**Суть.** Библиотека дополняет `java.util.Collections` операциями, которых в стандартной библиотеке нет, и структурами
данных общего назначения: мультимножество (`Bag`) и мультиотображение (`MultiValuedMap`).

**Проблема.** Теоретико-множественные операции над коллекциями (объединение, пересечение, разность) в стандартной
библиотеке пишутся вручную через `retainAll`/`removeAll` на защитной копии; подсчёт вхождений — через
`Map<T, Integer>` с ручным инкрементом.

**Пример.**

```java
void example() {
    List<String> watchlistA = List.of("SBER", "GAZP", "LKOH");
    List<String> watchlistB = List.of("GAZP", "LKOH", "YNDX");

    Collection<String> both = CollectionUtils.intersection(watchlistA, watchlistB); // [GAZP, LKOH]
    Collection<String> all  = CollectionUtils.union(watchlistA, watchlistB);
    Collection<String> only = CollectionUtils.subtract(watchlistA, watchlistB);     // [SBER]

    // Bag — мультимножество: хранит элементы и считает их вхождения.
    Bag<Currency> counts = new HashBag<>();
    counts.add(Currency.RUB);
    counts.add(Currency.RUB);
    counts.add(Currency.USD);
    int rub = counts.getCount(Currency.RUB); // 2
}
```

`CollectionUtils` содержит статические `union`/`intersection`/`subtract` и множество null-безопасных проверок
(`isEmpty`, `isNotEmpty`, `isEqualCollection`). `Bag` считает вхождения, не требуя ручного `Map<T, Integer>`;
`MultiValuedMap` (реализация `ArrayListValuedHashMap`) — отображение «один ключ → несколько значений», прямой аналог
Guava `Multimap`. Особенность библиотеки — акцент на null-безопасность и совместимость со старым кодом.

## 2. Guava — иммутабельные коллекции и `Multimap`

**Суть.** Guava (Google) даёт по-настоящему неизменяемые коллекции (`ImmutableList`/`ImmutableSet`/`ImmutableMap`) и
`Multimap` — мультиотображение из коробки, а также богатый набор фабрик и утилит (`Lists`, `Sets`, `Maps`).

**Проблема — иммутабельность.** `Collections.unmodifiableMap` возвращает лишь **обёртку** над изменяемым оригиналом:
если у кого-то осталась ссылка на исходную карту, её правки видны сквозь «неизменяемое» представление. Настоящей
неизменяемости это не даёт.

**Пример.**

```java
void example(Quote sberQuote, Quote gazpQuote, Instrument sber, Instrument gazp) {
    // Полноценная неизменяемая копия: у результата нет изменяемого оригинала.
    Map<String, Quote> seed = ImmutableMap.of("SBER", sberQuote, "GAZP", gazpQuote);

    // Multimap: один ключ (валюта) → несколько значений (инструменты).
    Multimap<Currency, Instrument> byCurrency = ArrayListMultimap.create();
    byCurrency.put(Currency.RUB, sber);
    byCurrency.put(Currency.RUB, gazp);
    Collection<Instrument> rub = byCurrency.get(Currency.RUB); // [sber, gazp]
}
```

`ImmutableMap`/`ImmutableList` — самостоятельная неизменяемая структура: `null` запрещён, любая мутация невозможна, а
не просто заблокирована на обёртке. `Multimap` избавляет от ручного `Map<K, List<V>>` с инициализацией списка при
первом добавлении: `ArrayListMultimap` допускает дубликаты значений и сохраняет порядок, `HashMultimap` хранит значения
множеством (без дубликатов). Фабрики `Lists.newArrayList`, `Sets.newHashSet`, `Maps.newHashMap` и операции
`Sets.intersection`/`union`/`difference` (ленивые представления) дополняют картину.

## 3. Vavr — персистентные коллекции

**Суть.** Vavr переносит в Java функциональные *персистентные* коллекции: они неизменяемы, а каждая «модификация»
возвращает новую версию, оставляя старую нетронутой. Это тот же безопасный от побочных эффектов стиль, что `Optional`
и `Try`, но для коллекций.

**Проблема.** Даже `ImmutableList` Guava — неизменяемая, но одноразовая копия: чтобы получить список с добавленным
элементом, нужно строить новый через builder. Персистентная коллекция делает это операцией самой коллекции, дёшево
переиспользуя внутренние узлы старой версии (structural sharing — не полное копирование).

**Пример.**

```java
void example() {
    io.vavr.collection.List<String> watchlist = io.vavr.collection.List.of("SBER", "GAZP");
    io.vavr.collection.List<String> extended = watchlist.append("LKOH");
    // watchlist по-прежнему List(SBER, GAZP); extended — List(SBER, GAZP, LKOH)

    io.vavr.collection.Map<String, Integer> weights = io.vavr.collection.HashMap.of("SBER", 40);
    io.vavr.collection.Map<String, Integer> updated = weights.put("GAZP", 60);
    // weights неизменен; updated содержит обе записи

    io.vavr.collection.List<String> lower = watchlist.map(String::toLowerCase); // новая коллекция
}
```

Операции `append`/`put`/`map`/`filter` не мутируют текущую коллекцию, а возвращают новую. Обе версии продолжают
существовать и дёшево делят общую часть структуры. Полные имена (`io.vavr.collection.List`) в примере — чтобы не
путать с `java.util.List`; на практике их разводят импортами. Цена — отдельная модель типов, слабо совместимая со
стандартными коллекциями (нужны конвертации `toJavaList` и т.п.).

## 4. fastutil — примитивные коллекции

**Суть.** fastutil предоставляет коллекции, специализированные под примитивы (`int`, `long`, `double`): они хранят
значения в примитивных массивах (`int[]`, `double[]`), а не в массивах обёрток.

**Проблема.** Стандартные `List<Integer>`/`Map<Integer, V>` хранят объекты, поэтому каждый примитив оборачивается в
`Integer`/`Double` (boxing): отдельный объект в куче на каждый элемент, лишняя память и разыменование при доступе. На
больших объёмах числовых данных это заметно бьёт и по памяти, и по скорости, и по локальности.

**Пример.**

```java
void example(Instrument sber) {
    // История цен как double[] под капотом — без обёрток Double и boxing на каждый элемент.
    DoubleArrayList priceHistory = new DoubleArrayList();
    priceHistory.add(250.00);
    priceHistory.add(251.20);
    double last = priceHistory.getDouble(priceHistory.size() - 1); // примитив, без unboxing

    // Индекс инструментов по числовому id: ключ хранится как int[], а не как Integer[].
    Int2ObjectMap<Instrument> byId = new Int2ObjectOpenHashMap<>();
    byId.put(1, sber);
    Instrument found = byId.get(1); // ключ-примитив, без boxing на поиске
}
```

Экономия памяти и рост скорости объясняются раскладкой объектов: `Integer` — это заголовок объекта плюс поле, тогда как
`int` в массиве занимает ровно 4 байта и лежит подряд (дружелюбно к кешу процессора) — тот же эффект, что виден на
раскладке объектов через JOL. Цена — дополнительная зависимость и специализированный API (`getDouble`, `Int2ObjectMap`
вместо дженериков); на малых коллекциях выигрыша нет, а код становится менее переносимым. Аналоги — Eclipse Collections
и Trove.

## 5. Сводка: что выбирать и когда достаточно `java.util`

| Библиотека     | Что добавляет                                        | Когда осмысленна                                       |
|----------------|------------------------------------------------------|--------------------------------------------------------|
| Commons        | `CollectionUtils` (union/intersection), `Bag`        | Теоретико-множественные операции, подсчёт вхождений    |
| Guava          | Настоящие `Immutable*`, `Multimap`, фабрики/утилиты  | Строгая иммутабельность, много ручных `Map<K, List<V>>`|
| Vavr           | Персистентные коллекции (structural sharing)         | Функциональный стиль, безопасность от мутаций по ссылке |
| fastutil       | Примитивные коллекции без boxing                     | Большие объёмы числовых данных, чувствительные к памяти |

Общее правило — по умолчанию стандартный `java.util` и `java.util.Collections`. Сторонняя библиотека оправдана, когда
стандартная коллекция вынуждает писать много вспомогательного кода (Commons, Guava `Multimap`), требует гарантий, которых
`unmodifiable*` не даёт (Guava `Immutable*`, Vavr), или упирается в производительность на конкретном профиле нагрузки
(fastutil). Каждая зависимость — это цена в сложности сборки и в разнородности API, поэтому её вводят под доказанную
потребность, а не заранее.

# Потоки в Java

Классический поток Java — обёртка над потоком операционной системы. Понимание того, что происходит на уровне ОС,
объясняет и стоимость потоков, и мотивацию пулов и виртуальных потоков. Материал разбирает связь с потоками ОС,
планировщик, жизненный цикл, создание/прерывание и безопасное распараллеливание.

## 1. Поток Java и поток ОС

Платформенный поток Java отображается на поток ОС в соотношении 1:1: создание Java-потока приводит к системному вызову
создания потока ядра, а исполнение Java-кода — это исполнение на реальном потоке ОС. Отсюда все свойства (и стоимость)
Java-потока наследуются от потока ОС.

Альтернатива 1:1 — модель M:N (много пользовательских «потоков» на немногих потоках ОС), которую в Java реализуют
виртуальные потоки (Project Loom). Но классический поток — именно 1:1.

## 2. Планировщик и стоимость потока

Какой из готовых (`RUNNABLE`) потоков получит ядро CPU, решает **планировщик ОС**, а не JVM. Планировщики обычно
вытесняющие и приоритетные: поток исполняется квант времени, затем вытесняется. Приоритет Java-потока (1–10) отображается
на приоритет ОС лишь как подсказка — гарантий порядка нет, и полагаться на приоритеты для корректности нельзя.

Стоимость платформенного потока складывается из:

- **Памяти** — стек (по умолчанию порядка мегабайта; настраивается `-Xss`) плюс структуры ядра. Десятки тысяч потоков —
  это десятки гигабайт только под стеки.
- **Переключения контекста** — сохранение/восстановление регистров, переключение таблиц памяти, инвалидация кешей и TLB.
  При числе потоков много больше числа ядер планировщик тратит заметную долю времени на переключения, а не на полезную
  работу.

Вывод: платформенных потоков должно быть немного (порядка числа ядер для CPU-bound задач; больше — для I/O-bound, но всё
равно ограниченно), и их переиспользуют через пулы. Радикальное снятие ограничения — виртуальные потоки.

## 3. Жизненный цикл и его связь с ОС

`Thread.State`: `NEW` → `RUNNABLE` → `TERMINATED`; из `RUNNABLE` — переходы в `BLOCKED` (ожидание монитора),
`WAITING`/`TIMED_WAITING` (ожидание условия/таймаута). Важная тонкость: `RUNNABLE` в Java объединяет и «исполняется на
ядре», и «готов, но ждёт ядро», и даже «ждёт в блокирующем системном вызове» — Java не различает их, хотя на уровне ОС
это разные состояния. `BLOCKED`/`WAITING` означают, что поток не прогрессирует, но его ресурсы (стек, поток ОС) заняты, —
именно это делает блокирующий I/O на платформенных потоках расточительным.

## 4. Создание, запуск, join

```java
void example(Runnable task, List<String> tickers, QuoteSource source) throws InterruptedException {
    Thread thread = Thread.ofPlatform().name("worker").daemon(false).start(task);

    Quote[] results = new Quote[tickers.size()];
    Thread[] threads = new Thread[tickers.size()];
    for (int i = 0; i < tickers.size(); i++) {
        int index = i;
        threads[i] = Thread.ofPlatform().start(() ->
                source.fetch(tickers.get(index)).ifPresent(q -> results[index] = q));
    }
    for (Thread t : threads) {
        t.join();   // happens-before: записи потока видны после join
    }
}
```

`Thread.ofPlatform()`/`ofVirtual()` — билдеры (Java 21). `daemon(true)` — фоновый поток, JVM не ждёт его завершения.
`join()` не только ждёт, но и устанавливает happens-before между действиями потока и кодом после `join`.

## 5. Параллелизм без общего состояния

Если потоки не делят изменяемое состояние (каждый пишет в свою ячейку `results[index]`), гонок нет по построению —
синхронизация не нужна. Это самый безопасный вид параллелизма и правильная отправная точка: сначала убедиться, что задача
раскладывается на независимые куски без общего состояния, и только при необходимости вводить разделяемое состояние (со
всеми вытекающими — следующий семинар).

Отдельно стоит помнить про безопасную публикацию: неизменяемые объекты (`final`-поля, без сеттеров — как `Quote`,
`Instrument`) безопасно передавать между потоками без синхронизации (подробнее — в материале про JMM).

## 6. Прерывание

Кооперативный механизм: `interrupt()` выставляет флаг; блокирующие методы бросают `InterruptedException` и сбрасывают
флаг; его восстанавливают (`Thread.currentThread().interrupt()`). Долгие вычислительные циклы без блокирующих вызовов
проверяют флаг сами (`isInterrupted()`). Проглоченное прерывание — код, который нельзя корректно остановить, и потерянный
сигнал для вызывающего.

## 7. Мостик к модели памяти

Даже корректно разложенный на потоки код упирается в вопросы видимости и порядка: гарантированно ли один поток видит
записи другого и в каком порядке они станут видны. Ответ даёт Java Memory Model через отношение happens-before,
инструменты `volatile`/`final`/`synchronized` и атомарные операции — см. материал
[«Java Memory Model»](./Java%20Memory%20Model.md).

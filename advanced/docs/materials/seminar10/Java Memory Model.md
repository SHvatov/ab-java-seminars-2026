# Java Memory Model

Java Memory Model (JMM) — контракт, описывающий, какие исполнения многопоточной программы валидны с учётом оптимизаций
компилятора, JIT и процессора. Материал разбирает, почему без JMM параллельный код непредсказуем, что такое
happens-before и как его устанавливают `volatile`, `synchronized`, `final` и атомарные операции.

## 1. Проблема: переупорядочивание и видимость

Рассмотрим два потока: поток 1 выполняет `x = 1; r1 = y;`, поток 2 — `y = 1; r2 = x;`. Интуитивно `(r1, r2)` может быть
`(1,1)`, `(1,0)`, `(0,1)`, но не `(0,0)`. На практике `(0,0)` встречается. Два независимых объяснения:

- **Instruction reordering.** Запись и чтение в каждом потоке независимы, поэтому компилятор/JIT/процессор вправе
  поменять их местами: чтение выполнится до записи. Тогда оба потока прочитают старые нули.
- **Visibility.** Даже без переупорядочивания запись одного потока может быть не видна другому: значение застряло в
  кеше ядра, пропагация отложена.

Оптимизируют на всех уровнях: компилятор байт-кода, JIT-компилятор машинного кода, процессор (out-of-order execution,
store buffers). Последовательности, эквивалентные в однопоточном исполнении, в многопоточном дают наблюдаемые различия.

## 2. JMM как контракт

JMM — не описание физической памяти (layout), а математическая модель: она строго задаёт, какие результаты исполнения
допустимы. Это абстракция между программистом и реализацией: код полагается на гарантии JMM, а конкретная
JVM/ОС/процессор вольны оптимизировать как угодно, лишь бы не нарушить контракт. Такой подход позволяет и агрессивные
оптимизации, и переносимые гарантии одновременно.

---

## 3. Happens-before

Центральное отношение JMM — **happens-before**: частичный порядок на действиях программы. Если A happens-before B, то
эффекты A (включая записи в память) видны в B независимо от переупорядочивания. Если между действиями двух потоков нет
цепочки happens-before, порядок и видимость между ними не гарантированы.

Основные источники happens-before:

- **Program order** — внутри одного потока каждое действие happens-before последующего.
- **Monitor lock** — освобождение монитора happens-before его последующего захвата (`synchronized`).
- **volatile** — запись volatile-переменной happens-before её последующего чтения.
- **Thread start/join** — `Thread.start()` happens-before любого действия запущенного потока; любое действие потока
  happens-before возврата `join()`.
- **Транзитивность** — если A hb B и B hb C, то A hb C.

Именно транзитивность делает `volatile`-флаг полезным: запись обычных полей до записи флага happens-before чтения этих
полей после чтения флага.

## 4. volatile

`volatile` даёт видимость (запись немедленно видна другим потокам) и запрет переупорядочивания вокруг обращения к
переменной. Классический паттерн безопасной публикации через флаг:

```java
class ResultProvider {
    private int value;                 // обычное поле
    private volatile boolean ready;    // volatile-флаг

    void publish(int v) {
        value = v;                     // (1)
        ready = true;                  // (2) volatile-запись; (1) happens-before (2)
    }

    int read() {
        if (!ready) return -1;         // (3) volatile-чтение
        return value;                  // (4) увидели ready==true ⇒ видим и value (транзитивность)
    }
}
```

Ограничение: `volatile` атомарен для одиночного чтения/записи, но не для составной операции. `volatile int count;
count++;` не потокобезопасен — между чтением и записью вклинивается другой поток. Для инкремента нужен CAS.

## 5. final и безопасная публикация

JMM даёт особую гарантию для `final`-полей: если объект корректно сконструирован (ссылка на `this` не «утекла» из
конструктора) и опубликован, то его `final`-поля видны всем потокам с правильными значениями — без синхронизации. Это
основа неизменяемых объектов: класс только с `final`-полями и без сеттеров (`Quote`, `Instrument`) безопасно шарить между
потоками как есть. Неизменяемость устраняет саму возможность гонки: нечего изменять — нечему рассинхронизироваться.

## 6. Атомарность и CAS

Составная операция (read-modify-write, например инкремент) требует атомарности, которой `volatile` не даёт.
**Compare-And-Swap (CAS)** — атомарная инструкция процессора «сравни текущее значение с ожидаемым и, если совпало, запиши
новое; верни, удалось ли». На CAS построены `Atomic*`:

```java
void example() {
    AtomicInteger counter = new AtomicInteger();
    counter.incrementAndGet();     // цикл: v = get(); compareAndSet(v, v+1); повтор при неудаче

    AtomicReference<String> ref = new AtomicReference<>("a");
    ref.compareAndSet("a", "b");   // записать "b", только если сейчас "a"
}
```

CAS — **неблокирующая** синхронизация: поток не засыпает на мониторе, а повторяет попытку. Свойство прогресса —
lock-free: система в целом всегда продвигается (хотя отдельный поток может повторять цикл). На этом держатся
высокопроизводительные структуры (`ConcurrentHashMap`, `ConcurrentLinkedQueue`), к которым вернёмся в семинаре про
потокобезопасные коллекции. Тонкость CAS — проблема ABA (значение сменилось с A на B и обратно на A), решаемая версиями
(`AtomicStampedReference`).

## 7. Три уровня гарантий

| Инструмент | Гарантия | Когда |
|---|---|---|
| `volatile` | видимость, запрет reordering (одиночные операции) | флаги, безопасная публикация |
| `synchronized` / `Lock` | взаимное исключение + happens-before | защита составного инварианта |
| `Atomic*` / CAS | атомарность RMW без блокировки | счётчики, lock-free структуры |
| неизменяемость (`final`) | нет разделяемого изменяемого состояния | доменные значения |

Правильный выбор — минимальный достаточный: неизменяемость дешевле блокировки, CAS-счётчик дешевле `synchronized`,
`volatile`-флаг дешевле всего, но годится только для одиночных операций.

# Чистая архитектура и границы сервисов

Материал разбирает Clean Architecture (правило зависимостей, слои, порты и адаптеры), применяет её к нашему коду — включая
очистку домена от фреймворка — и переходит к границам между сервисами: монолит против микросервисов.

## 1. Правило зависимостей

Clean Architecture строится вокруг одного правила — **правила зависимостей**: в исходном коде зависимости направлены
только внутрь. Внешние слои (UI, БД, сеть, фреймворки) знают о внутренних (прикладная логика, домен), но никогда
наоборот. Ничто во внутреннем слое не должно даже упоминать имя из внешнего.

Смысл — стабильность ядра. Детали (какой фреймворк сериализации, какой транспорт, какая БД) меняются часто; бизнес-логика
и домен — редко. Если зависимости идут внутрь, смена детали не затрагивает ядро.

---

## 2. Слои Clean Architecture

Концентрические слои от внешнего к внутреннему:

- **Frameworks & Drivers** — сеть, диск, UI, библиотеки: `cli`, `storage`, `HttpQuoteSource`.
- **Interface Adapters** — переводят данные между внешним миром и логикой (адаптеры портов).
- **Use Cases (Application)** — прикладные сценарии: `QuoteService`.
- **Entities (Domain)** — доменные сущности и правила: `Instrument`, `Quote`, `Watchlist`.

Домен — самый внутренний слой; он не знает ни о сети, ни о диске, ни о фреймворках. Прикладной слой знает о домене, но не
о деталях внешнего мира. Внешние слои знают обо всём внутреннем.

---

## 3. Порты и адаптеры

Чтобы зависимость шла внутрь, а внешний слой оставался подключаемым, применяют инверсию зависимости: внутренний слой
объявляет **порт** (интерфейс), внешний реализует его **адаптером**. Прикладная логика зависит от порта; конкретный
адаптер подставляется снаружи (композиция в точке входа).

```
        Application                 Frameworks & Drivers
        ┌───────────────┐            ┌───────────────────┐
        │ QuoteService  │──▶ QuoteSource ◀──│ HttpQuoteSource │
        └───────────────┘   (порт)          └───────────────────┘
                  зависимость направлена к порту (внутрь)
```

Без инверсии `QuoteService` зависел бы напрямую от `HttpClient` и токена — деталь внешнего слоя оказалась бы в ядре, а
код стал бы непроверяемым.

---

## 4. Порты в нашем проекте

Инверсия зависимости в Market Pulse уже реализована — на двух портах:

- **`QuoteSource`** (интерфейс). `QuoteService` зависит от него, а не от `HttpQuoteSource`. Адаптер (`HttpQuoteSource`)
  подключается в `Main`. Именно это позволяет подменить источник mock'ом в тестах и заменить заглушку реальным сетевым
  клиентом, не трогая `QuoteService`.
- **`InstrumentRepository`** (интерфейс). CLI зависит от абстракции; `InMemoryInstrumentRepository` — одна реализация,
  а завтра может появиться, например, репозиторий поверх БД, без правки вызывающего кода.

Порт окупается многократно: тестируемость, заменяемость реализации, изоляция ядра от деталей.

## 5. Нарушение: домен зависит от фреймворка

Правило зависимостей в проекте нарушено в одном месте. После добавления файлового хранилища доменные классы получили
аннотации Jackson:

```java
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, include = JsonTypeInfo.As.PROPERTY, property = "type")
@JsonSubTypes({ /* ... */ })
public abstract class Instrument { /* ... */ }
```

`Instrument` (домен, самый внутренний слой) зависит от Jackson (библиотека внешнего слоя). Симптомы: смена сериализатора
потребует правки домена; доменные классы нельзя использовать в контексте, где Jackson не нужен или недоступен. Деталь
внешнего слоя протекла в ядро.

---

## 6. Очистка домена через mixin

Jackson позволяет вынести аннотации из класса в отдельный **mixin** — абстрактный тип, привязываемый к целевому классу
снаружи, без правки самого класса. Знание о сериализации переезжает в слой `storage`:

```java
// storage/InstrumentJsonMixin — полиморфизм
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, include = JsonTypeInfo.As.PROPERTY, property = "type")
@JsonSubTypes({
        @JsonSubTypes.Type(value = Stock.class, name = "STOCK"),
        @JsonSubTypes.Type(value = Bond.class, name = "BOND"),
        @JsonSubTypes.Type(value = Etf.class, name = "ETF")
})
abstract class InstrumentJsonMixin { }

// storage/StockJsonMixin — конструктор для десериализации
abstract class StockJsonMixin {
    @JsonCreator
    StockJsonMixin(@JsonProperty("ticker") String ticker, /* ... */) { }
}
```

```java
// InstrumentStorage регистрирует mixin'ы в ObjectMapper
void example(ObjectMapper mapper) {
    mapper.addMixIn(Instrument.class, InstrumentJsonMixin.class);
    mapper.addMixIn(Stock.class, StockJsonMixin.class);
    mapper.addMixIn(Bond.class, BondJsonMixin.class);
    mapper.addMixIn(Etf.class, EtfJsonMixin.class);
}
```

Аннотации уходят из `model` — домен снова свободен от фреймворка; знание о формате живёт в адаптере хранения.
Характеризационный тест round-trip (сохранить → загрузить) остаётся зелёным: изменилось не поведение, а место, где живёт
знание о сериализации.

Это рефакторинг в чистом виде — исправление нарушения правила зависимостей без изменения поведения, проверенное тестом.
Цена — дополнительные классы-mixin: за архитектурную чистоту всегда платят сложностью, и для небольшого проекта плата
может не окупиться, так что аннотации прямо на домене там остаются приемлемым компромиссом.

## 7. Монолит против микросервисов

**Монолит** — одно развёртываемое приложение; компоненты общаются внутренними вызовами. Market Pulse — монолит.
**Микросервисы** — отдельно развёртываемые сервисы со своими данными, общающиеся по сети.

Границы будущих сервисов совпадают с портами: `QuoteSource` (котировки), `InstrumentRepository`/`InstrumentStorage`
(каталог), `WatchlistStorage` (watchlist). Микросервис прошёл бы по такому шву, заменив внутренний вызов интерфейса
сетевым. Чистые границы монолита — предпосылка к разделению: плохие границы внутри монолита станут плохими границами по
сети, только дороже в отладке и эксплуатации.

Цена микросервисов — сетевые вызовы вместо внутренних (задержки, частичные сбои), распределённые данные и согласованность
в конечном счёте, распределённая трассировка, оркестрация и мониторинг. Для CLI-утилиты одного пользователя это чистый
проигрыш.

---

## 8. Границы и monolith-first

Дробить на сервисы имеет смысл, когда у частей системы **разный цикл изменений**, **разная нагрузка** или **разные
команды**-владельцы — то есть когда независимое развёртывание и масштабирование дают реальную выгоду. Пока этого нет,
монолит с чистыми внутренними границами выигрывает по всем осям.

Практическое правило — **monolith first**: начинать с монолита, держать в нём ясные границы (порты, слои, правило
зависимостей) и выделять сервис только под доказанную потребность. Микросервисы решают организационные и масштабные
задачи, а не задачи качества кода: разнесённый по сети плохой код не становится лучше — он становится распределённым.
Хорошо структурированный монолит одновременно и достаточен для проекта такого размера, и является правильной отправной
точкой, если он когда-нибудь дорастёт до разделения.

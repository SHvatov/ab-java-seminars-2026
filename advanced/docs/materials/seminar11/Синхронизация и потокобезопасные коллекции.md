# Синхронизация и потокобезопасные коллекции

Общее изменяемое состояние между потоками требует синхронизации. Материал разбирает низкоуровневую базу (монитор,
`synchronized`, `wait`/`notify`), высокоуровневые синхронизаторы и их общую основу (AQS), классификацию потокобезопасных
коллекций по гарантии прогресса и классические проблемы конкурентности.

## 1. Монитор, synchronized, wait/notify

У каждого объекта в Java есть **монитор** с двумя множествами — Entry Set и Wait Set — и владельцем (не более одного
потока в единицу времени). `synchronized` захватывает монитор на входе в блок/метод и освобождает на выходе; потоки, не
получившие монитор, ждут в Entry Set. Освобождение монитора **happens-before** его последующего захвата — отсюда
`synchronized` гарантирует не только взаимное исключение, но и видимость (семинар про JMM).

`wait()`/`notify()`/`notifyAll()` вызываются только при владении монитором. `wait()` освобождает монитор и переводит поток
в Wait Set; `notify()` перемещает один поток из Wait Set в Entry Set (он продолжит, когда снова получит монитор).
`wait()` всегда используют в цикле проверки условия (защита от ложных пробуждений):

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();       // освобождает монитор, ждёт notify
    }
    // условие выполнено, монитор снова наш
}
```

Это низкоуровневая база; на практике поверх неё используют синхронизаторы.

## 2. Data race на общем состоянии

Незащищённая одновременная запись в общий `HashMap` повреждает его структуру: потерянные записи, `ConcurrentModificationException`,
исторически — закольцевание цепочки при рехешировании (бесконечный цикл). Плюс ошибка check-then-act: «`get` → если null →
`put`» неатомарна. Грубая починка — `synchronized (map)` вокруг доступа: корректно, но сериализует весь доступ. Правильная
— потокобезопасная коллекция (раздел 6).

## 3. AQS — основа синхронизаторов

Большинство синхронизаторов (`ReentrantLock`, `Semaphore`, `CountDownLatch`, `CyclicBarrier`) построены на
`AbstractQueuedSynchronizer` (AQS). AQS хранит атомарное `int`-состояние (меняется через CAS) иFIFO-очередь ожидающих
потоков. Синхронизатор определяет, что означает состояние (для `Semaphore` — число разрешений, для `CountDownLatch` —
счётчик, для `ReentrantLock` — глубина захвата), а AQS берёт на себя постановку в очередь, парковку/распарковку потоков
(`LockSupport.park`) и справедливость. Понимание AQS объясняет, почему все они ведут себя единообразно (прерываемое
ожидание, таймауты, справедливый/несправедливый режим).

---

## 4. Обзор синхронизаторов

- `CountDownLatch` — одноразовый барьер «дождаться N».
- `CyclicBarrier` — многоразовая точка сбора N потоков (+ действие при срабатывании).
- `Phaser` — многофазный барьер с динамическим числом участников.
- `Semaphore` — ограничение одновременности (рейт-лимитер).
- `ReentrantLock`/`ReentrantReadWriteLock` — явные блокировки с `tryLock(timeout)`, справедливостью, разделением
  read/write.
- `StampedLock` — read/write с оптимистичным чтением (быстрее RRWL на преобладающих чтениях; не реентрантен).
- `Exchanger` — обмен объектами между двумя потоками.

Детальные примеры — в презентационном материале «Синхронизаторы». Правило: блокирующие операции — с таймаутом.

## 5. Прогресс: blocking / lock-free / wait-free

Способ обеспечения потокобезопасности задаёт гарантию прогресса:

- **Blocking** — поток без замка засыпает; при контеншене простой, риск взаимоблокировок.
- **Lock-free** — на CAS; гарантирован прогресс системы (хоть один поток всегда продвигается), отдельный может повторять
  цикл.
- **Wait-free** — каждый поток завершает операцию за конечное число шагов независимо от других.

`CopyOnWriteArrayList` даёт wait-free чтение (по неизменяемому снимку), `ConcurrentLinkedQueue` — lock-free
(`offer`/`poll` на CAS), `synchronizedMap`/`BlockingQueue` — blocking.

## 6. Внутри ConcurrentHashMap

`ConcurrentHashMap` сочетает подходы. Массив корзин; вставка первого узла в пустую корзину — атомарным CAS без блокировки;
запись в занятую корзину — под `synchronized` на **головном узле именно этой корзины** (не на всей карте), поэтому потоки
с разными ключами почти не конфликтуют. Чтение идёт без блокировок (узлы `volatile`, видимость гарантирована). При росте
таблица рехешируется кооперативно — потоки, попавшие на занятую рехешем корзину, помогают переносить. Отсюда
масштабируемость, которой лишён `synchronizedMap` с единым замком. `computeIfAbsent`/`compute`/`merge` — атомарные
составные операции поверх этого.

## 7. CAS и проблема ABA

Lock-free структуры строятся на CAS: «если значение всё ещё ожидаемое — заменить». Тонкость — **ABA**: поток прочитал
`A`, другой сменил `A→B→A`; CAS видит `A` и «успевает», хотя состояние менялось, — что может нарушить инвариант (например,
в стеке на связных узлах). Решение — версии/метки: `AtomicStampedReference` (значение + счётчик версии) или
`AtomicMarkableReference`. Стандартные коллекции JDK это уже учитывают; знать про ABA важно при написании собственных
lock-free структур.

---

## 8. Deadlock, livelock, starvation

- **Deadlock** — циклическое ожидание блокировок (A держит r1 ждёт r2, B держит r2 ждёт r1). Профилактика — глобальный
  порядок захвата, таймауты (`tryLock`).
- **Livelock** — потоки активны, но не прогрессируют, бесконечно реагируя друг на друга (оба уступают).
- **Starvation** — поток не получает ресурс из-за несправедливого доступа; лечится справедливыми блокировками (fair
  `ReentrantLock`) ценой пропускной способности.

Выявление — thread dump/профилировщик (видно, кто на каком мониторе висит) и мониторинг. Стратегически надёжнее всего —
сокращать разделяемое изменяемое состояние и предпочитать неизменяемость: то, что нельзя изменить, не нуждается в
синхронизации.

# Project Loom и Continuation Pattern

---

## Проблема: поток ОС на время ожидания

Платформенный поток на блокирующем I/O простаивает, занимая поток ОС (стек, слот планировщика). Поэтому пулы ограничены,
и модель «поток на соединение/задачу» не масштабируется на тысячи одновременных ожиданий (проблема C10K). Раньше выход
был один — неблокирующий/реактивный код (колбэки, `CompletableFuture`, реактивные стримы), который эффективен, но
«выворачивает» логику наизнанку.

---

## Виртуальные потоки

Виртуальный поток (Java 21) — лёгкий поток, управляемый рантаймом JVM, а не ядром ОС. Их можно создавать миллионами.
Модель исполнения — **M:N**: много виртуальных потоков поверх немногих платформенных потоков-**носителей** (carrier),
которые берутся из выделенного `ForkJoinPool`.

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // виртуальный поток на задачу; блокирующий код внутри не блокирует поток ОС
}
```

---

## Continuation Pattern: mount / unmount

Ключевая механика — continuation (продолжение): сохранённое состояние исполнения (стек), которое можно приостановить и
возобновить.

- Виртуальный поток исполняется, будучи **смонтированным** (mount) на поток-носитель.
- Когда он упирается в блокирующую операцию (сетевое чтение), рантайм **размонтирует** (unmount) его: стек виртуального
  потока сохраняется в куче как continuation, а носитель освобождается для другого виртуального потока.
- Когда операция готова, виртуальный поток **монтируется** обратно на какой-нибудь носитель и продолжает с сохранённой
  точки.

Итог: блокирующий по виду вызов не блокирует поток ОС — на время ожидания носитель занят другой работой. Это и есть
«синхронный код с асинхронной эффективностью»: логика остаётся прямой (`source.fetch(ticker)` — обычный вызов), а
неблокирующий I/O спрятан в рантайме, а не в колбэках прикладного кода.

## Пример: блокирующий сетевой I/O на виртуальных потоках

Каноничный разбор — «Networking IO with Virtual Threads» (`inside.java/2021/05/10/networking-io-with-virtual-threads`):
тысячи одновременных блокирующих соединений обслуживаются на горстке потоков ОС, потому что каждое ожидание чтения
размонтирует свой виртуальный поток. Наш `quotesFor` — ровно этот случай: много блокирующих HTTP-вызовов, каждый из
которых почти всё время ждёт.

Связь с семинаром 7: там `HttpClient` внутри опирался на неблокирующие каналы и `Selector`, пряча асинхронность за
колбэками. Loom даёт ту же эффективность, но код остаётся синхронным — mount/unmount делает то же неблокирующее ожидание
прозрачно для прикладного кода.

## Тонкости

- **Pinning.** Если виртуальный поток блокируется внутри `synchronized`-блока или нативного вызова, он не может
  размонтироваться — «пришпилен» (pinned) к носителю. Отсюда рекомендация: для защиты критических секций в коде,
  работающем на виртуальных потоках, предпочитать `ReentrantLock` вместо `synchronized`.
- **Не для CPU-bound.** Виртуальные потоки снимают ограничение на число одновременно ждущих задач, но не добавляют
  вычислительной мощности: CPU-bound работу по-прежнему ограничивает число ядер.
- **Дёшевы, но не бесплатны.** Создавать по виртуальному потоку на задачу — нормально; пулить их не нужно и вредно.

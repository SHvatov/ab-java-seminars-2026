### Этап 1. `ExecutorService` и `Future` вместо ручных потоков (~20 мин)

Лекция по материалу [«Executor Framework»](./Executor%20Framework.md).

Ручное управление потоками из семинара 10 (`Thread[]` + `join`) заменяем на пул: задачи отделены от исполнителя, потоки
переиспользуются.

```java
try (ExecutorService executor = Executors.newFixedThreadPool(8)) {
    List<Future<Optional<Quote>>> futures = list.stream()
            .map(ticker -> executor.submit(() -> cachedFetch(ticker)))   // Callable → Future
            .toList();
    return futures.stream().map(this::get).flatMap(Optional::stream).toList();
}   // AutoCloseable (Java 21+): close() дожидается задач и гасит пул
```

`Callable` (в отличие от `Runnable`) возвращает значение и может бросать checked-исключения; `submit` возвращает
`Future` (get/cancel/isDone). Кеш (`ConcurrentHashMap`, семинар 11) и прогресс (`AtomicInteger`) сохраняются.

> **Акцент:** отделение задач от исполнителя — то, что позволит на этапе 4 сменить пул на виртуальные потоки, не трогая
> код задач.

### Этап 2. `CompletableFuture`: конвейеры и где они исполняются (~25 мин)

Лекция по материалу [«CompletableFuture»](./CompletableFuture.md).

`Future.get()` блокирует. `CompletableFuture` описывает обработку результата по готовности и строит конвейеры:

```java
CompletableFuture.supplyAsync(() -> cachedFetch(ticker), executor)
        .thenApply(this::enrich)
        .exceptionally(ex -> Optional.empty());
```

Категории методов `CompletionStage`: `thenApply`/`thenAccept`/`thenRun` (последовательный конвейер);
`thenCombine`/`thenCompose`/`acceptEither` (композиция нескольких стадий); `handle`/`exceptionally` (обработка ошибок);
`...Async`-варианты. Важный нюанс — **где** исполняется стадия: не-`Async`-метод выполняется в потоке, завершившем
предыдущую стадию; `...Async` без executor'а — в общем `ForkJoinPool.commonPool()`; `...Async` с executor'ом — в
заданном пуле. Исключения пропагируются вниз по конвейеру (сверху вниз), не вверх.

> **Самостоятельно (студенты):** перевести `quotesFor` на `CompletableFuture` c `exceptionally`, чтобы сбой одного
> тикера превращался в пропуск, а не рушил пакет. Проговорить, в каком пуле окажется каждая стадия.

### Этап 3. Project Loom и Continuation Pattern (~35 мин)

Лекция по материалу [«Project Loom и Continuation Pattern»](./Project%20Loom%20и%20Continuation%20Pattern.md); подробно —
в deep-dive [«Виртуальные потоки и Continuation Pattern»](../../materials/seminar12/Виртуальные%20потоки%20и%20Continuation%20Pattern.md).

Платформенный поток на блокирующем I/O простаивает, занимая поток ОС, — отсюда ограниченные пулы. Виртуальные потоки
(Java 21) снимают это ограничение.

**Continuation Pattern — как это устроено.** Виртуальный поток исполняется на **потоке-носителе** (carrier, платформенный
поток из пула ForkJoinPool). Когда виртуальный поток упирается в блокирующую операцию (сетевое чтение), рантайм
**размонтирует** (unmount) его с носителя, сохранив стек как *continuation* в куче, и освобождает носитель для другого
виртуального потока. Когда I/O готов, виртуальный поток **монтируется** (mount) обратно на какой-нибудь носитель и
продолжает с сохранённой точки. Блокирующий по виду код на самом деле не блокирует поток ОС — это и есть суть Loom:
синхронный стиль, асинхронная эффективность.

Каноничный пример — сетевой I/O на виртуальных потоках (`inside.java/2021/05/10/networking-io-with-virtual-threads`):
тысячи одновременных блокирующих соединений на горстке потоков ОС, без реактивного «выворачивания» кода наизнанку. Наш
`quotesFor` — ровно этот случай: много блокирующих HTTP-вызовов.

> **Для семинариста:** свяжите с семинаром 7 — там `HttpClient` внутри опирался на неблокирующие каналы и `Selector`,
> пряча асинхронность за колбэками. Loom даёт ту же эффективность, но код остаётся прямым и синхронным — mount/unmount
> прячет неблокирующий I/O под капот рантайма, а не в колбэки прикладного кода.

### Этап 4. Классический пул против виртуальных потоков: замер через JMH (~30 мин)

Сначала — классический `ExecutorService` с пулом платформенных потоков (как на этапе 1): при большом числе блокирующих
задач упираемся либо в размер пула (задачи ждут очереди), либо в число потоков ОС (если пул большой — дорогое
переключение контекста). Затем — замена одной строкой:

```java
Executors.newFixedThreadPool(8)              // было: 8 платформенных потоков, задачи в очереди
Executors.newVirtualThreadPerTaskExecutor()  // стало: виртуальный поток на задачу
```

Код задач не меняется (отделены от исполнителя). JMH-бенчмарк `VirtualThreadsBenchmark` сравнивает пропускную способность
на смоделированной блокирующей нагрузке (I/O заменён на `sleep`, чтобы не зависеть от сети): на I/O-bound задачах
виртуальные потоки дают кратный выигрыш при росте числа задач; на CPU-bound разницы нет.

> **Акцент:** вывод для проекта и в общем — виртуальные потоки снимают ограничение на число одновременно **ждущих**
> задач, а не ускоряют вычисления. Правило выбора: I/O-bound с высокой одновременностью → виртуальные потоки; CPU-bound
> → пул по числу ядер. Замер (а не интуиция) — единственный честный аргумент, ровно как в семинаре про JMH.

### Этап 1. Обзор JCF: иерархия, реализации, сложность операций (~15 мин)

Презентация по материалу [«Java Collection Framework»](./Java%20Collection%20Framework.md), разделы про иерархию и
сложность операций.

Единственной «коллекцией» в проекте до сих пор был сырой массив `Instrument[100]` внутри репозитория: фиксированный
размер, ручной `size`, линейный поиск. Java Collection Framework (JCF) даёт готовый набор структур данных под разные
задачи, разделяя контракт (`List`, `Set`, `Queue`, `Map`) и реализацию (`ArrayList`, `HashSet`, `ArrayDeque`,
`HashMap`).

Корень иерархии коллекций — `Iterable` → `Collection` → `List`/`Set`/`Queue`. `Map` стоит отдельно и **не** наследует
`Collection` (оперирует парами, а не элементами; у неё нет `iterator()`, перебор — через `keySet`/`values`/`entrySet`).

> **Акцент — сложность как критерий выбора.** Ключ к правильному выбору структуры — асимптотика её основной операции.
> Поиск по значению в `ArrayList` — `O(n)`; поиск по ключу в `HashMap`/`HashSet` — `O(1)` в среднем; операции в
> `TreeMap`/`TreeSet` — `O(log n)`. Полная таблица сложности по реализациям — в материале
> [«Java Collection Framework»](../../materials/seminar5/Java%20Collection%20Framework.md). Эти цифры сегодня не
> берутся на веру — на этапе 5 они замеряются через JMH.

> **Связь с семинаром 1.** Выбор коллекции — это ещё и выбор раскладки в памяти: `ArrayList` хранит ссылки подряд в
> одном массиве, `LinkedList` — по узлу на элемент с двумя дополнительными ссылками, `HashMap` — массив бакетов плюс
> узлы. Инструмент JOL из семинара 1 позволяет увидеть эту разницу в байтах, к чему вернёмся на этапе 6 при разговоре
> о специализированных коллекциях.

### Этап 2. Из требований к структурам данных: List, Set, Queue, Map (~15 мин)

Идём от требований проекта, а не от справочника реализаций. Market Pulse обзаводится двумя обязанностями:

1. **Хранить watchlist** — тикеры инструментов, интересные пользователю (пока в коде, на семинаре 7 переедет на диск).
2. **Получать котировки по запросу** — по «внешнему API»; реальной сети ещё нет (семинар 7), источник — заглушка с
   заготовленными данными.

> **Обсуждение с группой (~5 мин):** прежде чем показывать решение, разбираем, какая структура данных ложится на
> каждую задачу и почему — по критерию сложности основной операции.

| Задача | Что важно | Структура |
|--------|-----------|-----------|
| Индекс инструментов: поиск по тикеру, запрет дубликатов | `O(1)` поиск по ключу, уникальность ключа | `Map<String, Instrument>` |
| Watchlist: набор отслеживаемых тикеров | уникальность, `O(1)` проверка «есть ли» | `Set<String>` |
| Очередь запросов котировок | FIFO, `O(1)` в хвост/из головы | `Queue<String>` |
| Кеш котировок: тикер → котировка | `O(1)` поиск по ключу | `Map<String, Quote>` |
| Результат `list`: упорядоченный вывод | порядок, индексный доступ | `List<Instrument>` |

Индекс инструментов и watchlist переезжают на hash-структуры именно потому, что их основная операция — поиск —
перестаёт зависеть от объёма данных. Под интерфейс берутся `LinkedHashMap`/`LinkedHashSet`: та же `O(1)`-сложность,
что и у `HashMap`/`HashSet`, но с сохранением порядка добавления, что важно для предсказуемого вывода.

### Этап 3. Практика: индекс инструментов на Map, watchlist на Set (~20 мин)

Реализуется вживую вместе с группой.

**3.1. Репозиторий с массива на `Map`.** `InMemoryInstrumentRepository` (реализация интерфейса `InstrumentRepository`,
введённого на семинаре 2 ради Proxy) переводится с `Instrument[100]` на `LinkedHashMap<String, Instrument>`:

```java
public class InMemoryInstrumentRepository implements InstrumentRepository {

    private final Map<String, Instrument> instruments = new LinkedHashMap<>();

    @Override
    public void add(Instrument instrument) {
        String key = instrument.getTicker().toUpperCase();
        if (instruments.containsKey(key)) {
            throw new DuplicateTickerException(instrument.getTicker());
        }
        instruments.put(key, instrument);
    }

    @Override
    public Optional<Instrument> findByTicker(String ticker) {
        return Optional.ofNullable(instruments.get(ticker.toUpperCase()));
    }

    @Override
    public Iterator<Instrument> iterator() {
        return instruments.values().iterator();
    }
}
```

Линейный `findByTicker` и повторный линейный проход при проверке дубликата (`DuplicateTickerException` из семинара 4)
заменяются на `Map.get`/`containsKey` — `O(1)`. Интерфейс `InstrumentRepository` не меняется, поэтому JDK Dynamic
Proxy и CGLIB из семинара 2 продолжают работать поверх той же абстракции.

> **Акцент — нормализация ключа.** Массивная версия искала регистронезависимо (`equalsIgnoreCase`). У `Map` равенство
> ключей строгое (`String.hashCode`/`equals` чувствительны к регистру), поэтому ключ приводится к верхнему регистру и
> при записи, и при чтении. Типовая ловушка перехода на hash-структуру: ключ надо нормализовать в одном месте.

**3.2. Watchlist на `Set`.** Как в базовом треке — новый класс `Watchlist` поверх `LinkedHashSet<String>`, с опорой на
то, что `Set.add` возвращает `false` для уже присутствующего элемента (не нужен предварительный `contains`), а наружу
множество отдаётся неизменяемым представлением (`Collections.unmodifiableSet`). Подключается CLI-командой `watch`
(`cli/WatchCommand`), зарегистрированной в `Main` с общим на приложение экземпляром `Watchlist`.

**3.3. Collections API.** Утильный класс `java.util.Collections` — статические операции над коллекциями (`sort` с
`Comparator`, `max`/`min`, `frequency`, `unmodifiableList`/`unmodifiableSet`). Сортировку по `Comparator` студенты
видели в `ListCommand` семинара 3; `Collections.sort` — тот же механизм в форме статической утилиты, сортирует
изменяемый список на месте (в отличие от `stream().sorted()`, возвращающего новый, — Stream API следующий семинар).

### Этап 4. Самостоятельная задача: очередь запросов и кеш котировок (~20 мин)

Реализуется студентами самостоятельно; условие и разбор — на семинаристе. Постановка совпадает с базовым треком.

**Условие.** Пользователь запрашивает котировки сразу по нескольким тикерам; запросы обрабатываются в порядке
поступления (FIFO), результаты кешируются, повторный запрос не ходит к источнику снова. Источник — заглушка
`QuoteSource` с заготовленными данными.

Дана заглушка источника; реализовать `QuoteService`, который хранит `Queue<String>` запросов и `Map<String, Quote>`
кеш; метод `request` кладёт тикер в хвост очереди (`offer`), `processAll` разгребает очередь (`poll`), тянет котировку
из источника и кладёт в кеш, пропуская уже закешированные, `cached` отдаёт из кеша.

```java
public class QuoteService {

    private final QuoteSource source;
    private final Queue<String> pending = new ArrayDeque<>();
    private final Map<String, Quote> cache = new HashMap<>();

    public QuoteService(QuoteSource source) {
        this.source = source;
    }

    public void request(String ticker) {
        pending.offer(ticker.toUpperCase());
    }

    public void processAll() {
        while (!pending.isEmpty()) {
            String ticker = pending.poll();
            if (cache.containsKey(ticker)) {
                continue;
            }
            source.fetch(ticker).ifPresent(quote -> cache.put(ticker, quote));
        }
    }

    public Optional<Quote> cached(String ticker) {
        return Optional.ofNullable(cache.get(ticker.toUpperCase()));
    }
}
```

> **Акцент:** `ArrayDeque` — реализация `Queue`/`Deque` общего назначения на кольцевом буфере; `offer`/`poll` — `O(1)`,
> накладных расходов меньше, чем у `LinkedList`. Разделение «положить запрос» и «обработать» — заготовка под
> асинхронную обработку: очередь запросов на будущих семинарах сможет разгребать отдельный поток.

`QuoteService` подключается CLI-командой `quote` (`cli/QuoteCommand`): `market-pulse quote SBER GAZP` кладёт тикеры в
очередь, обрабатывает её и печатает котировки. Источник в `Main` — `QuoteSource`, засеянный заготовленными котировками
(заглушка «внешнего API»; реальный сетевой источник — семинар 7).

> **Для семинариста:** к концу семинара в CLI появляются две новые рабочие команды — `watch` и `quote`; это и есть
> проверка, что доменный код встроен в приложение, а не написан «в стол». Удобно показать живьём:
> `market-pulse quote SBER GAZP` и `market-pulse watch SBER`.

### Этап 5. JMH: O-нотация вживую — ArrayList vs LinkedList (~25 мин)

Методология JMH разобрана на семинаре 4 (прогрев JIT, `Blackhole`, чтение результатов) — здесь она применяется к
структурам данных. Асимптотика из этапа 1 — не абстракция из учебника, её видно на замере.

Заранее заготовленный бенчмарк сравнивает `ArrayList` и `LinkedList` на трёх операциях с разной асимптотикой:

```java
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@State(Scope.Thread)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(1)
public class CollectionComplexityBenchmark {

    @Param({"1000", "100000"})
    private int size;

    private List<Integer> arrayList;
    private List<Integer> linkedList;

    @Setup
    public void setup() {
        arrayList = new ArrayList<>();
        linkedList = new LinkedList<>();
        for (int i = 0; i < size; i++) {
            arrayList.add(i);
            linkedList.add(i);
        }
    }

    @Benchmark
    public Integer arrayListGetMiddle() {
        return arrayList.get(size / 2);      // O(1)
    }

    @Benchmark
    public Integer linkedListGetMiddle() {
        return linkedList.get(size / 2);     // O(n)
    }

    @Benchmark
    public void arrayListAddFirst(Blackhole bh) {
        arrayList.add(0, 42);                // O(n): сдвиг всех элементов
        arrayList.remove(0);
        bh.consume(arrayList);
    }

    @Benchmark
    public void linkedListAddFirst(Blackhole bh) {
        linkedList.addFirst(42);             // O(1): перестановка ссылок
        linkedList.removeFirst();
        bh.consume(linkedList);
    }
}
```

**Ожидаемая картина** (важно относительное соотношение, не абсолютные числа): `arrayListGetMiddle` практически не
зависит от `size` — доступ по индексу `O(1)`; `linkedListGetMiddle` растёт с `size` на порядки и на `100000` элементов
катастрофически медленнее — обход по ссылкам `O(n)`. На вставке в начало картина обратная: `linkedListAddFirst` не
зависит от `size` (`O(1)` — перестановка ссылок), `arrayListAddFirst` растёт с `size` (`O(n)` — `System.arraycopy`
сдвигает хвост).

> **Вывод.** `LinkedList` формально выигрывает на вставке в начало, но проигрывает на индексном доступе, и на практике
> `ArrayList` почти всегда быстрее за счёт локальности памяти (данные лежат подряд, дружелюбны к кешу процессора) —
> ровно тот эффект, который на уровне раскладки объектов показывал JOL на семинаре 1. Асимптотика — необходимый, но не
> достаточный критерий: константа и поведение в кеше решают не меньше.

> **Для семинариста:** разница в стоимости `get(i)` формализована маркерным интерфейсом `RandomAccess` (`ArrayList` его
> реализует, `LinkedList` — нет). Хороший момент проговорить связанную ловушку: обход `LinkedList` по индексу
> (`for (i) list.get(i)`) — это `O(n²)`, и именно поэтому обобщённые алгоритмы JDK (`Collections.binarySearch`,
> `shuffle`) проверяют `instanceof RandomAccess` и переключают стратегию обхода. Подробнее — в материале
> [«Java Collection Framework»](../../materials/seminar5/Java%20Collection%20Framework.md), раздел про `RandomAccess`.

### Этап 6. Внешние библиотеки коллекций: Guava, Apache Commons (~15 мин)

Стандартный JCF закрывает большинство задач, но экосистема предлагает коллекции, которых в стандартной библиотеке нет
или которые в ней многословны.

**Guava.** Иммутабельные коллекции и мультиотображения:

```java
void example() {
    // Иммутабельный seed для заглушки источника — нельзя случайно изменить после создания
    Map<String, Quote> seed = ImmutableMap.of(
            "SBER", sberQuote,
            "GAZP", gazpQuote);

    // Multimap: один ключ → несколько значений, без ручного Map<K, List<V>>
    Multimap<Currency, Instrument> byCurrency = ArrayListMultimap.create();
    byCurrency.put(Currency.RUB, sber);
    byCurrency.put(Currency.RUB, gazp);
    Collection<Instrument> rub = byCurrency.get(Currency.RUB); // [sber, gazp]
}
```

`ImmutableMap`/`ImmutableList` отличаются от `Collections.unmodifiableMap` тем, что это по-настоящему неизменяемая
копия, а не обёртка над изменяемым оригиналом (оригинал за обёрткой `unmodifiable*` всё ещё может измениться).
`Multimap` избавляет от ручного `Map<K, List<V>>` с проверкой на `null` и созданием списка при первом добавлении.

**Apache Commons Collections.** Утилиты и структуры, дополняющие `java.util.Collections`:

```java
void example() {
    // Теоретико-множественные операции над коллекциями
    Collection<String> both = CollectionUtils.intersection(watchlistA, watchlistB);

    // Bag: мультимножество, считает количество вхождений каждого элемента
    Bag<Currency> currencyCounts = new HashBag<>();
    currencyCounts.add(Currency.RUB);
    currencyCounts.add(Currency.RUB);
    int rub = currencyCounts.getCount(Currency.RUB); // 2
}
```

> **Для семинариста:** цель этапа — не выучить API конкретной библиотеки, а показать, что за пределами `java.util`
> есть зрелые коллекции под специализированные задачи (иммутабельность, мультиотображения, мультимножества,
> теоретико-множественные операции), и что тянуть их стоит осознанно — под конкретную нужду, а не по умолчанию.
> Примитивные коллекции (FastUtils и подобные), экономящие память на отказе от boxing, — отдельная большая тема,
> смыкающаяся с разговором о раскладке объектов из семинара 1; упоминается со ссылкой на самостоятельное изучение.

### Этап 7. Итераторы: fail-fast, Iterator.remove (~10 мин)

На семинаре 2 `Iterator` использовался только для обхода. Прямое удаление из коллекции во время for-each по ней роняет
программу с `ConcurrentModificationException`:

```java
void example(List<String> tickers) {
    for (String ticker : tickers) {
        if (ticker.startsWith("T")) {
            tickers.remove(ticker); // ConcurrentModificationException
        }
    }
}
```

Механизм — **fail-fast**: каждая структурная модификация увеличивает внутренний счётчик `modCount`; итератор
запоминает его при создании и сверяет на каждом `next()`. Расхождение означает изменение в обход итератора — итератор
бросает исключение, а не продолжает с потенциально испорченным состоянием. «Concurrent» здесь не про многопоточность:
одного потока достаточно.

Безопасное удаление по ходу обхода — через сам итератор, `Iterator.remove()` синхронно обновляет `modCount`:

```java
void example(List<String> tickers) {
    Iterator<String> it = tickers.iterator();
    while (it.hasNext()) {
        if (it.next().startsWith("T")) {
            it.remove();
        }
    }
}
```

`for-each` — сахар над `Iterator`, поэтому прямой `remove` по коллекции в нём и падает. Для случая «удалить всё по
условию» есть `removeIf(predicate)` (Java 8+), внутри использующий тот же итератор.

**Итоги семинара.** Массив-заглушка ушёл: репозиторий на `Map` с `O(1)`-поиском, watchlist на `Set`, обработка
запросов котировок на `Queue` с кешем на `Map`. Выбор структуры обоснован сложностью основной операции, и эта
сложность подтверждена замером JMH; разобраны специализированные коллекции из внешних библиотек и безопасное изменение
коллекции во время обхода.

Следующий семинар — Stream API: ручные циклы обработки коллекций уступят место декларативным пайплайнам `stream()`.

### Этап 1. Data race на общем кеше; монитор, `synchronized`, wait/notify (~30 мин)

В семинаре 10 параллельный `quotesFor` был безопасен by construction (каждый поток — своя ячейка массива). Вводим общий
кеш котировок, чтобы не дёргать сеть повторно, — и получаем общее изменяемое состояние, в которое пишут несколько
потоков:

```java
private final Map<String, Quote> cache = new HashMap<>();   // ломается под конкурентной записью
// worker: get → (если null) source.fetch → put   — data race + check-then-act
```

Под нагрузкой `HashMap` теряет записи, бросает `ConcurrentModificationException` или зависает: одновременный `put`
портит внутреннюю структуру.

**Монитор — низкоуровневая база синхронизации.** У каждого объекта в Java есть монитор с двумя множествами — Entry Set
и Wait Set; владеть монитором может один поток в единицу времени. `synchronized` захватывает монитор на входе в блок и
освобождает на выходе (выход из монитора happens-before входа — та самая гарантия видимости из семинара 10). Грубая
починка кеша:

```java
synchronized (cache) {                       // взаимное исключение вокруг доступа к кешу
    cache.computeIfAbsent(ticker, t -> source.fetch(t).orElse(null));
}
```

`wait()`/`notify()` (вызываются только при владении монитором) кладут поток в Wait Set / будят его — низкоуровневый
механизм ожидания условия, поверх которого построены синхронизаторы. Работает, но `synchronized (cache)` сериализует
весь доступ — параллелизм теряется.

> **Для семинариста:** это кульминация 10–11: в семинаре 10 параллелизм был безопасен из-за отсутствия общего
> состояния; завели общее — сломалось. `synchronized` чинит корректность, но убивает производительность (все потоки в
> очередь за одним монитором). Отсюда мотивация к специализированным потокобезопасным коллекциям.

### Этап 2. Починка кеша: `ConcurrentHashMap` под капотом (~20 мин)

Правильный инструмент — `ConcurrentHashMap` с атомарным `computeIfAbsent`:

```java
private final Map<String, Quote> cache = new ConcurrentHashMap<>();
Quote quote = cache.computeIfAbsent(ticker, t -> source.fetch(t).orElse(null));
```

Внутри — не единый замок на всю карту, а тонкая блокировка: запись синхронизируется на уровне отдельной корзины (bin),
а вставка первого элемента в пустую корзину делается через CAS вообще без блокировки; чтение — почти всегда без
блокировок (`volatile`-видимость узлов). Отсюда масштабируемость под конкурентной нагрузкой, которой нет у
`Collections.synchronizedMap` (единый замок) и тем более у `synchronized (cache)`. Заодно чиним `figiCache` внутри
`HttpQuoteSource` — та же проблема конкурентной записи.

Тест конкурентной загрузки после починки стабильно зелёный.

### Этап 3. Синхронизаторы детально + самостоятельная работа (~30 мин)

Лекция по материалу [«Синхронизаторы»](./Синхронизаторы.md); внутреннее устройство (монитор, AQS, ABA, deadlock) — в
deep-dive [«Синхронизация и потокобезопасные коллекции»](../../materials/seminar11/Синхронизация%20и%20потокобезопасные%20коллекции.md).
Синхронизаторы — утилиты координации поверх мониторов и CAS, дающие более высокий уровень абстракции:

- `CountDownLatch` — одноразовый барьер «дождаться N событий»;
- `CyclicBarrier` — многоразовая точка сбора N потоков;
- `Semaphore` — ограничение числа одновременных участников (естественный рейт-лимитер к внешнему API);
- `Phaser` — гибкий многофазный барьер с динамическим числом участников;
- `StampedLock` — read/write-блокировка с оптимистичным чтением (быстрее `ReentrantReadWriteLock` на преобладающих
  чтениях);
- `Exchanger` — точка обмена объектами между двумя потоками.

**Самостоятельная работа.** Даны тесты со сценариями координации (дождаться N воркеров; ограничить одновременность
запросов к API; собрать потоки в фазах; оптимистичное чтение общего счётчика) с пропусками — студенты выбирают и
подключают корректный синхронизатор. Разбор — по каждому тесту.

> **Для семинариста:** ключ — сопоставление задачи и инструмента: «дождаться N однократно» → `CountDownLatch`,
> «многоразовый сбор» → `CyclicBarrier`/`Phaser`, «ограничить одновременность» → `Semaphore`, «много чтений, редко
> запись» → `StampedLock`. Подчеркните правило: блокирующие операции — только с таймаутом (`tryLock`/`tryAcquire`),
> иначе рискуем зависанием.

### Этап 4. Потокобезопасные коллекции: wait-free / lock-free / blocking (~30 мин)

Лекция по материалу [«Потокобезопасные коллекции»](./Потокобезопасные%20коллекции.md). Потокобезопасность достигается
по-разному, и это влияет на гарантии прогресса:

- **Blocking** — доступ через блокировку (`Collections.synchronizedMap`, `BlockingQueue.put`/`take`): поток может ждать.
  Просто, но при контеншене потоки простаивают; риск взаимных блокировок.
- **Lock-free** — прогресс системы гарантирован без блокировок, на CAS-циклах (`ConcurrentLinkedQueue`,
  вставка в `ConcurrentHashMap`): отдельный поток может повторять попытку, но система в целом всегда продвигается.
- **Wait-free** — каждый поток завершает операцию за конечное число шагов независимо от других (сильнейшая гарантия;
  например, чтение из `CopyOnWriteArrayList` — читатели работают по неизменяемому снимку, не ожидая никого).

Разбираем на примерах проекта: кеш — `ConcurrentHashMap` (lock-free запись в незанятую корзину); watchlist, если бы
читался из многих потоков при редких изменениях, — кандидат на `CopyOnWriteArrayList`/`CopyOnWriteArraySet`
(wait-free чтение); связь producer/consumer (семинар про Executor) — `BlockingQueue` (blocking по назначению).

> **Для семинариста:** различение прогресс-гарантий — не академизм: оно объясняет, почему `CopyOnWriteArrayList` идеален
> для «много читаем, редко пишем» (чтение никогда не блокируется), но катастрофичен при частой записи (каждая запись
> копирует массив), и почему lock-free структуры не «всегда быстрее», а «всегда продвигаются».

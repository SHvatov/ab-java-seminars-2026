# Потокобезопасные коллекции

---

## Три способа обеспечить потокобезопасность

Потокобезопасность достигается по-разному, и способ определяет гарантию прогресса — насколько потоки мешают друг другу.

- **Blocking** — доступ через блокировку. Поток, не получивший замок, засыпает и ждёт. Просто, но при контеншене потоки
  простаивают, а неаккуратные блокировки ведут к взаимоблокировкам.
- **Lock-free** — без блокировок, на CAS. Гарантия прогресса на уровне **системы**: всегда хоть один поток продвигается,
  хотя отдельный может повторять CAS-цикл.
- **Wait-free** — сильнейшая гарантия: **каждый** поток завершает операцию за конечное число шагов независимо от других;
  никто никого не ждёт.

Иерархия гарантий: wait-free ⊂ lock-free ⊂ (обычно быстрее blocking под контеншеном, но сложнее).

---

## Blocking-коллекции

`Collections.synchronizedMap`/`synchronizedList` оборачивают каждую операцию единым замком — корректно, но параллелизм
нулевой (все операции сериализуются). `BlockingQueue` (`LinkedBlockingQueue`, `ArrayBlockingQueue`) — блокирует
намеренно и по назначению:

```java
void example(BlockingQueue<String> queue) throws InterruptedException {
    queue.put("task");     // блокирует, если очередь полна
    String task = queue.take();   // блокирует, если очередь пуста
}
```

`put`/`take` — блокирующие; `offer`/`poll` — неблокирующие (с опциональным таймаутом). `BlockingQueue` — основа
producer/consumer: потребитель спит на пустой очереди, не тратя CPU.

## Lock-free-коллекции

`ConcurrentLinkedQueue` — неблокирующая очередь на CAS: `offer`/`poll` пытаются атомарно переставить указатели, при
конфликте повторяют. `ConcurrentHashMap` — гибрид: вставка первого узла в пустую корзину идёт через CAS без блокировки,
запись в занятую корзину — под тонкой блокировкой только этой корзины, чтение — почти всегда без блокировок
(`volatile`-видимость узлов).

```java
void example(Map<String, Quote> cache, String ticker, QuoteSource source) {
    // вставка отсутствующего значения — атомарно, без блокировки всей карты
    cache.computeIfAbsent(ticker, t -> source.fetch(t).orElse(null));
}
```

Отсюда масштабируемость `ConcurrentHashMap`: потоки, работающие с разными ключами, почти не мешают друг другу — в отличие
от `synchronizedMap` с единым замком.

## Wait-free-чтение: CopyOnWrite

`CopyOnWriteArrayList`/`CopyOnWriteArraySet` — для сценария «часто читаем, редко пишем». Чтение работает по неизменяемому
снимку массива и **никогда** не блокируется и не ждёт (wait-free); запись создаёт новую копию массива под замком.

```java
void example(List<String> subscribers) {
    for (String s : subscribers) {   // итерация по снимку; параллельная запись её не затрагивает
        notify(s);
    }
}
```

Идеален, когда чтений на порядки больше записей (списки подписчиков, конфигурация). Катастрофичен при частой записи —
каждая копирует весь массив (`O(n)` на запись).

## Выбор под профиль доступа

| Профиль | Коллекция | Способ |
|---|---|---|
| Конкурентные записи по ключу | `ConcurrentHashMap` | lock-free вставка + тонкая блокировка |
| Много чтений, редко запись | `CopyOnWriteArrayList` | wait-free чтение |
| Передача задач между потоками | `BlockingQueue` | blocking по назначению |
| Неблокирующая очередь | `ConcurrentLinkedQueue` | lock-free CAS |

Ключевой вывод: «потокобезопасная» — не значит «быстрая». Способ обеспечения безопасности (blocking / lock-free /
wait-free) и профиль доступа (читаем/пишем, по ключу/по порядку) вместе определяют, какая коллекция подойдёт.

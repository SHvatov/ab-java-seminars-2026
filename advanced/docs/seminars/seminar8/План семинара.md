### Этап 1. JUnit 5 и Mockito: тесты домена и изоляция зависимостей (~25 мин)

Лекция по материалу [«JUnit 5 и Mockito»](./JUnit%205%20и%20Mockito.md).

Тест — метод с `@Test`; проверки — `Assertions` (`assertEquals`, `assertTrue`, `assertThrows`); структура —
Arrange-Act-Assert. Покрываем детерминированную доменную логику:

```java
@Test
void дивидендыЭтоЦенаУмноженнаяНаДоходность() {
    Stock stock = new Stock("SBER", "Сбербанк", Currency.RUB, "Banks", new BigDecimal("10"));
    assertEquals(new BigDecimal("25.00"), stock.getDividends(new BigDecimal("250.00")));
}
```

**Изоляция зависимости (Mockito).** `QuoteService` зависит от сетевого `QuoteSource`. Чтобы тест не требовал токена и
сети, источник подменяется заглушкой:

```java
QuoteSource source = mock(QuoteSource.class);
when(source.fetch("SBER")).thenReturn(Optional.of(sberQuote));
QuoteService service = new QuoteService(source);
assertEquals(Optional.of(sberQuote), service.quoteFor("SBER"));
verify(source).fetch("SBER");
```

Интерфейс `QuoteSource` (семинар 7) — та самая граница, которую подменяет mock.

> **Самостоятельно (студенты):** тесты на `Watchlist` (дедуп с нормализацией регистра) и `InstrumentRepository`
> (`findByTicker` регистронезависим, повторный `add` → `DuplicateTickerException` через `assertThrows`).

### Этап 2. TDD: разработка через тесты (red-green-refactor) (~25 мин)

Test-Driven Development переворачивает порядок: сначала тест, потом код. Цикл — **red-green-refactor**: написать
падающий тест на желаемое поведение (red), написать минимальный код, чтобы тест прошёл (green), улучшить код при зелёных
тестах (refactor). Разбираем на реальной новой фиче — удаление из watchlist (сейчас `Watchlist` умеет только добавлять).

**Red — сначала падающий тест.** Метода `remove` ещё нет, тест не компилируется/падает:

```java
@Test
void removeУбираетТикерИзWatchlist() {
    Watchlist watchlist = new Watchlist();
    watchlist.add("SBER");
    assertTrue(watchlist.remove("sber"));       // регистронезависимо
    assertFalse(watchlist.contains("SBER"));
}
```

**Green — минимальная реализация.** Добавляем в `Watchlist` метод, доводящий тест до зелёного:

```java
public boolean remove(String ticker) {
    return tickers.remove(ticker.toUpperCase());
}
```

**Refactor.** Тест зелёный — можно спокойно чистить код; тесты страхуют. Затем тем же циклом добавляется CLI-флаг
`watch --remove TICKER` (сначала тест на команду, потом реализация в `WatchCommand`).

> **Для семинариста:** ценность TDD — не «тесты сначала» ради ритуала, а то, что тест формулирует требование до кода и
> сразу становится проверкой. Фича `remove` выбрана намеренно маленькой: весь цикл проходится за один этап и остаётся
> в проекте настоящим кодом, а не выкидывается.

### Этап 3. BDD: сценарии Given-When-Then (~25 мин)

Лекция по материалу [«TDD и BDD»](./TDD%20и%20BDD.md).

Behavior-Driven Development смещает фокус с «тестируем метод» на «описываем поведение» на языке, близком к требованию:
**Given** (предусловие) — **When** (действие) — **Then** (ожидаемый результат). В JUnit 5 это выражается вложенными
классами `@Nested` и человекочитаемыми `@DisplayName`, без отдельного фреймворка:

```java
@DisplayName("QuoteService")
class QuoteServiceBddTest {

    @Nested
    @DisplayName("когда котировка уже в кеше")
    class WhenCached {
        @Test
        @DisplayName("тогда повторный запрос не идёт к источнику")
        void неХодитКИсточникуПовторно() {
            // Given
            QuoteSource source = mock(QuoteSource.class);
            when(source.fetch("SBER")).thenReturn(Optional.of(sberQuote));
            QuoteService service = new QuoteService(source);
            // When
            service.quoteFor("SBER");
            service.quoteFor("SBER");
            // Then
            verify(source, times(1)).fetch("SBER");
        }
    }
}
```

Отчёт JUnit читается как спецификация поведения. Для полноценного BDD с человекочитаемыми сценариями существуют
отдельные инструменты (Cucumber, Gherkin), но идеологию Given-When-Then удобно применять и в чистом JUnit.

> **Для семинариста:** подчеркните, что BDD — не другой инструмент, а другой способ формулировать и структурировать
> тесты: имя теста описывает поведение, тело следует Given-When-Then. `verify(source, times(1))` заодно показывает
> проверку количества вызовов.

### Этап 4. Мутационное тестирование: PIT (~25 мин)

Лекция по материалу [«Мутационное тестирование»](./Мутационное%20тестирование.md); подробный разбор — в deep-dive
[«TDD, BDD и мутационное тестирование»](../../materials/seminar8/TDD,%20BDD%20и%20мутационное%20тестирование.md).

Покрытие строк лжёт: код может быть «покрыт», но реально не проверен — если убрать ассерт, тест всё равно пройдёт.
Мутационное тестирование измеряет качество тестов напрямую: инструмент вносит мелкие правки в код (мутации — заменить
`+` на `-`, `>` на `>=`, вернуть `null`, убрать вызов) и проверяет, **упадёт ли** хоть один тест. Упал — мутант убит
(тесты поймали изменение); прошёл — мутант выжил (в тестах дыра).

**PIT** (`pitest`) — инструмент мутационного тестирования для Java. Подключается плагином Maven и запускается
`mvn org.pitest:pitest-maven:mutationCoverage`, формируя HTML-отчёт с процентом убитых мутантов и списком выживших.

```xml
<plugin>
    <groupId>org.pitest</groupId>
    <artifactId>pitest-maven</artifactId>
    <version>1.20.4</version>
    <configuration>
        <targetClasses><param>academy.backend.market_pulse.*</param></targetClasses>
        <targetTests><param>academy.backend.market_pulse.*</param></targetTests>
    </configuration>
</plugin>
```

На семинаре запускаем PIT на написанных тестах, находим выжившего мутанта (например, в `Stock.getDividends` замена
округления или множителя) и усиливаем тест так, чтобы мутант был убит.

> **Для семинариста:** ключевая мысль — «100% покрытие» ничего не гарантирует, а мутационное тестирование показывает,
> что тесты действительно проверяют, а не просто исполняют код. Выживший мутант — это конкретное указание, какой
> ассерт слабый. PIT в песочнице курса не запускался (плагин докачивается при `mvn`) — прогон за студентом.

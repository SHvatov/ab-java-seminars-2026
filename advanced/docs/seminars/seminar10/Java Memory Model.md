# Java Memory Model

---

## Проблема: (0, 0), которого «не должно быть»

Классический тест: два потока, один пишет `x = 1` и читает `y`, другой пишет `y = 1` и читает `x`. Интуиция допускает
пары `(1,1)`, `(1,0)`, `(0,1)`. Но среди тысяч прогонов встречается и `(0, 0)` — обе записи будто не произошли.

Причина — оптимизации. Переупорядочивают инструкции и кешируют значения не только программисты, но и:

- **компилятор байт-кода и JIT** — меняют местами независимые инструкции;
- **процессор** — исполняет вне порядка, откладывает пропагацию записей между кешами ядер.

Записи одного потока могут быть **не видны** другому (visibility) или видны **не в том порядке** (reordering), если между
ними нет установленного отношения порядка.

---

## Что такое JMM

Java Memory Model — не «layout памяти», а математический **контракт**: строго описывает, какие исполнения многопоточной
программы допустимы с учётом всех оптимизаций. Это абстракция между кодом и реализацией: мы полагаемся на гарантии JMM, а
не на поведение конкретной JVM/ОС/процессора.

---

## Happens-before

Ключевое отношение JMM — **happens-before**. Если действие A happens-before действия B, то все эффекты A (в том числе
записи в память) гарантированно видны в B, как бы инструкции ни переупорядочивали. Без happens-before между потоками
порядок и видимость не гарантированы.

Отношения happens-before устанавливают:

- **Программный порядок** — внутри одного потока.
- **`volatile`** — запись volatile-переменной happens-before её последующего чтения.
- **Монитор** — выход из `synchronized`-блока happens-before входа в него (следующий семинар).
- **`Thread.start`/`join`** — старт happens-before кода потока; код потока happens-before возврата из `join`.

## volatile

`volatile` даёт две гарантии: видимость (запись сразу видна другим потокам, без застревания в кеше) и запрет
переупорядочивания вокруг обращения. В тесте выше пометка переменных `volatile` убирает пары `(0, 0)`.

Ограничение: `volatile` обеспечивает атомарность **одиночного** чтения/записи, но не составной операции. `volatile int`
не спасает `count++` (прочитать-прибавить-записать) — между чтением и записью вклинивается другой поток. Для составных
операций нужен CAS (`Atomic*`) или блокировка.

```java
class ResultProvider {
    private volatile boolean ready;   // видимость флага между потоками гарантирована
    private int value;

    void publish(int v) { value = v; ready = true; }        // value записан до ready (happens-before)
    int read() { return ready ? value : -1; }               // увидели ready == true ⇒ увидим и value
}
```

## final и безопасная публикация

Корректно инициализированные `final`-поля видны всем потокам после публикации объекта (safe publication) без
дополнительной синхронизации. Практический вывод: **неизменяемые** доменные объекты (`Instrument`, `Quote` — только
`final`-поля, никаких сеттеров) можно свободно шарить между потоками. Неизменяемость — самый дешёвый способ обойтись без
синхронизации вовсе.

---

## Три уровня гарантий

| Инструмент | Что даёт |
|---|---|
| `volatile` | видимость и запрет переупорядочивания (для одиночных операций) |
| `synchronized` / `Lock` | взаимное исключение (атомарность через блокировку) + happens-before |
| `Atomic*` / CAS | атомарность составной операции без блокировки |

Выбор — по задаче: флаг видимости → `volatile`; инкремент счётчика → `Atomic*`; защита составного инварианта → блокировка
или потокобезопасная коллекция.

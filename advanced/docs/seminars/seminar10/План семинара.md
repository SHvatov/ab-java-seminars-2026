### Этап 1. Потоки Java и уровень ОС (~20 мин)

Презентация по материалу [«Потоки в Java»](./Потоки%20в%20Java.md).

Классический (platform) поток Java — тонкая обёртка над потоком ОС (1:1). За то, какой поток окажется на ядре CPU,
отвечает **планировщик ОС** (его алгоритм и приоритеты зависят от системы), а не JVM. Практические следствия:

- **Стоимость.** Поток ОС — это стек (обычно ~1 МБ), структуры ядра, переключение контекста (сохранение/восстановление
  регистров, инвалидация кешей). Отсюда — потоков не может быть много (тысячи, не миллионы), и их переиспользуют
  (пулы, семинар про Executor Framework) вместо создания на задачу.
- **Состояния** (`NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING`, `TERMINATED`) — проекция состояний потока ОС;
  `BLOCKED`/`WAITING` означают простой с занятыми ресурсами.

Мотивация та же, что у базового трека: `quotesFor` ходит за котировками последовательно, десятки блокирующих HTTP-вызовов
подряд, хотя они независимы.

> **Акцент:** дороговизна потока ОС — корень двух будущих тем: пулов (переиспользование) и виртуальных потоков
> (Project Loom — много «потоков» на немногих потоках ОС).

### Этап 2. Параллельная загрузка котировок и прерывание (~25 мин)

Распараллеливаем `quotesFor`: поток на тикер, результат — в свою ячейку массива по индексу, сбор после `join`. Общего
изменяемого состояния нет, поэтому синхронизация не нужна (что будет при общем состоянии — семинар 11).

```java
Quote[] results = new Quote[list.size()];
Thread[] threads = new Thread[list.size()];
for (int i = 0; i < list.size(); i++) {
    int index = i;
    threads[i] = Thread.ofPlatform().start(() ->
            source.fetch(list.get(index)).ifPresent(quote -> results[index] = quote));
}
```

Прерывание — кооперативное: `interrupt()` выставляет флаг, блокирующие методы бросают `InterruptedException`, после
броска флаг сбрасывается и его восстанавливают (`Thread.currentThread().interrupt()`). Проглоченное прерывание — код,
который нельзя корректно остановить.

> **Самостоятельно (студенты):** реализовать распараллеливание и корректный `join` с восстановлением флага прерывания;
> замерить время до/после.

### Этап 3. Java Memory Model: happens-before и переупорядочивание (~35 мин)

Лекция по материалу [«Java Memory Model»](./Java%20Memory%20Model.md).

**Проблема.** Прогресс-бар из соседнего трека увеличивает общий счётчик из нескольких потоков. Если сделать его обычным
`int`, значение будет теряться, а другой поток может вообще не увидеть изменений. Классическая демонстрация: два потока
пишут `x=1`/`y=1` и читают чужую переменную; среди результатов встречается `(0, 0)` — обе записи «не увидены».

**Почему.** Оптимизируют не только программисты: компилятор байт-кода, JIT и процессор **переупорядочивают** независимые
инструкции, а записи одного потока могут быть **не видны** другому из-за кешей и отложенной пропагации. Пары
«запись→чтение» без явных гарантий не упорядочены между потоками.

**JMM** — это не «layout памяти», а математический **контракт**: он строго описывает, какие исполнения программы валидны
с учётом всех оптимизаций. Ключевое отношение — **happens-before**: если действие A happens-before B, то результаты A
гарантированно видны в B, как бы инструкции ни переупорядочивали.

**Инструменты установить happens-before:**
- `volatile` — запись volatile-переменной happens-before её последующего чтения; снимает переупорядочивание вокруг неё и
  форсирует видимость. Работает для **атомарных** операций (одиночная запись/чтение), но `volatile int++` не атомарен.
- `synchronized` — выход из монитора happens-before входа в него (семинар 11).
- `final` — корректно инициализированные `final`-поля видны всем потокам после публикации объекта (safe publication) —
  поэтому неизменяемые доменные объекты (`Instrument`, `Quote`) безопасно шарить между потоками.

> **Для семинариста:** подчеркните, что JMM — контракт, а не реализация. `volatile` не «делает медленно и правильно», а
> даёт конкретную гарантию happens-before; там, где нужна атомарность составной операции (инкремент), одного `volatile`
> мало — нужен CAS (следующий этап). Неизменяемость (`final` + отсутствие сеттеров) — самый дешёвый способ обойтись без
> синхронизации вовсе.

### Этап 4. Атомарность и CAS (~30 мин)

Почему прогресс-счётчик — `AtomicInteger`, а не `volatile int`? Инкремент — составная операция (прочитать, прибавить,
записать); между чтением и записью другой поток может вклиниться, и обновление потеряется. `volatile` обеспечивает
видимость, но не атомарность составной операции.

**CAS (Compare-And-Swap)** — атомарная инструкция процессора «сравни текущее значение с ожидаемым и, если совпало,
запиши новое». На ней построены `Atomic*`-классы:

```java
AtomicInteger completed = new AtomicInteger();
completed.incrementAndGet();          // внутри — CAS-цикл: read → compute → compareAndSet, повтор при неудаче

AtomicReference<Quote> latest = new AtomicReference<>();
latest.compareAndSet(expected, updated);   // запись только если значение не изменилось
```

`incrementAndGet` внутри — цикл «прочитать текущее, вычислить +1, `compareAndSet`; если другой поток успел изменить —
повторить». Это **неблокирующая** (lock-free) синхронизация: без монитора, без простоя потока — основа
высокопроизводительных структур, к которым вернёмся в семинаре про потокобезопасные коллекции.

> **Акцент:** три уровня гарантий стоит различать чётко: `volatile` — видимость; `synchronized`/`Lock` — взаимное
> исключение (атомарность через блокировку); `Atomic*`/CAS — атомарность без блокировки. Выбор — по задаче: для счётчика
> достаточно CAS.

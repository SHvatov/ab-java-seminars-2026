### Этап 2. Теория: ООП (~10 мин)

Организационный/теоретический этап, к конкретной функции проекта не привязан. Презентация. Цель — не пересказать
учебник, а показать **зачем** и **как принципы работают вместе**; аудитория продвинутая — темп выше, определения
короче, акцент на взаимосвязи, а не на повторении азов. Подробное изложение — в сопроводительном материале
[ООП](../../materials/seminar1/ООП.md).

**Ключевые тезисы (кратко, без разжёвывания базовых определений):**

- **Инкапсуляция** — не геттеры/сеттеры, а сокрытие реализации и защита инвариантов. Пример из C: `open()` в
  `fcntl.h` — один контракт, разные реализации под каждую ОС.
- **Наследование** — IS-A и переиспользование кода; цена — жёсткая связанность, каскадные изменения в глубоких
  иерархиях. Короткий намёк на Interface Segregation Principle — подробнее на семинаре 2.
- **Полиморфизм** — подтипов (runtime, через override) и перегрузка (compile-time). Параметрический (generics) —
  позже.
- **Принцип подстановки Лисков (LSP), коротко.** Объект подкласса должен без проблем подменять объект базового
  класса. Подробно LSP и остальные принципы SOLID разбираются на следующих семинарах — сегодня термин прозвучит
  предметно на практике (шаг 4.5).
- **Взаимосвязь:** полиморфизм подтипов невозможен без наследования; наследование без полиморфизма теряет смысл;
  инкапсуляция — фундамент, без которого всё течёт наружу.

### Этап 3. Брейншторминг: моделируем домен (~10 мин) — самостоятельная работа

**Задача этапа:** прежде чем писать код, нужно понять, какие сущности вообще потребуются будущим функциям Market
Pulse — поиску инструментов, котировкам, сравнению, портфелю/избранному — и как они связаны между собой.

Студенты **самостоятельно** проектируют домен на доске (WhiteBoard или доска в Толке): какие сущности есть, какие
между ними связи, какими полями и свойствами они обладают. Семинарист не подсказывает решение, а только направляет
обсуждение вопросами и фиксирует результат.

**Задание:**

> Представьте, что вы проектируете MVP Market Pulse — минимально рабочее приложение на придуманных тестовых данных,
> без реального обращения к T-Invest API.
>
> **Подумайте по трём осям:**
> 1. **Сущности.** Какие объекты из мира Т-Инвестиций вам понадобятся?
> 2. **Связи.** Какие из них связаны и как именно (наследование «является», владение «часть-целое», ссылка)?
> 3. **Атрибуты и поведение.** Какие данные и какие операции у каждой сущности?

**Сущности и их атрибуты:**

- **Instrument** — финансовый инструмент. Абстрактная сущность: «просто инструмента» не бывает, бывают его виды.
    - `ticker` — биржевой тикер, уникальный идентификатор инструмента.
    - `name` — человекочитаемое название.
    - `currency` — валюта, в которой торгуется инструмент.
    - **Stock** (акция) — дополнительно: `sector`, дивидендная доходность.
    - **Bond** (облигация) — дополнительно: купон и год погашения.
    - **Etf** (биржевой фонд) — дополнительно: отслеживаемый индекс.
- **Quote** (котировка — инструмент с текущей рыночной ценой): ссылка на `Instrument`, `price`, `changePercent`.
- **Portfolio** (портфель пользователя): `name`, список позиций.
    - **Position** (позиция) — существует только внутри портфеля: ссылка на `Instrument`, `quantity`.

**Связи между сущностями:**

```other
Instrument (абстрактный)
  ├── Stock          «является»  (наследование)
  ├── Bond           «является»  (наследование)
  └── Etf            «является»  (наследование)

Quote ──► Instrument             ссылка / агрегация (инструмент живёт сам по себе)

Portfolio ◆── Position           «часть-целое» / композиция (позиция живёт внутри портфеля)
Position  ──► Instrument         ссылка
```

> **Ремарка семинаристу:** цена (`price`) намеренно относится к `Quote`, а не к `Instrument` — почему, разберём на
> шаге 4.5: один и тот же инструмент имеет разные цены в разные моменты и на разных биржах.

#### Шаг 4.3. `BigDecimal` вместо `double` для денег (~5 мин)

**Задача:** «текущие котировки» и «сравнение инструментов» оперируют ценами и доходностью — нужно решить, каким
типом их представлять.

```java
void example() {
    System.out.println(0.1 + 0.2);            // 0.30000000000000004 — double не подходит для денег

    new BigDecimal(278.50);                    // наследует неточность double!
    new BigDecimal("278.50");                  // точно
}
```

> **Акцент:** везде, где в модели есть цена или доходность, используем `BigDecimal` — см. `NOTICE` в
> [`Stock.java#L8`](../../../src/main/java/academy/backend/market_pulse/model/Stock.java).

**`scale` и хрупкий `equals`.** `BigDecimal` хранит значение как пару `unscaledValue` и `scale` (число знаков после
запятой) — `278.50` и `278.5` численно равны, но имеют разный `scale`, и стандартный `equals()` сравнивает **обе**
составляющие:

```java
void example() {
    new BigDecimal("278.50").equals(new BigDecimal("278.5"));    // false — разный scale
    new BigDecimal("278.50").compareTo(new BigDecimal("278.5")); // 0    — значения равны
}
```

> **Обсуждение:** для сравнения денежных сумм *по значению* нужен не `equals`, а `compareTo` — интерфейс
> `Comparable`. Практическое следствие: `BigDecimal` нельзя безопасно класть в `HashSet`/использовать как ключ
> `HashMap`, полагаясь на «эквивалентные» значения с разным `scale` — они окажутся в разных корзинах.

**Задача:** функциям «текущие котировки» и «котировки в реальном времени» нужна сущность «инструмент с ценой на

### Этап 5. Теория: устройство памяти в JVM (~15 мин)

Организационный/теоретический этап — фундамент для практики этапа 6, к конкретной функции проекта не привязан. Идёт
по презентации. Подробное изложение — в сопроводительном материале
[Java Process Memory Model](../../materials/seminar1/Java%20Process%20Memory%20Model%20.md).

**Области памяти.** Heap (объекты и массивы, под управлением GC) и Non-Heap (Metaspace — метаданные классов и
байт-код; Code Cache — JIT-скомпилированный код) — разделяют общую память процесса JVM. Stack — отдельно на каждый
поток: кадры вызовов, локальные переменные и ссылки; сами объекты — всегда в Heap.

**Сборка мусора (обзорно).** В основе большинства сборщиков — гипотеза о поколениях: подавляющее большинство
объектов живут очень недолго, поэтому Heap разделён на молодое и старое поколения, и малая сборка (только молодое
поколение) выполняется намного чаще полной. Классический алгоритм — mark → sweep → compact; работа сборщика не
бесплатна и оплачивается паузами stop-the-world. Кратко назвать сборщики HotSpot (Serial, Parallel, G1 — по
умолчанию, ZGC/Shenandoah) без детального разбора — он будет на последующих семинарах.

> **Форвард-референс:** Java Memory Model в смысле многопоточности (`volatile`, happens-before, видимость изменений
> между потоками) — отдельная и более глубокая тема, вынесенная на семинары по многопоточности. Сегодняшняя тема —
> устройство памяти процесса JVM, а не согласованность памяти между потоками; не путать по названию.

**Устройство объекта в памяти.** Заголовок (Mark Word 8 байт + Class Pointer 4-8 байт) + поля экземпляра +
выравнивание до кратности 8 байт. Минимальный объект без полей — 16 байт.

**Вопрос к студентам:** что больше весит в памяти — `int[10][1000]` или `int[1000][10]`? Оба содержат по 10 000
`int`, но многомерный массив в Java — это массив ссылок на массивы, и число объектов-массивов у них разное (11
против 1001) — второй тяжелее из-за накладных расходов на дополнительные заголовки.

> Проверим это вместе — сначала в VisualVM, потом с помощью JOL.

### Этап 6. Практика: VisualVM и JOL (~30 мин)

#### Шаг 6.1. VisualVM — мониторинг в реальном времени (~10 мин)

Итоговый код: [`MemoryDemo.java`](../../../src/main/java/academy/backend/market_pulse/demo/MemoryDemo.java) —

#### Шаг 6.2. JOL — точные размеры (~20 мин) — самостоятельная часть

Библиотека JOL уже подключена в `pom.xml` (координаты `groupId:artifactId:version`, `org.openjdk.jol:jol-core:0.17`

> **Для семинариста:** JOL читает внутреннее устройство объектов через рефлексию поверх `java.base`. Если у

> команду под рукой на случай вопроса из зала.

**Самостоятельно (часть 1):** в `JolDemo.java` две последние строки с `GraphLayout` закомментированы.

### Этап 1. Безопасный рефакторинг с тестами (~25 мин)

Устраняем дублирование: конвейер «тикеры → котировки» (`map(quoteFor).flatMap(Optional::stream)`) повторяется в
`stats`/`movers`/`compare`. Выносим его в `QuoteService`:

```java
public List<Quote> quotesFor(Collection<String> tickers) {
    return tickers.stream()
            .map(this::quoteFor)
            .flatMap(Optional::stream)
            .toList();
}
```

Команды сводятся к вызову `quotesFor(...)`. Тесты семинара 8 остаются зелёными — поведение не изменилось; на `quotesFor`
добавляется свой тест.

**Характеризационный тест как подготовка.** Перед следующим этапом (очистка сериализации) фиксируем текущее поведение
хранилища тестом round-trip:

```java
@Test
void полиморфныйКаталогПереживаетRoundTrip() throws IOException {
    Path dir = Files.createTempDirectory("mp");
    InstrumentStorage storage = new InstrumentStorage(dir);
    storage.save(new Stock("SBER", "Сбербанк", Currency.RUB, "Banks", new BigDecimal("6.5")));
    storage.save(new Bond("OFZ", "ОФЗ", Currency.RUB, new BigDecimal("8"), 2030));
    storage.save(new Etf("TMOS", "Т iMOEX", Currency.RUB, "IMOEX"));

    List<Instrument> loaded = storage.loadAll();
    assertEquals(3, loaded.size());
    // каждый тип восстановлен своим классом, и поле подкласса тоже пережило
    Instrument sber = loaded.stream().filter(i -> i.getTicker().equals("SBER")).findFirst().orElseThrow();
    assertInstanceOf(Stock.class, sber);
    assertEquals("Banks", ((Stock) sber).getSector());
}
```

> **Для семинариста:** характеризационный тест фиксирует поведение legacy-кода **до** его изменения, чтобы рефакторинг
> был проверяем. На этапе 3 мы будем менять устройство сериализации — этот тест не даст сломать её незаметно.

### Этап 2. Dependency Inversion на практике (~25 мин)

Лекция по материалу [«Clean Architecture»](./Clean%20Architecture.md), часть про принцип инверсии зависимостей.

**Dependency Inversion Principle (DIP):** модули верхнего уровня не должны зависеть от модулей нижнего уровня; оба
зависят от абстракций. В проекте это уже реализовано — на двух портах:

- **`QuoteSource`** (интерфейс). `QuoteService` зависит от `QuoteSource`, а не от `HttpQuoteSource`. Сетевой клиент —
  адаптер, подставляемый снаружи (в `Main`). Именно поэтому на семинаре 8 его удалось подменить mock'ом.
- **`InstrumentRepository`** (интерфейс, продвинутый трек). CLI зависит от интерфейса; `InMemoryInstrumentRepository` —
  одна из возможных реализаций.

```
QuoteService ──зависит от──▶ QuoteSource (интерфейс)
                                  ▲
                                  │ реализует
                            HttpQuoteSource
```

Стрелка зависимости направлена к абстракции, а не к конкретной реализации — деталь (сеть, диск) подключается к ядру, а
не наоборот. Это и есть инверсия: без интерфейса `QuoteService` зависел бы от `HttpClient` и токена напрямую и был бы
непроверяем.

> **Для семинариста:** подчеркните, что DIP здесь не теория — это то, что уже сделало код тестируемым (семинар 8) и
> заменяемым (стаб → реальный API на семинаре 7). Интерфейс окупился дважды.

### Этап 3. Clean Architecture: правило зависимостей и очистка домена (~30 мин)

Лекция по материалу [«Clean Architecture»](./Clean%20Architecture.md); подробно — в deep-dive
[«Чистая архитектура и границы сервисов»](../../materials/seminar9/Чистая%20архитектура%20и%20границы%20сервисов.md).

**Правило зависимостей.** В Clean Architecture зависимости направлены только внутрь: внешние слои (UI, БД, фреймворки)
знают о внутренних (прикладная логика, домен), но не наоборот. Домен — самый внутренний слой — не должен знать ни о
сети, ни о диске, ни о фреймворках.

**Находим нарушение.** Наш домен его нарушает: `Instrument` и подклассы несут аннотации Jackson
(`@JsonTypeInfo`, `@JsonSubTypes`, `@JsonCreator`). Доменная сущность зависит от библиотеки сериализации — деталь
внешнего слоя протекла в ядро.

**Чиним (порты и адаптеры).** Переносим знание о сериализации в слой `storage` через Jackson **mixin** — абстрактный
класс с теми же аннотациями, привязываемый к домену снаружи, без правки самого домена:

```java
// storage/InstrumentJsonMixin — аннотации живут здесь, а не в model
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, include = JsonTypeInfo.As.PROPERTY, property = "type")
@JsonSubTypes({ @JsonSubTypes.Type(value = Stock.class, name = "STOCK"), /* Bond, Etf — аналогично */ })
abstract class InstrumentJsonMixin { }
```

```java
// InstrumentStorage — регистрируем mixin в ObjectMapper
void example(ObjectMapper mapper) {
    mapper.addMixIn(Instrument.class, InstrumentJsonMixin.class);
    mapper.addMixIn(Stock.class, StockJsonMixin.class);   // @JsonCreator для конструктора
}
```

Аннотации уходят из `model` — домен снова свободен от фреймворка. Характеризационный тест round-trip из этапа 1 остаётся
зелёным: поведение сериализации не изменилось, изменилось только то, **где** живёт знание о ней.

> **Самостоятельно (студенты):** семинарист показывает mixin для `Stock` и его регистрацию в `ObjectMapper`; mixin'ы
> для `Bond` и `Etf` (по образцу, со своими полями в конструкторе) пишут студенты — характеризационный тест round-trip
> сразу подтверждает, что каждый тип по-прежнему сериализуется.

> **Для семинариста:** это семинар в миниатюре — нашли нарушение правила зависимостей, устранили его рефакторингом,
> проверили тестом, что ничего не сломали. Заодно честно: в базовом треке аннотации на домене оставлены осознанно — за
> чистоту всегда платят сложностью, и для маленького проекта mixin может быть избыточен.

### Этап 4. Монолит против микросервисов (~30 мин)

Лекция по материалу [«Монолит и микросервисы»](./Монолит%20и%20микросервисы.md).

Market Pulse — **монолит**: одно приложение, один процесс, внутренние вызовы между слоями. Микросервисная архитектура
разбила бы его на отдельно развёртываемые сервисы (например, «каталог инструментов», «котировки», «портфель»),
общающиеся по сети.

Разбираем на нашем проекте:

- **Границы.** Естественные швы уже видны — `QuoteSource` (котировки), `InstrumentRepository` (каталог),
  `WatchlistStorage` (watchlist). Микросервис прошёл бы ровно по такому шву, заменив внутренний вызов сетевым.
- **Цена.** Микросервисы дают независимое развёртывание и масштабирование, но приносят сетевые вызовы, распределённые
  сбои, согласованность данных и сложность эксплуатации. Для CLI-утилиты одного пользователя это чистый проигрыш.
- **Когда дробить.** Не «модно», а когда части приложения имеют разный цикл изменений, нагрузку или команду. Правило —
  начинать с монолита с чистыми границами (как у нас), а выделять сервис только под доказанную потребность.

> **Для семинариста:** ключевая мысль — микросервисы решают организационные и масштабные проблемы, а не проблемы кода;
> плохие границы внутри монолита превратятся в плохие границы между сервисами, только уже по сети. Чистый монолит —
> предпосылка к разделению, а не его противоположность.

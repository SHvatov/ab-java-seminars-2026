# Clean Architecture

---

## Правило зависимостей

Clean Architecture организует код концентрическими слоями и вводит одно жёсткое правило — **правило зависимостей**:
исходные зависимости направлены только внутрь. Внешние слои (UI, БД, фреймворки, сеть) знают о внутренних (прикладная
логика, домен), но никогда наоборот.

```
        ┌──────────────────────────────┐
        │  Frameworks & Drivers         │  cli, storage, HttpQuoteSource
        │   ┌──────────────────────┐    │
        │   │  Interface Adapters  │    │  адаптеры к внешнему миру
        │   │   ┌──────────────┐   │    │
        │   │   │  Use Cases   │   │    │  QuoteService
        │   │   │  ┌────────┐  │   │    │
        │   │   │  │ Domain │  │   │    │  Instrument, Quote, Watchlist
        │   │   │  └────────┘  │   │    │
        │   │   └──────────────┘   │    │
        │   └──────────────────────┘    │
        └──────────────────────────────┘
                зависимости → внутрь
```

Домен — самый внутренний слой — не знает ни о сети, ни о диске, ни о фреймворках. Это делает его стабильным: меняются
детали (сеть, формат хранения), ядро — нет.

---

## Dependency Inversion как механизм

Чтобы внешний слой оставался подключаемым, а зависимость шла внутрь, используют инверсию: внутренний слой объявляет
**порт** (интерфейс), внешний — реализует его **адаптером**. В проекте это уже есть:

```
QuoteService ──зависит от──▶ QuoteSource (порт, внутренний слой)
                                  ▲
                                  │ реализует
                            HttpQuoteSource (адаптер, внешний слой)
```

`QuoteService` не знает про `HttpClient` — только про интерфейс. Сетевой адаптер подключается снаружи (в `Main`). Та же
схема — `InstrumentRepository` + `InMemoryInstrumentRepository`. Инверсия зависимости — то, что сделало код тестируемым
(mock вместо сети) и заменяемым (стаб → реальный API).

## Нарушение: домен знает про фреймворк

Правило зависимостей в проекте нарушено в одном месте: `Instrument` и подклассы несут аннотации Jackson
(`@JsonTypeInfo`, `@JsonCreator`). Домен зависит от библиотеки сериализации — деталь внешнего слоя протекла в ядро.
Симптом: смена формата хранения (Jackson → другой сериализатор) потребует правки доменных классов, хотя домен к
хранению отношения не имеет.

---

## Очистка через mixin

Знание о сериализации переносится в слой `storage` через Jackson **mixin** — абстрактный класс с теми же аннотациями,
привязываемый к домену снаружи:

```java
// storage/InstrumentJsonMixin — аннотации здесь, домен чист
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, include = JsonTypeInfo.As.PROPERTY, property = "type")
@JsonSubTypes({ @JsonSubTypes.Type(value = Stock.class, name = "STOCK"), /* ... */ })
abstract class InstrumentJsonMixin { }
```

```java
void example(ObjectMapper mapper) {
    mapper.addMixIn(Instrument.class, InstrumentJsonMixin.class);
    mapper.addMixIn(Stock.class, StockJsonMixin.class);
}
```

Домен освобождается от аннотаций; знание о формате живёт в адаптере хранения. Характеризационный тест round-trip
подтверждает, что поведение сериализации не изменилось.

---

## Цена чистоты

Clean Architecture не бесплатна: порты, адаптеры и mixin'ы — дополнительный код и уровни косвенности. Для небольшого
проекта строгое следование правилу может быть избыточным — аннотации на домене остаются приемлемым компромиссом.
Ценность растёт с размером и сроком жизни системы: чем дольше живёт код и чем чаще меняются детали, тем важнее, чтобы
ядро от них не зависело.

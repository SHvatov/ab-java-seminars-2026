# Монолит и микросервисы

---

## Что это

**Монолит** — одно приложение, развёртываемое и запускаемое как единое целое; компоненты общаются внутренними вызовами.
Market Pulse — монолит: один процесс, вызовы между слоями внутри JVM.

**Микросервисы** — приложение, разбитое на отдельно развёртываемые сервисы, каждый со своей зоной ответственности и
своими данными; общаются по сети (HTTP/gRPC/очереди).

Это не «плохо против хорошо», а разные компромиссы под разные задачи.

---

## Где прошли бы границы

Микросервис режет систему по естественным швам. В нашем проекте швы уже видны — это порты:

- `InstrumentRepository` / `InstrumentStorage` — сервис «каталог инструментов»;
- `QuoteSource` — сервис «котировки»;
- `WatchlistStorage` — сервис «watchlist»;
- (в перспективе) `Portfolio` — сервис «портфель».

Микросервис прошёл бы ровно по такому шву, заменив внутренний вызов интерфейса сетевым запросом. Чистые границы монолита
— предпосылка к разделению: плохие границы внутри монолита станут плохими границами по сети, только дороже.

---

## Цена микросервисов

Разделение на сервисы приносит не только плюсы:

| | Монолит | Микросервисы |
|---|---|---|
| Развёртывание | одно | независимое по сервисам |
| Масштабирование | целиком | по сервисам |
| Вызовы | внутренние, быстрые | сетевые, с задержкой и сбоями |
| Данные | одна согласованная база | распределённые, согласованность в конечном счёте |
| Отладка | один процесс | распределённая трассировка |
| Эксплуатация | простая | сложная (оркестрация, мониторинг) |

Для CLI-утилиты одного пользователя микросервисы — чистый проигрыш: вся цена, ноль выгоды.

---

## Когда дробить

Не «модно», а когда у частей системы:

- **разный цикл изменений** — одна часть меняется ежедневно, другая годами;
- **разная нагрузка** — одну надо масштабировать отдельно;
- **разные команды** — независимое владение и развёртывание.

Пока этого нет, монолит с чистыми внутренними границами выигрывает. Практическое правило — **monolith first**: начинать
с монолита, поддерживать в нём ясные границы (порты, слои), и выделять сервис только под доказанную потребность, а не
авансом.

---

## Вывод

Микросервисы решают организационные и масштабные проблемы, а не проблемы качества кода. Плохой код не станет лучше от
разнесения по сети — станет только распределённым. Хорошо структурированный монолит (как наш, с портами `QuoteSource`,
`InstrumentRepository`) — и достаточное решение для проекта такого размера, и правильная отправная точка, если он
когда-нибудь дорастёт до разделения.

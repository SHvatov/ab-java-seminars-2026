## Часть 1. Работа с файловой системой

### Этап 1. IO vs NIO: старое и новое API работы с файлами (~15 мин)

Презентация по материалу [«Java IO vs NIO»](./Java%20IO%20vs%20NIO.md).

Всё состояние приложения (каталог инструментов, watchlist, кеш котировок) до сих пор жило в памяти и терялось при
перезапуске. Java даёт два поколения файлового API:

- **Классический IO** (`java.io`, Java 1.0) — потоки байтов и символов, ориентированные на последовательное чтение;
  ручная обёртка ресурсов.
- **NIO** — двухслойный: низкоуровневый `java.nio.channels` (каналы и буферы, Java 1.4) и высокоуровневый
  `java.nio.file` — NIO.2 (`Path`, `Files`, Java 7). Каналы работают блоками через `ByteBuffer` и умеют неблокирующий
  режим (этап 6); `Files`/`Path` дают компактные высокоуровневые операции.

```java
void example(Path file) throws IOException {
    String content = Files.readString(file);   // NIO.2 — одна операция
    Files.writeString(file, content);
}
```

> **Акцент:** новый код проекта — на NIO.2 (`Path`/`Files`). Каналы (`FileChannel`, `SocketChannel`) — нижний слой, к
> которому вернёмся на этапе 6 со стороны сети.

### Этап 2. Постоянное хранилище: инструменты и watchlist в JSON через NIO (~25 мин)

Каталог инструментов и watchlist должны переживать перезапуск. Храним их на диске в JSON, в отдельных директориях,
читаем и пишем через NIO.

**Сериализация.** Домен полиморфен (`Stock`/`Bond`/`Etf`) и использует `BigDecimal`. Стандартная библиотека
JSON-сериализатора не содержит, поэтому подключаем Jackson (`jackson-databind`). Полиморфизм разрешается через
`@JsonTypeInfo`/`@JsonSubTypes` (дискриминатор `type` в JSON); `BigDecimal` Jackson сериализует без потери точности.

**Раскладка.** Каждый инструмент — файл `data/instruments/<TICKER>.json`; watchlist — `data/watchlist.json`. Директории
создаются `Files.createDirectories`.

**Хранилище.** Класс `storage/InstrumentStorage` сохраняет и загружает каталог через NIO. Репозиторий продвинутого
трека — интерфейс `InstrumentRepository` (реализация `InMemoryInstrumentRepository`); хранилище работает с интерфейсом,
не завязываясь на реализацию:

```java
public List<Instrument> loadAll() throws IOException {
    if (Files.notExists(instrumentsDir)) {
        return List.of();
    }
    try (Stream<Path> files = Files.list(instrumentsDir)) {   // NIO: обход директории; стрим закрываем
        return files
                .filter(path -> path.toString().endsWith(".json"))
                .map(this::readInstrument)
                .toList();
    }
}
```

При старте репозиторий наполняется из `loadAll()`; `add` сохраняет инструмент на диск.

> **Самостоятельно (студенты):** реализовать персистентность watchlist (`Set<String>` → `data/watchlist.json` и
> загрузка при старте) по образцу `InstrumentStorage`.

> **Для семинариста:** стрим из `Files.list`/`walk` держит открытый дескриптор директории — его обязательно закрывать
> через try-with-resources (семинар 4). Частая утечка ресурсов.

### Этап 3. Эффективная работа с диском (~10 мин)

Подробнее — в материале [«Эффективная работа с диском»](../../materials/seminar7/Эффективная%20работа%20с%20диском.md).
Тезисы: буферизация группирует мелкие операции в крупные (`newBufferedReader/Writer`); маленький файл читается целиком
(`readString`/`readAllBytes`), большой — потоково (`Files.lines`); каждый доступ к диску — системный вызов, поэтому JSON
формируется в памяти и пишется одним `Files.write`. Отдельно — memory-mapped файлы (`FileChannel.map`, `MappedByteBuffer`):
отображение файла в память для больших объёмов, к которым обращаются как к массиву.

> **Акцент:** для наших данных хватает `Files.write`/`readString`; буферизация, потоковое чтение и mmap — задел на рост
> объёмов.

### Этап 5. Реальный T-Invest API через `HttpClient` (~25 мин)

Заменяем заглушку котировок реальными данными из T-Invest API
([developer.tbank.ru/invest](https://developer.tbank.ru/invest/intro/intro)) через `java.net.http.HttpClient`
(стандартная библиотека). Новый источник `service/HttpQuoteSource` реализует контракт `QuoteSource`, но ходит в сеть
`POST`-запросом с `Authorization: Bearer <token>`; ответ парсится Jackson в `Quote`.

**Токен** — из переменной окружения (`TINVEST_TOKEN`), не в репозитории; без токена приложение предупреждает при старте,
а сетевые команды возвращают пустой результат. **Идентификатор и изменение** — T-Invest адресует инструменты по
FIGI/instrumentId (тикер разрешается через API, результат кешируется); последнюю цену даёт `GetLastPrices`, изменение
считается относительно закрытия (`GetClosePrices`). `QuoteSource` становится интерфейсом; `stats`/`movers` агрегируют
котировки **отслеживаемых инструментов** (watchlist), `compare` — переданных тикеров. Котировка строится только для
инструмента, уже добавленного в каталог (`add`).

> **Самостоятельно (студенты):** реализовать `fetch` для одного эндпоинта (последняя цена по идентификатору): собрать
> `HttpRequest`, отправить, проверить статус, распарсить ответ.

> **Для семинариста:** каждая котировка — несколько отдельных запросов (резолв + последняя и закрытая цены), поэтому
> опрос большого watchlist упирается в лимит (`429` из этапа 4). В проде такие запросы батчат (`GetLastPrices` принимает
> массив идентификаторов) и кешируют; здесь для простоты каждый инструмент опрашивается отдельно.

> **Для семинариста:** `HttpClient.send(...)` блокирующий; есть и `sendAsync(...)` → `CompletableFuture`. Это мост к
> этапу 6: `HttpClient` внутри опирается на неблокирующие каналы и `Selector`, скрывая их за высокоуровневым API.

### Этап 6. Неблокирующий ввод-вывод: `Selector` и `AsynchronousSocketChannel` (~25 мин)

Лекция по материалу [«Selector и AsynchronousSocketChannel»](./Selector%20и%20AsynchronousSocketChannel.md); подробный
разбор — в deep-dive [«Неблокирующее сетевое взаимодействие в Java»](../../materials/seminar7/Неблокирующее%20сетевое%20взаимодействие%20в%20Java.md).

Разбираем три модели сетевого ввода-вывода на примерах (примеры в материале, семинарист проходит по коду):

- **Блокирующая** (`SocketChannel` в блокирующем режиме, как `HttpClient.send`): поток на соединение, `read` блокирует
  поток до данных. Просто, но не масштабируется на тысячи соединений.
- **Неблокирующая с `Selector`** (`SocketChannel.configureBlocking(false)` + `Selector.select()`): один поток
  обслуживает много каналов, реагируя на события готовности (`OP_READ`/`OP_WRITE`/`OP_ACCEPT`). Именно эта модель лежит
  под высоконагруженными серверами.
- **Асинхронная** (`AsynchronousSocketChannel`): операции возвращают `Future`/принимают `CompletionHandler`, завершение
  приходит колбэком; пул потоков управляется JDK.

**Selector под капотом.** `Selector` — обёртка над системным механизмом мультиплексирования готовности: `epoll` на
Linux, `kqueue` на macOS/BSD, `poll`/`select` как переносимый fallback. JDK выбирает реализацию по ОС; семантика
`select()` одна, эффективность и внутреннее устройство различаются.

> **Для семинариста:** ключевой вывод — `HttpClient` из этапа 5 не магия: под ним неблокирующие каналы и `Selector`.
> Разница подходов — не «какой лучше», а «какая цена и под какую нагрузку»: блокирующая модель проще и годится для CLI,
> неблокирующая/асинхронная — для серверов с тысячами соединений. Пример с `AsynchronousSocketChannel` (эхо по
> loopback) разбирается по коду из материала; в проект он не встраивается — это иллюстрация механизма, а не фича
> Market Pulse.

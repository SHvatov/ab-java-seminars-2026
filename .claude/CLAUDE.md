# Проект: курс Java (АБ, 2026–2027)

Разработка программы и материалов учебного курса по Java для образовательного учреждения. Это **не** production-код —
это учебные материалы (планы семинаров, лекционные конспекты, сопроводительные тексты) плюс сопровождающий их
эталонный код проекта, который студенты пишут по ходу курса.

## Два трека

- **Базовый (`basic/`)** — базовый курс для студентов, которые только начинают учить Java.
- **Продвинутый (`advanced/`)** — то же базовый трек плюс более глубокое погружение (JVM internals, байт-код,
  расширенные
  паттерны, замеры производительности, дополнительные библиотеки).

Различия между треками **не проговариваются явно внутри материалов продвинутого трека** — он читается как
самостоятельный документ. Материалы продвинутого трека написаны **независимо**, а не как копипаст базового с добавками:
при переносе правки между треками переносится **смысл**, а не дословный текст (структура, порядок и уровень детализации
могут различаться).

## Сквозной проект: Market Pulse

CLI-терминал аналитики фондового рынка на T-Invest API (Т-Банк). Сюжетная рамка — вымышленный «Серёжа», который хочет
разобраться в инвестициях. Каждый семинар наращивает один и тот же проект.

**Доменная модель** (`academy.backend.market_pulse`): `Instrument` (abstract) → `Stock`/`Bond`/`Etf`; `Quote`
(агрегация инструмента с ценой); `Portfolio` с вложенным `Position` (композиция). Цена (`price`) живёт **только в
`Quote`**, а не в `Instrument`. Денежные величины — `BigDecimal` (не `double`), деление — с явным `RoundingMode`.

## Жёсткие ограничения курса

- Только vanilla Java, без Spring и фреймворков (сторонние библиотеки допустимы, но приоритет — стандартной библиотеке).
- Формат — CLI-инструмент, источник данных — T-Invest API.
- Java 25, Maven (родительский `pom.xml` + модули `basic`/`advanced`).
- Хронометраж семинара — ~1 час 30 минут, из них ~30 минут на самостоятельную активность студентов.
- **Никаких разделов домашнего задания** внутри файлов семинаров.
- В конце каждого файла семинара — блок тегов навыков (skills tags).
- У каждого студента — собственный репозиторий.

## Структура репозитория

- `raw/moduleN/seminarM/` — черновики-исходники: `Карточка семинара.md`, `Базовый трек.md`, `Продвинутый трек.md` плюс
  лекционные заготовки. Неполированный вход, из которого выводятся финальные материалы. **Есть только для семинаров
  1–4.** Для семинаров 5+ готовых черновиков в `raw/` нет — исходником служит секция `## Семинар N — ...` из
  `raw/Верхнеуровневый план.md` (пререквизиты, «что делаем», состояние проекта на начало/конец, навыки), из которой
  материалы создаются с нуля.
- `{basic,advanced}/docs/seminars/seminarN/` — выход: `План семинара.md` (для семинариста — что делать, про что
  рассказать, какой код получить в итоге) плюс короткие «презентационные» md-файлы, которые семинарист использует как
  live-референс/слайды на занятии.
- `{basic,advanced}/docs/materials/seminarN/` — более детальный технический материал для самостоятельного изучения
  студентами (deep-dive), те же темы, но подробнее.
- `{basic,advanced}/src/` — эталонный код проекта.
- `review/` — сводные MD-файлы (один на трек на семинар) для внешнего ревью: план + лекционный материал + исходный код
  вставками + сопроводительный материал, в этом порядке.
- `raw/Верхнеуровневый план.md` — 14-семинарный план курса + полное описание Market Pulse.

## Аудитория и тон

- **План семинара** — для семинариста: верхнеуровневое описание хода занятия, акценты, ремарки для преподавателя.
- **Всё остальное** — материалы для студентов, без авторских/методических комментариев к преподавателю.
- Сопроводительные/лекционные документы **самодостаточны**: не ссылаются на номера семинаров или структуру курса.
- Форвард-референсы: будущее содержание кратко упоминается со ссылкой вперёд, а не опускается и не раскрывается
  преждевременно.
- Тон — академический, безличный (без «мы/вы»), без эмодзи, строго формальный. Технические термины — на английском
  (`Heap`, `Non-Heap` и т.п.), основной текст — на русском.
- Описания лаконичны (2–4 предложения). Гранулярность — отдельный файл на каждую тему/семинар (во избежание конфликтов
  при редактировании).

## Правила по коду в материалах

- **Каждый Java-фрагмент** должен быть синтаксически валиден на верхнем уровне: либо полный класс/интерфейс, либо
  голые операторы обёрнуты в `void example() { ... }`. Никаких висящих операторов на file scope — IntelliJ ругается.
- **Domain model drift:** черновики в `raw/` для будущих семинаров написаны с опережением и ссылаются на поля/классы,
  которых в реальном коде нет (историческая ловушка: `Instrument.getPrice()`). Перед тем как доверять любому фрагменту
  из черновика — сверять с фактическим `src/`. При расхождении — чинить консистентно с уже принятыми решениями (не
  возвращать `price` в `Instrument` ради компиляции примера).
- Код должен реально компилироваться против доменной модели, а не только иллюстрировать идею.

## Workflow создания семинара (→ docs + src)

Четыре этапа, каждый — на оба трека. Источник зависит от семинара: для 1–4 есть черновики в `raw/` (перенос +
вычитка); для 5+ черновиков нет — вводные берутся из **двух** частей верхнеуровневого плана: строки семинара в таблице
«Первичный план-капкан» (проектные мысли автора) + детальной секции `## Семинар N`.

0. **Обсуждение (только сем. 5+, до генерации)** — не разворачивать верхнеуровневый план молча: прочитать оба
   источника вводных, выявить открытые развилки, предложить пользователю ~2 целостных варианта структуры семинара
   (через `AskUserQuestion`, с поэтапной аркой в preview); пользователь выбирает один или накидывает свой. План
   пишется из согласованной структуры.
1. **План семинара** — из `raw/` (сем. 1–4) либо из согласованной структуры (сем. 5+); критически вычитать на
   внутреннюю непротиворечивость и соответствие **фактическому текущему коду** (в т.ч. устаревшая мотивация — источник
   мог описывать поведение, уже изменённое поздним семинаром), исправить противоречия.
2. **Лекционный материал** — вынести встроенную в план теорию в отдельные референс-файлы `docs/seminars/`, оформить по
   образцу предыдущих семинаров, план сослать на них вместо инлайна.
3. **Сопроводительный материал** — deep-dive в `docs/materials/`: для сем. 1–4 перенести из `raw/` (убрать
   дубль-заголовок и пометку «Сопроводительный материал к семинару N»), для 5+ написать с нуля. Материалы
   самодостаточны.
4. **Код** — реализовать `src/`-изменения; код обязан компилироваться против актуальных классов. В конце `План
   семинара.md` — секция «Исходный код» со ссылками на файлы.

**После значимого этапа — обновить «Журнал изменений» ниже** (готов семинар, проведено ревью, изменена
договорённость/архитектурное решение). Одна короткая строка, чтобы будущая сессия восстановила контекст, не перечитывая
весь репозиторий.

Порядок: полностью один трек (базовый), затем другой (продвинутый) — advanced может ссылаться на решения basic
(«как в базовом треке»).

Гранулярность коммитов **уточняется под каждый семинар**: и по коммиту на этап×трек (8 штук), и один общий коммит на
всё — оба варианта уже применялись. Сообщение коммита — две части: «Затронутые темы» и «Правки в уже существующих
материалах» (что было не так и что изменилось, а не только что добавлено).

## Git

- Пользователь **по умолчанию коммитит сам**. «Собрать/составить commit message» = только текст, без `git add`/`git
  commit`. Исключение — когда явно просит «сделай N коммитов сам» в рамках многоэтапной задачи.
- Ветки — по семинарам (`seminar1`, `seminar2`, …).

## Ключевые архитектурные решения по коду (для консистентности)

- **Factory Method:** базовый трек — самрегистрация фабрик через `static`-блок + `Class.forName`-форсирование загрузки
  в `InstrumentFactories` (осознанный компромисс с OCP, проговаривается в плане). Продвинутый трек — `ServiceLoader`
  (SPI, `META-INF/services/...`), честно закрывающий OCP.
- **Repository:** базовый трек — конкретный класс `InstrumentRepository`. Продвинутый — интерфейс `InstrumentRepository`
    + реализация `InMemoryInstrumentRepository` (интерфейс нужен для JDK Dynamic Proxy на семинаре 2).
- Прогрессия: доменная модель (сем. 1) → CLI на picocli + паттерны Command/Factory/Strategy/Iterator (сем. 2) →
  функциональный стиль: лямбды/generics/Optional, `Predicate` вместо классов-фильтров, `Registry<K,V>` (сем. 3) →
  обработка ошибок: собственные исключения, try-with-resources, JMH-замеры (сем. 4).

# graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

- **graphify** (`.claude/skills/graphify/SKILL.md`) - any input to knowledge graph. Trigger: `/graphify`
  When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:

- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use
  `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a
  scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough
  context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

# Составление плана семинара

**Что производим:** `{basic|advanced}/docs/seminars/seminarN/План семинара.md`.

**Аудитория:** это **единственный** документ курса с ремарками для преподавателя (акценты, «обсудить со студентами»,
«для семинариста»). Всё остальное — student-facing.

## Источники

Зависит от семинара:

- **Семинары 1–4** — есть черновик в `raw/moduleN/seminarM/`: `{Базовый,Продвинутый} трек.md` (черновик плана) и
  `Карточка семинара.md` (пререквизиты, темы, навыки, тайминг/сложность). Перенос + вычитка.
- **Семинары 5+** — черновиков в `raw/` **нет**. Два источника вводных внутри `raw/Верхнеуровневый план.md`:
  1. **Строка семинара в таблице «Первичный план-капкан»** (в самом начале файла) — проектные мысли автора: тема
     лекции, буллеты «Практика на семинаре», отдельная колонка «Продвинутый трек» (что убираем / что добавляем).
  2. **Детальная секция `## Семинар N — ...`** — пререквизиты, «что делаем», состояние проекта на начало/конец, блок
     навыков (отдельно на каждый трек).

Черновики/верхнеуровневый план написаны с опережением и могут ссылаться на несуществующий или уже изменённый код —
**сверять с фактическим `src/`** (см. «Обязательная критическая вычитка»).

## Обсуждение с пользователем ДО генерации (семинары 5+)

Для семинаров без готового черновика **не разворачивать верхнеуровневый план в план молча** — сначала обсудить с
пользователем его видение по каждому треку:

1. Прочитать **оба** источника вводных выше (строку таблицы + детальную секцию).
2. Выявить реальные развилки, которые вводные оставляют открытыми (пример сем. 4: реального API ещё нет — заглушка до
   семинара 7, поэтому на каких сценариях учить обработке ошибок — открытый вопрос).
3. Предложить пользователю **~2 целостных варианта структуры** семинара (арка этапов + формат самостоятельной
   активности + различия треков) через `AskUserQuestion`; варианты обосновать вводными, в `preview` показать
   поэтапную арку по трекам. Пользователь выбирает один вариант **или накидывает свой** (опция «Other»).
4. Только после выбора — писать план из согласованной структуры.

Не задавать 4 разрозненных микровопроса — пользователь предпочитает выбор из пары holistic-вариантов «собери так или
так».

## Структура файла (по образцу семинаров 1–4)

1. `# Базовый трек` / `# Продвинутый трек` — строка-маркер трека.
2. `# Семинар N. <Название>`
3. `**Тема модуля:**` и `**Тема семинара:**`
4. `## Пререквизиты` — inline-код-теги через backticks, включая ссылки на предыдущие семинары и нужные инструменты.
5. `## План семинара` — таблица `| # | Этап | Время |`.
6. Секции `### Этап N. <Название> (~T мин)` — что делать, про что рассказать, какой код получить, акценты в
   blockquote (`> **Акцент:**`, `> **Обсуждение:**`, `> **Для семинариста:**`).
7. `### Исходный код` — ссылки на итоговые файлы `src/` (добавляются на этапе реализации кода).
8. `## Навыки, полученные на семинаре` — блок тегов через backticks.

**Кросс-линки на свои материалы.** Там, где этап опирается на теорию, вынесенную в отдельный файл, план **ссылается**
на неё, а не повторяет текст: на презентационный файл того же семинара
(`Презентация по материалу [«...»](./<Тема>.md)`) и на deep-dive в `docs/materials/`
(`Подробнее — в материале [«...»](../../materials/seminarN/<Тема>.md)`). Эти ссылки проставляются/сверяются на этапе
выноса лекционных материалов, но держать их в голове уже при написании плана.

## Тайминг

Сумма этапов ≈ 90 минут, из них ~30 минут заложено на самостоятельную активность студентов (брейншторминг,
самостоятельная задача, разбор). Продвинутый трек обычно длиннее (~120 мин) за счёт доп. тем. Правишь состав этапов —
пересчитай тайминг и в таблице, и в заголовках `### Этап` (легко забыть одно из двух).

## Обязательная критическая вычитка

Перед тем как доверять черновику, проверить план на:

- **Соответствие реальному коду** предыдущих семинаров (не тексту черновика для будущих). Классическая ловушка —
  `Instrument.getPrice()`: цены в `Instrument` нет, она в `Quote`. См. `[[domain-model-drift]]` в CLAUDE.md. При
  расхождении чинить консистентно с уже принятыми решениями, а не подгонять модель под пример.
- **Устаревшая мотивация (draft-vs-current-code).** Отдельный, более коварный класс расхождений, чем drift сигнатур:
  черновик/верхнеуровневый план мотивирует семинар «сломанным» текущим поведением, которое **более поздний семинар уже
  починил** — код при этом компилируется, ломается только педагогическая точность. Если этап опирается на «вот тут
  сейчас падает / молчит / возвращает null» — **фактически проследить это поведение по реальному коду** на момент
  этого семинара. Если проблема уже (частично) решена: переписать нарратив под реальность, **удалить шаги, которые
  предыдущий семинар уже сделал**, перенумеровать оставшиеся и пересчитать тайминг. (Сем. 4: черновик мотивировал
  `NullPointerException` в `InstrumentFactories.create`, но с семинара 3 `create` уже кидает осмысленный
  `IllegalArgumentException` через `orElseThrow` — «первая поломка» переписана в «громкая, но никем не услышанная», а
  шаг «добавляем проверку на null» удалён как избыточный.)
- **Внутреннюю непротиворечивость**: код в одном этапе не должен ломать компиляцию кода из другого (пример: перевод
  метода на `Optional` без обновления всех его вызовов).
- **Код-фрагменты** обёрнуты корректно: полный класс/интерфейс либо `void example() { ... }`, без висящих операторов.
- **Форвард-референсы**: будущее упоминается кратко со ссылкой вперёд, не раскрывается преждевременно.
- **Тайминг** сходится (и в таблице, и в заголовках `### Этап` — при удалении/слиянии шагов пересчитать оба).

## Тон

Академический, безличный, без эмодзи. Ремарки для преподавателя допустимы **только здесь** (в blockquote). Технические
термины — на английском, текст — на русском.

## Порядок треков

Сначала полностью базовый трек, затем продвинутый. Продвинутый трек пишется **независимо** (не копипаст), правки
переносятся по смыслу; advanced может ссылаться на решения basic («как в базовом треке»), но различия между треками
внутри материалов продвинутого трека явно не проговариваются.

## После работы

Добавить короткую запись в «Журнал изменений» в `.claude/CLAUDE.md` (готов план семинара N — оба трека), чтобы будущая
сессия восстановила контекст.

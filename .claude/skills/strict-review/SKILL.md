# Придирчивое ревью результата

**Роль:** строгий, придирчивый куратор курса, который оценивает готовый семинар как цельный результат. Задача — не
поправить материал, а **вынести исчерп, приоритизированный разбор в файл `COMMENTS.md`**. Исходники (планы,
материалы, код) в этом режиме **не редактируются** — ни инлайн-правок, ни «мелких» исправлений опечаток. Правки —
отдельная задача, которую пользователь запускает потом (например, через `materials-review`).

## Жёсткое правило вывода

- Всё, что нашлось, пишется в `COMMENTS.md` (по умолчанию — в корне репозитория). Никаких `Edit`/`Write` по файлам
  семинара.
- Если пользователь уже принял какое-то решение (например, через вопрос-развилку), это не повод молча внести правку —
  зафиксировать в `COMMENTS.md` как «согласовано: …», чтобы след остался.
- `COMMENTS.md` перезаписывается целиком при новом прогоне того же семинара; для разных семинаров — разделы внутри
  файла (`# Семинар N`) либо, если так удобнее пользователю, отдельный `COMMENTS.md` рядом с материалами семинара.
  Уточнить размещение, если неочевидно.

## Четыре критерия оценки

Каждую находку соотнести с одним из критериев (в `COMMENTS.md` группировать по ним):

1. **Связность** — материал читается как единое целое: этапы вытекают один из другого, код одного этапа не ломает
   другой, презентации и deep-dive согласованы с планом, кросс-линки ведут куда надо.
2. **Логичность** — мотивация каждого шага честна: проблема, которую решает этап, действительно существует в коде на
   этот момент (а не «почищена» более поздним семинаром); выводы следуют из посылок; акценты расставлены верно.
3. **Актуальность** — всё сверено с **фактическим** `src/`, а не с текстом черновика: сигнатуры, поля, доменная
   модель, версии, ссылки на файлы. Главный рецидив — domain-model drift (`Instrument.getPrice()`, `double` для денег,
   устаревшие сигнатуры после рефакторингов).
4. **Соответствие верхнеуровневому плану** — сверить с обеими частями `raw/Верхнеуровневый план.md`: строкой семинара
   в таблице «Первичный план-капкан» и детальной секцией `## Семинар N` (состояние проекта на начало/конец, заявленные
   темы и навыки). Явно отметить: что из заявленного покрыто, что опущено, что добавлено сверх плана, и разошёлся ли
   список навыков.

## Что проверять по пунктам

Полный чек-лист на непротиворечивость (domain-drift, устаревшая мотивация, внутренняя согласованность этапов,
преемственность с предыдущими семинарами, кросс-трек, обёртка код-фрагментов, тайминг, самодостаточность, doc↔code
sync, отсутствие висячего кода) — переиспользовать из скилла `materials-review`, раздел «Что проверять» и «Типовые
находки». Этот скилл добавляет к нему: (а) роль придирчивого куратора и планку строгости, (б) явную оценку по четырём
критериям выше, (в) вывод в `COMMENTS.md` вместо инлайн-правок.

Дополнительно, специфично для «придирчивости»:

- **Тайминг против бюджета.** Сумма этапов должна укладываться в ~90 минут (в т.ч. ~30 на self-work). Перебор — находка,
  даже если внутри план согласован; посчитать и назвать цифру.
- **Заявленные навыки vs выданные.** Теги навыков в конце файла семинара сверить с навыками из верхнеуровневого плана и
  с реально пройденным материалом; расхождения — находка.
- **Формулировка «конец состояния проекта».** Сопоставить обещанное планом конечное состояние с тем, что реально
  получилось в коде; переинтерпретации отметить (даже когда реализация связнее плана).

## Дисциплина точности (придирчивость ≠ вкусовщина)

- Каждую находку **верифицировать по реальному коду/файлам** перед записью — придирчивый ревьюер не плодит ложные
  срабатывания. Если утверждение не подтвердилось при проверке — не выносить.
- Отделять **дефект** (объективно не так: не компилируется, противоречит модели, ломает другой этап, расходится с
  планом) от **дизайн-решения** (спорно, но допустимо). Дефекты — в раздел замечаний; дизайн-решения — в раздел
  «Вопросы на решение автора», как вопрос, а не как приговор.
- Стиль/вкус (формулировки, порядок абзацев) выносить только если это реально вредит связности или логике, и помечать
  как низкий приоритет.

## Формат `COMMENTS.md`

```markdown
# Придирчивое ревью — Семинар N

_Отревьюено: <дата>, ветка <branch>, треки: базовый / продвинутый._

## Вердикт
<2–4 предложения: общий уровень, где главные риски.>

## Сильные стороны
- <по пунктам, с указанием файла>

## Замечания
Приоритизированы (сначала самое серьёзное). Для каждого: **[критерий]** суть — файл:строка — почему это проблема —
предлагаемое направление правки (без внесения).

1. **[Актуальность]** …
2. **[Связность]** …
…

## Вопросы на решение автора
- <дизайн-развилки, где нужно решение пользователя, а не правка>

## Согласовано ранее
- <решения, уже принятые пользователем в этой сессии, зафиксированы для следа>
```

Строгий порядок разделов: Вердикт → Сильные стороны → Замечания → Вопросы → Согласовано.

## После работы

- Сообщить пользователю кратко: путь к `COMMENTS.md`, число находок по критериям, 1–2 самые серьёзные. Полный разбор —
  в файле, не дублировать его целиком в чат.
- Исходники не трогать. Если пользователь после прочтения `COMMENTS.md` попросит внести правки — это уже другой режим
  (`materials-review` с инлайн-правкой).
- Журнал изменений в `CLAUDE.md` в этом режиме **не** обновлять (ревью без правок — не значимый этап изменения
  материалов); обновление журнала — забота того шага, который реально вносит правки.

# Написание кода семинара

**Что производим:** изменения в `{basic|advanced}/src/main/java/academy/backend/market_pulse/...` (и `pom.xml` при
новых зависимостях) — эталонный код, который студенты пишут на семинаре. Плюс секция `### Исходный код` со ссылками на
итоговые файлы в конце `План семинара.md`.

## Главное правило

Это **реальный компилируемый код**, а не иллюстрация. Он обязан собираться против **фактических текущих классов**
проекта, а не против того, что предполагает черновик плана. Если план/черновик расходится с реальной моделью —
исправить и код, и план (пример: `InstrumentFactory.create(..., price)` не компилируется, т.к. `price` не поле
`Instrument` → сменить сигнатуру на `Currency`, поправить и план). См. `[[domain-model-drift]]` в CLAUDE.md.

Правило обёртки `void example() {}` относится к **фрагментам в документах**, а не к реальным `.java`-файлам — здесь
пишутся полноценные классы.

## Никакого висячего (dead) кода

Каждый новый класс/сервис/метод должен **откуда-то вызываться**. Провал — конкретно: класс `Foo` реализован, но
`grep Foo src` находит только его собственное определение (исторический пример — «висящий» `Quote`: модель есть, ни
одного использования).

**Доменный код — только через CLI.** Новая доменная возможность (`Watchlist`, `QuoteService` и т.п.) должна быть
достижима из реального приложения — то есть из `Main` через picocli-команду, закрывающую функциональное требование
Market Pulse (`watch`, `quote`, …). Именно CLI-команда, а не отдельный демонстрационный класс, считается использованием
доменного класса. Заводя такую возможность, добавляешь: саму команду в `cli/`, её регистрацию в `Main`
(`addSubcommand(...)` с общими на приложение `repository`/`watchlist`/сервисами), и отражаешь команду в плане (этап,
где она вводится) и в секции «Исходный код».

**Демо-`main` — только как замена тестов для инструментария.** Классы `demo/` с `main` допустимы **лишь** для замера и
интроспекции, где полноценного теста пока нет и не обсуждался: JOL (раскладка объектов), JMH-бенчмарки и т.п. (образцы —
`demo/JolDemo`, `benchmark/*`). Их «использование» — сам факт запуска инструмента. Демо-класс, который просто
демонстрирует работу доменного класса вместо того, чтобы подключить его к CLI, — **не** валидное использование: домен
идёт в функциональные команды, а не в витрину.

После реализации — самопроверка `grep`-ом: у каждого нового доменного типа есть использование в `cli/`+`Main`, а не
только в демо.

## Различия треков (держать консистентно)

- **Factory Method:**
  - базовый — самрегистрация фабрик через `static`-блок + `Class.forName`-форсирование загрузки в `InstrumentFactories`
    (осознанный компромисс с OCP);
  - продвинутый — `ServiceLoader` (SPI): `InstrumentFactory.getSupportedType()`, файл
    `advanced/src/main/resources/META-INF/services/academy.backend.market_pulse.factory.InstrumentFactory`, без
    статических блоков.
- **Repository:**
  - базовый — конкретный класс `InstrumentRepository`;
  - продвинутый — интерфейс `InstrumentRepository` + реализация `InMemoryInstrumentRepository` (интерфейс нужен для
    JDK Dynamic Proxy на семинаре 2).
- Продвинутый трек имеет доп. `demo/`-классы и зависимости (`jol`, `cglib`, `vavr`, `jmh`), которых нет в базовом.

## Доменные инварианты (не нарушать)

- `price` — только в `Quote`, не в `Instrument`.
- Деньги — `BigDecimal`, не `double` (в т.ч. `Bond.couponRate`); деление — с явным `RoundingMode` (например
  `HALF_UP`).
- `Quote.toString()` различает рост/падение/ноль (`▲`/`▼`/`▬`), не выдаёт ноль за рост.
- Пакетная база — `academy.backend.market_pulse`.

## После реализации

- Добавить/обновить `### Исходный код` в `План семинара.md` — markdown-ссылки на созданные/изменённые файлы
  (`[`model/Foo.java`](../../../src/main/java/.../Foo.java)`).
- Новые зависимости — в соответствующий `{track}/pom.xml` с комментарием, на каком семинаре/этапе они появились.
- Компиляцию проверяет пользователь в IntelliJ IDEA (в среде нет `mvn`) — не гадать про результат сборки, но код
  писать так, чтобы он компилировался.
- Обновить «Журнал изменений» в `.claude/CLAUDE.md` — короткая запись про готовый код семинара (и особо — про новые
  архитектурные решения или расхождения plan-vs-code, которые пришлось разрешить: следующая сессия должна их видеть).

# Ревью материалов и кода

**Цель:** проверить план, лекционные/сопроводительные материалы и код семинара на согласованность — внутреннюю, с
предыдущими семинарами и с фактической доменной моделью. По умолчанию **отдельно** перечислить сильные стороны и
**отдельно** — что поправить; править инлайн, если пользователь просит.

## Что проверять

1. **Domain-model drift** (главный рецидивный класс багов): любой код-фрагмент и сигнатура сверяются с реальным
   `src/`, а не с текстом черновика. Ловушки: `Instrument.getPrice()` (цены нет, она в `Quote`), `double` вместо
   `BigDecimal` для денег, устаревшие сигнатуры после более поздних рефакторингов (например `InstrumentFactories.register`
   после перехода на `ServiceLoader`). См. `[[domain-model-drift]]` в CLAUDE.md.
2. **Устаревшая мотивация (draft-vs-current-code):** этап мотивирует «сломанным» текущим поведением, которое более
   поздний семинар уже починил, — код компилируется, но нарратив неверен. Проследить описанное поведение по реальному
   коду; если проблема уже решена — нарратив переписать, лишние шаги удалить, перенумеровать, пересчитать тайминг.
   (Сем. 4: мотивация «NPE в `create`», хотя с сем. 3 `create` кидает `IllegalArgumentException` через `orElseThrow`.)
3. **Внутренняя непротиворечивость плана:** код одного этапа не ломает компиляцию кода из другого (перевод метода на
   `Optional`/новую сигнатуру без обновления всех вызовов; удаление класса, на который ещё ссылаются).
4. **Согласованность с предыдущими семинарами:** используемые классы/методы действительно существуют в состоянии
   проекта на момент этого семинара; форвард-референсы корректны и не раскрыты преждевременно.
5. **Кросс-трек:** базовый и продвинутый согласованы **по смыслу** (не дословно); правка, внесённая в один трек, имеет
   аналог в другом там, где темы пересекаются; в advanced нет ремарок про базовый трек и различия треков.
6. **Обёртка код-фрагментов:** полный класс/интерфейс либо `void example() {}`, без висящих операторов.
7. **Тайминг** этапов сходится (и в таблице, и в заголовках `### Этап`).
8. **Самодостаточность материалов** (`docs/seminars` презентации и `docs/materials`): нет ссылок на номера семинаров;
   ремарки для преподавателя — только в `План семинара.md`.
9. **Doc↔code sync:** код-вставки в плане совпадают с реальными файлами `src/`; ссылки в секции «Исходный код» ведут на
   существующие файлы. Кросс-линки плана на свои презентационные/deep-dive файлы ведут на существующие пути.
10. **Нет висячего (dead) кода:** каждый новый класс/сервис/метод откуда-то **вызывается** (`grep`-ом: у типа `Foo` вне
    `Foo.java` есть использование — иначе дефект; исторический пример — «висящий» `Quote`). Строже для **доменного**
    кода: он должен быть достижим из реального приложения — из `Main` через picocli-команду, закрывающую функциональное
    требование Market Pulse (`watch`, `quote`, …), а не через демонстрационный класс. Демо-`main` — валидное
    использование **только** для инструментария замера/интроспекции как замены тестов (JOL, JMH-бенчмарки); демо,
    показывающее работу доменного класса вместо подключения его к CLI, — не считается использованием.

## Типовые находки прошлых ревью (проверять адресно)

- `couponRate: double` в `Bond` при том, что план учит использовать `BigDecimal` для денег.
- `Quote.toString()` показывает `▲ 0%` при нулевом изменении.
- `divide(...)` без `RoundingMode`.
- Утверждение об OCP, которое не выдерживает проверки (статический блок `InstrumentFactories`, который всё равно
  придётся править при новом типе).
- Материал, объясняющий словами то, что уже сделано в коде иначе (или наоборот — расхождение plan-vs-code).
- Демо с жёстким `Thread.sleep` там, где уместнее ожидание ввода (`Scanner`).
- Новый класс/сервис, реализованный, но никем не вызываемый (`grep` находит только его собственное определение).
- Опечатки в `raw/Верхнеуровневый план.md` (внутренняя методичка, но всё равно чинить по просьбе).

## Сборка сводных файлов для внешнего ревью

Директория `review/` — по одному MD-файлу на трек на семинар: план → лекционный материал → исходный код (вставками с
путями) → сопроводительный материал, именно в этом порядке, каждый раздел отделён `# N. НАЗВАНИЕ` и `---`. Код брать из
состояния репозитория **на момент завершения этого семинара** (через `git show <ref>:<path>`), а не из текущего HEAD —
иначе в бандл попадут более поздние правки из семинаров 3–4 в общих файлах (`Main.java`, `Stock.java`, `pom.xml`).
Исключение — файлы, уже поправленные позднейшим ревью (`Bond.java`, `Quote.java`, …): их брать из HEAD, чтобы не тащить
в бандл уже найденные баги.

## Формат ответа

Сильные стороны — отдельным блоком, замечания — отдельным, с указанием файла и сути. Если правишь инлайн — кратко
описать каждую правку. Если находка спорна или это дизайн-решение, а не баг — вынести на решение пользователю, не чинить
молча.

## После работы

Если по итогам ревью внесены правки — добавить короткую запись в «Журнал изменений» в `.claude/CLAUDE.md` (что за
семинар отревьюен, ключевые исправления). Особенно важно зафиксировать **изменённые архитектурные решения** (как переход
на `ServiceLoader` по итогам ревью сем. 2) — это то, из чего следующая сессия восстанавливает актуальное состояние.

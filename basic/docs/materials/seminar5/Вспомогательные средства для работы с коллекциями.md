# Вспомогательные средства для работы с коллекциями

Коллекции редко используются «в чистом виде»: типовые операции — отсортировать, найти минимум, посчитать вхождения,
отдать наружу неизменяемое представление — вынесены в утилитарные средства, чтобы не переписывать их вручную на каждый
случай. Стандартная библиотека покрывает эти задачи классом `java.util.Collections` и фабричными методами
`List.of`/`Set.of`/`Map.of`. За её пределами существуют сторонние библиотеки со специализированными коллекциями; их
краткий обзор — в конце.

## Содержание

1. `java.util.Collections` — утилитарные операции
2. Неизменяемость: `unmodifiable*` против фабрик `List.of`/`Map.of`
3. Сторонние библиотеки — краткий обзор

## 1. `java.util.Collections` — утилитарные операции

`Collections` — служебный класс из `java.util`, целиком состоящий из статических методов над коллекциями. Он не хранит
данные, а предоставляет готовые алгоритмы; работает через интерфейсы (`List`, `Collection`), поэтому применим к любой
реализации.

### Сортировка

`Collections.sort` упорядочивает `List` на месте. Порядок задаётся либо естественным сравнением (если элементы
`Comparable`), либо явным `Comparator`:

```java
void example(List<Instrument> instruments) {
    // По тикеру, по возрастанию.
    Collections.sort(instruments, Comparator.comparing(Instrument::getTicker));
}
```

Тот же результат даёт метод самого списка `instruments.sort(...)`; `Collections.sort` — исторически более ранняя форма,
обе делегируют одному алгоритму (устойчивая сортировка слиянием). `Comparator` комбинируется: `reversed()` разворачивает
порядок, `thenComparing(...)` добавляет вторичный ключ.

### Поиск и агрегаты

```java
void example(List<Instrument> instruments) {
    Instrument first = Collections.min(instruments, Comparator.comparing(Instrument::getTicker));
    Instrument last  = Collections.max(instruments, Comparator.comparing(Instrument::getTicker));

    int rubCount = Collections.frequency(
            instruments.stream().map(Instrument::getCurrency).toList(), Currency.RUB);
}
```

- `min`/`max` возвращают крайний элемент по компаратору за один проход (`O(n)`), не сортируя весь список.
- `frequency` считает, сколько раз значение встречается в коллекции (сравнение через `equals`).

`Collections.binarySearch` ищет элемент за `O(log n)`, но требует **предварительно отсортированного** по тому же
компаратору списка — иначе результат не определён:

```java
void example(List<Instrument> instruments, Instrument target) {
    Comparator<Instrument> byTicker = Comparator.comparing(Instrument::getTicker);
    instruments.sort(byTicker);
    int index = Collections.binarySearch(instruments, target, byTicker);
    // index >= 0 — позиция найденного; index < 0 — элемента нет
}
```

### Разворот, перемешивание, заполнение

`Collections.reverse` разворачивает список, `shuffle` перемешивает в случайном порядке, `fill` заменяет все элементы
одним значением, `nCopies` создаёт список из `n` одинаковых элементов. Это точечные операции, избавляющие от ручного
цикла.

### Неизменяемые представления

`Collections.unmodifiableList`/`unmodifiableSet`/`unmodifiableMap` оборачивают коллекцию так, что попытка изменения
через обёртку бросает `UnsupportedOperationException`. Именно этот приём использует `Portfolio.getPositions()` и
`Watchlist.tickers()`, чтобы отдать внутреннюю коллекцию наружу, не давая клиенту её испортить:

```java
public Set<String> tickers() {
    return Collections.unmodifiableSet(tickers);
}
```

Важная оговорка про этот приём — в следующем разделе.

## 2. Неизменяемость: `unmodifiable*` против фабрик `List.of`/`Map.of`

`Collections.unmodifiableSet(set)` возвращает не копию, а **представление** (view) поверх исходной коллекции. Менять
через обёртку нельзя, но если у кого-то остаётся ссылка на исходный изменяемый `set`, его правки будут видны сквозь
обёртку:

```java
void example() {
    Set<String> backing = new HashSet<>(Set.of("SBER"));
    Set<String> readOnly = Collections.unmodifiableSet(backing);

    backing.add("GAZP");       // меняем оригинал
    // readOnly теперь тоже содержит GAZP — обёртка смотрит на тот же набор
}
```

Поэтому `unmodifiable*` защищает от изменения *через данную ссылку*, но не делает данные по-настоящему неизменяемыми.
Когда исходная коллекция гарантированно не доживает до места использования (как приватное поле, отдаваемое наружу
только через обёртку) — этого достаточно.

Фабричные методы `List.of`, `Set.of`, `Map.of` (Java 9+) создают **по-настоящему неизменяемую** коллекцию: у неё нет
изменяемого оригинала, любая мутация невозможна, а `null`-элементы запрещены (бросается `NullPointerException` при
создании). Это предпочтительный способ задать неизменяемый набор литералом:

```java
void example() {
    List<Currency> supported = List.of(Currency.RUB, Currency.USD, Currency.EUR);
    Map<String, Integer> weights = Map.of("SBER", 40, "GAZP", 60);
    // supported.add(...) и weights.put(...) бросят UnsupportedOperationException
}
```

Правило выбора: для неизменяемой константы, задаваемой на месте, — `List.of`/`Map.of`; для защиты уже существующего
приватного поля при отдаче наружу — `Collections.unmodifiable*`. Если нужна независимая неизменяемая копия внешних
данных — сначала защитная копия (`new ArrayList<>(source)`), затем обёртка или `List.copyOf(source)`.

## 3. Сторонние библиотеки — краткий обзор

Стандартная библиотека закрывает подавляющее большинство задач. Специализированные коллекции из экосистемы имеют смысл
там, где стандартных средств не хватает по выразительности или по производительности; цена — дополнительная
зависимость. Ниже — что предлагает каждая и когда к ней осмысленно тянуться.

- **Guava** (Google) — среди прочего даёт по-настоящему неизменяемые `ImmutableList`/`ImmutableMap` (полноценная копия,
  а не обёртка) и `Multimap` — отображение «один ключ → несколько значений» вместо ручного `Map<K, List<V>>` с
  инициализацией списка при первом добавлении. Осмысленна, когда в коде много ручных `Map<K, List<V>>` или требуется
  строгая иммутабельность.
- **Apache Commons Collections** — утилитарный класс `CollectionUtils` с теоретико-множественными операциями (`union`,
  `intersection`, `subtract`) и структуры вроде `Bag` (мультимножество, считающее вхождения). Дополняет
  `java.util.Collections` операциями, которых в стандартной библиотеке нет.
- **Vavr** — функциональные *персистентные* (неизменяемые) коллекции: каждая «модификация» возвращает новую версию, а
  старая остаётся неизменной, причём версии дёшево делят общие внутренние узлы. Уместна в функциональном стиле, где
  недопустимо незаметное изменение коллекции по ссылке.
- **fastutil** — примитивные коллекции (`int`/`long`/`double` вместо обёрток `Integer`/`Long`/`Double`): хранят
  примитивы напрямую, без boxing, экономя память и повышая скорость доступа. Выигрыш заметен на больших объёмах
  числовых данных; на малых коллекциях смысла нет.

Общий принцип: сторонняя библиотека оправдана, когда стандартная коллекция вынуждает писать много вспомогательного
кода или упирается в производительность на конкретном профиле нагрузки. По умолчанию выбор — стандартный `java.util`.

## 1. Обзор и иерархия интерфейсов

Java Collection Framework (JCF) — часть стандартной библиотеки (`java.util`), предоставляющая интерфейсы структур
данных и их готовые реализации. Framework отделяет **контракт** структуры (интерфейс `List`, `Set`, `Queue`, `Map`)
от **реализации** (`ArrayList`, `HashSet`, `ArrayDeque`, `HashMap`), что позволяет программировать против интерфейса и
менять реализацию, не трогая остальной код.

Корень иерархии коллекций — интерфейс `Iterable`, обеспечивающий перебор элементов. Его наследует `Collection` — общий
предок для `List`, `Set` и `Queue`. Отдельно стоит `Map`: она **не** наследует `Collection`, потому что оперирует
парами «ключ-значение», а не отдельными элементами.

```
Iterable
 └── Collection
      ├── List   — упорядоченная последовательность, дубликаты допускаются
      ├── Set    — множество уникальных элементов
      └── Queue  — очередь с дисциплиной обработки

Map          — отображение «ключ → значение» (самостоятельная иерархия)
```

Практическое следствие обособленности `Map`: у неё нет метода `iterator()`. Для перебора `Map` используются три
представления — `keySet()` (множество ключей), `values()` (коллекция значений) и `entrySet()` (множество пар
`Map.Entry`), каждое из которых уже является `Collection` и перебирается обычным образом.

## 2. List под капотом: ArrayList и LinkedList

`List` — упорядоченная последовательность: элементы хранятся в порядке добавления, допускаются дубликаты, есть доступ
по индексу. Две основные реализации устроены принципиально по-разному.

### ArrayList

Внутри `ArrayList` — обычный Java-массив (`Object[] elementData`) и поле `size` с числом реально занятых ячеек. Массив
почти всегда больше, чем `size`: в нём есть запас под будущие добавления.

**Добавление в конец (`add`).** Если в массиве есть свободная ячейка, элемент просто записывается в позицию `size`, и
`size` увеличивается — это `O(1)`. Когда массив заполнен, происходит **расширение** (grow): создаётся новый массив
большего размера (в текущей реализации — примерно в 1.5 раза), и все элементы копируются в него через
`Arrays.copyOf`. Единичное расширение стоит `O(n)`, но происходит редко, поэтому в среднем по множеству добавлений
стоимость одного `add` — амортизированно `O(1)`.

```java
void example() {
    List<String> tickers = new ArrayList<>();  // начальная ёмкость по умолчанию — 10
    tickers.add("SBER");                        // запись в ячейку, O(1)
    // ...после заполнения следующий add вызовет grow: новый массив + копирование
}
```

Если итоговый размер известен заранее, стоит задать начальную ёмкость через `new ArrayList<>(expectedSize)` — это
избавляет от промежуточных расширений и копирований.

**Доступ по индексу (`get(i)`).** Прямое обращение к ячейке массива — `O(1)`.

**Поиск по значению (`contains`, `indexOf`).** Линейный перебор всех элементов до совпадения — `O(n)`. Именно поэтому
поиск нужного объекта в большом `ArrayList` замедляется пропорционально его размеру.

**Удаление по индексу (`remove(i)`).** После удаления все элементы правее сдвигаются на одну позицию влево
(`System.arraycopy`) — `O(n)`.

### LinkedList

`LinkedList` — двусвязный список: каждый элемент обёрнут в узел (`Node`) с ссылками на предыдущий и следующий узлы.
Сам список хранит ссылки на первый и последний узлы.

**Добавление и удаление в известной позиции** (в начало, в конец, либо через итератор, стоящий на нужном месте) —
`O(1)`: достаточно переставить несколько ссылок, без сдвига данных.

**Доступ по индексу (`get(i)`)** — `O(n)`: чтобы добраться до i-го элемента, приходится идти по ссылкам от начала
(или от конца) списка.

**Поиск по значению** — `O(n)`, как и у `ArrayList`.

### Что выбирать

По умолчанию — `ArrayList`. Он компактнее по памяти (нет накладных узлов со ссылками), лучше ложится на кеш
процессора (данные лежат подряд) и в реальных сценариях почти всегда быстрее, даже там, где асимптотика `LinkedList`
формально выигрывает. `LinkedList` оправдан редко — например, когда список используется как очередь/дек с частыми
вставками и удалениями с обоих концов, но и для этого случая `ArrayDeque` обычно предпочтительнее.

## 3. Set: обзор, сложность, когда использовать

`Set` — множество уникальных элементов. Ключевое свойство: повторное добавление уже присутствующего элемента ничего
не меняет, и `add` возвращает `false`.

| Реализация | add / contains / remove | Порядок обхода |
|------------|-------------------------|----------------|
| `HashSet` | `O(1)` в среднем | не определён |
| `LinkedHashSet` | `O(1)` в среднем | порядок добавления |
| `TreeSet` | `O(log n)` | отсортированный |

`HashSet` внутри устроен поверх `HashMap` (элементы множества — это ключи, значение везде одна и та же заглушка),
поэтому его поведение и требования к `equals`/`hashCode` — те же, что у `HashMap` (см. раздел 5). `LinkedHashSet`
дополнительно связывает элементы в список в порядке добавления и обеспечивает предсказуемый порядок обхода. `TreeSet`
хранит элементы в сбалансированном дереве по порядку сравнения (`Comparable` или `Comparator`).

```java
void example() {
    Set<String> tickers = new LinkedHashSet<>();
    boolean added = tickers.add("SBER"); // true — добавлено
    boolean again = tickers.add("SBER"); // false — уже есть, множество не изменилось
}
```

**Когда использовать.** Когда нужна уникальность элементов и/или быстрая проверка принадлежности («есть ли уже такой»).
`HashSet` — по умолчанию; `LinkedHashSet` — когда важен стабильный порядок обхода; `TreeSet` — когда элементы нужно
держать отсортированными или запрашивать диапазоны/ближайшие значения.

## 4. Queue: обзор, сложность, когда использовать

`Queue` — очередь: элементы обрабатываются в определённом порядке, чаще всего FIFO (первым пришёл — первым обработан).
Базовые операции работают с двумя концами: добавление в хвост и извлечение из головы.

Два набора методов различаются поведением на границе:

| Операция | Не бросает исключение | Бросает исключение |
|----------|-----------------------|--------------------|
| Добавить в хвост | `offer(e)` → `boolean` | `add(e)` |
| Извлечь из головы | `poll()` → `null` на пустой | `remove()` |
| Посмотреть голову | `peek()` → `null` на пустой | `element()` |

Основная реализация — `ArrayDeque` (кольцевой буфер поверх массива): все операции с обоими концами — `O(1)`, накладных
расходов меньше, чем у `LinkedList`. `ArrayDeque` работает и как FIFO-очередь (`offer`/`poll`), и как LIFO-стек
(`push`/`pop`), и предпочтительнее устаревшего класса `Stack`.

```java
void example() {
    Queue<String> pending = new ArrayDeque<>();
    pending.offer("SBER");            // в хвост
    pending.offer("GAZP");
    String next = pending.poll();     // "SBER" — из головы (FIFO)
}
```

**Когда использовать.** Когда элементы нужно обрабатывать по мере поступления, буферизовать задачи между «положить» и
«обработать», реализовать обход в ширину или как эффективную замену стека.

## 5. HashMap под капотом

`Map` хранит пары «ключ → значение» и обеспечивает быстрый доступ к значению по ключу. `HashMap` — реализация на
основе хеш-таблицы; понимание её устройства объясняет и производительность, и требования к ключам.

### Массив бакетов и хеширование

Внутри `HashMap` — массив «корзин» (buckets), `Node[] table`. Чтобы положить пару, `HashMap`:

1. вычисляет `hashCode()` ключа и дополнительно «перемешивает» его старшие биты (чтобы плохие хеш-функции реже давали
   коллизии);
2. по полученному хешу вычисляет индекс бакета — через побитовое `И` с `(размер_массива - 1)` (поэтому размер таблицы
   всегда степень двойки);
3. кладёт узел (`ключ`, `значение`, `хеш`) в этот бакет.

Поиск `get(key)` идёт тем же путём: вычислить бакет по хешу ключа, затем внутри бакета найти узел с равным ключом.
Если ключи распределены по бакетам равномерно, в каждом бакете — единицы элементов, и `get`/`put`/`containsKey`
работают за `O(1)` в среднем.

### Коллизии

Разные ключи могут попасть в один бакет (коллизия). Тогда узлы в бакете связываются в список, и при поиске
`HashMap` перебирает этот короткий список, сравнивая ключи через `equals`. Если из-за плохой хеш-функции в один бакет
попадает много ключей, список становится длинным, и поиск деградирует к `O(n)`. Чтобы ограничить деградацию, начиная
с Java 8 длинный список в бакете (порог — 8 элементов при достаточном размере таблицы) преобразуется в
сбалансированное дерево, и поиск в переполненном бакете идёт за `O(log n)`, а не `O(n)`.

### Load factor и расширение

Чтобы бакеты не переполнялись по мере роста данных, `HashMap` следит за заполненностью через **load factor** (по
умолчанию `0.75`). Когда число пар превышает `ёмкость × 0.75`, таблица расширяется: создаётся вдвое больший массив
бакетов, и все существующие пары **перераспределяются** (rehash) по новым бакетам. Это разовая операция `O(n)`,
амортизируемая по множеству вставок. Если итоговый размер известен, начальная ёмкость через `new HashMap<>(capacity)`
избавляет от промежуточных перехеширований.

### Требования к ключу: equals и hashCode

Корректная работа `HashMap` держится на согласованности `equals` и `hashCode` ключа:

- если два ключа равны по `equals`, их `hashCode` **обязаны** совпадать — иначе `HashMap` будет искать значение не в
  том бакете и «потеряет» его;
- обратное не требуется: разные по `equals` ключи могут иметь одинаковый `hashCode` (это коллизия, она допустима).

Отсюда правило: переопределяя `equals`, всегда переопределяют и `hashCode` согласованно. Использовать в качестве ключа
изменяемый объект, у которого `hashCode` меняется после помещения в `Map`, — ошибка: узел останется в старом бакете, и
`get` его не найдёт. Поэтому хорошие ключи — неизменяемые (`String`, обёртки примитивов, значения-`record`).

`String` как ключ чувствителен к регистру: `"sber"` и `"SBER"` дают разные `hashCode` и считаются разными ключами.
Если нужна нечувствительность к регистру, ключ нормализуют (например, к верхнему регистру) в одном месте — и при
записи, и при чтении.

```java
void example() {
    Map<String, String> byTicker = new HashMap<>();
    byTicker.put("SBER".toUpperCase(), "Сбербанк");
    String name = byTicker.get("sber".toUpperCase()); // "Сбербанк" — ключ нормализован
}
```

## 6. Другие реализации Map: LinkedHashMap и TreeMap

`LinkedHashMap` наследует `HashMap` и дополнительно связывает записи в двусвязный список в порядке добавления ключей.
Сложность операций та же — `O(1)` в среднем, — но обход идёт в предсказуемом порядке. Это делает `LinkedHashMap`
удобной, когда нужна и скорость hash-таблицы, и стабильный порядок вывода.

`TreeMap` хранит ключи в сбалансированном дереве по порядку сравнения (`Comparable` ключа или переданный
`Comparator`). Операции — `O(log n)`, зато доступны отсортированный обход и запросы по диапазону
(`firstKey`, `floorKey`, `subMap` и подобные).

| Реализация | get / put / containsKey | Порядок обхода |
|------------|-------------------------|----------------|
| `HashMap` | `O(1)` в среднем | не определён |
| `LinkedHashMap` | `O(1)` в среднем | порядок добавления |
| `TreeMap` | `O(log n)` | отсортированный по ключу |

## 7. Выбор структуры данных под задачу

Выбор структуры определяется тем, какая операция на ней частая и во сколько она обходится при росте данных.

- **Нужен доступ по индексу и порядок, дубликаты допустимы** → `List` (`ArrayList`).
- **Нужна уникальность и/или быстрая проверка принадлежности** → `Set` (`HashSet`/`LinkedHashSet`).
- **Нужна обработка по порядку поступления, буфер задач** → `Queue` (`ArrayDeque`).
- **Нужен быстрый поиск значения по ключу** → `Map` (`HashMap`/`LinkedHashMap`).
- **Нужен отсортированный порядок или запросы по диапазону** → `TreeSet`/`TreeMap`.

Типичная ошибка — хранить данные в `List` и постоянно искать в нём по значению линейным перебором. Если основная
операция — поиск по некоторому ключу, данные стоит индексировать в `Map` по этому ключу: поиск станет `O(1)` вместо
`O(n)` и перестанет зависеть от размера.

## 8. Итераторы, fail-fast и ConcurrentModificationException

`Iterator` — объект обхода коллекции с методами `hasNext()`, `next()` и `remove()`. Цикл for-each — синтаксический
сахар над `Iterator`: компилятор разворачивает его в получение итератора и цикл по `hasNext`/`next`.

Коллекции JCF реализуют принцип **fail-fast**: каждая структурная модификация коллекции (добавление/удаление элемента)
увеличивает внутренний счётчик изменений `modCount`. Итератор запоминает значение `modCount` в момент создания и
сверяет его на каждом шаге. Если коллекция изменилась в обход итератора (например, прямым вызовом `remove` по коллекции
внутри for-each), значения расходятся, и итератор бросает `ConcurrentModificationException` — вместо того чтобы молча
продолжить с потенциально испорченным состоянием.

```java
void example(List<String> tickers) {
    for (String ticker : tickers) {
        if (ticker.startsWith("T")) {
            tickers.remove(ticker); // ConcurrentModificationException на следующем шаге
        }
    }
}
```

Имя исключения обманчиво: «concurrent» здесь не про многопоточность — одного потока, изменяющего коллекцию мимо
итератора, достаточно, чтобы его получить.

Правильный способ удалять элементы во время обхода — через сам итератор: `Iterator.remove()` удаляет последний
возвращённый `next()` элемент и синхронно обновляет `modCount`, поэтому обход остаётся согласованным.

```java
void example(List<String> tickers) {
    Iterator<String> it = tickers.iterator();
    while (it.hasNext()) {
        String ticker = it.next();
        if (ticker.startsWith("T")) {
            it.remove(); // безопасно
        }
    }
}
```

`Iterator.remove()` разрешено вызывать только после `next()` и не более одного раза на каждый `next()` — иначе
`IllegalStateException`. Для частого случая «удалить всё, подходящее под условие» удобнее метод коллекции
`removeIf(predicate)` (Java 8+), который внутри использует тот же итератор и не нарушает fail-fast.

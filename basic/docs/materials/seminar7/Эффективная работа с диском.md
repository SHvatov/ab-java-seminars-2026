# Эффективная работа с диском

Диск на порядки медленнее памяти, а каждое обращение к нему — переход в ядро операционной системы. Поэтому то, *как*
организованы чтение и запись, влияет на производительность не меньше, чем объём данных. Этот материал разбирает
буферизацию, выбор между чтением целиком и потоково и минимизацию системных вызовов.

## Содержание

1. Почему диск медленный
2. Буферизация

## 1. Почему диск медленный

Обращение к диску (даже SSD) на несколько порядков медленнее доступа к памяти. Кроме самой задержки, каждая операция
чтения/записи через API — это системный вызов: переключение из пользовательского кода в код ядра и обратно, само по себе
не бесплатное. Отсюда общий принцип: меньше и крупнее обращения к диску лучше, чем много мелких.

---

## 2. Буферизация

Буфер — область памяти, в которой данные накапливаются, чтобы обмениваться с диском крупными порциями вместо множества
мелких. Чтение файла по одному байту породило бы отдельный системный вызов на каждый байт; буфер собирает, скажем, 8 КБ
за один вызов, а код читает из буфера уже из памяти.

```java
void example(Path file) throws IOException {
    // Буферизованное чтение построчно — по одному системному вызову на блок, а не на строку.
    try (BufferedReader reader = Files.newBufferedReader(file)) {
        String line;
        while ((line = reader.readLine()) != null) {
            process(line);
        }
    }
}
```

`Files.newBufferedReader`/`newBufferedWriter` дают буферизацию из коробки. `BufferedWriter` накапливает записи и сбрасывает
их на диск блоком (при заполнении буфера, `flush()` или закрытии).

---

## 3. Целиком против потоково

- **Целиком** (`Files.readString`, `Files.readAllBytes`) — одна операция, весь файл в памяти. Быстро и просто для
  небольших файлов; для нашего JSON инструмента (сотни байт) это оптимально.
- **Потоково** (`Files.lines`, буферизованный `Reader`) — файл обрабатывается порциями, не загружаясь целиком. Нужно для
  больших файлов, которые не помещаются (или не должны помещаться) в память.

Ошибка в обе стороны: читать большой лог целиком в `String` — риск `OutOfMemoryError`; читать маленький конфиг по строкам
ручным циклом — лишняя сложность без выигрыша.

---

## 4. Минимизация системных вызовов

Каждый вызов `write` — переход в ядро. Сто записей по строке — сто переходов; одна запись массива байтов — один. Поэтому
данные выгодно сформировать в памяти и записать одной операцией:

```java
void example(Path file, byte[] json) throws IOException {
    Files.write(file, json);   // один системный вызов на весь файл
}
```

Именно так сохраняется JSON инструмента: Jackson формирует массив байтов в памяти, а `Files.write` пишет его целиком.

---

## 5. Практика для нашего приложения

Данные Market Pulse — десятки небольших JSON-файлов. Для них:

- запись — `Files.write(path, bytes)` целиком, один системный вызов на файл;
- чтение — `Files.readAllBytes`/`readString` целиком;
- обход директории — `Files.list` (не забывая закрыть стрим).

Буферизация и потоковое чтение здесь не нужны — это инструменты для больших объёмов. Но понимать их важно: когда данные
вырастут (история котировок, логи), выбор между «целиком» и «потоково» и наличие буфера начнут определять, работает ли
приложение под нагрузкой.

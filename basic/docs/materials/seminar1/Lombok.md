# Lombok

---

## 1. Проблема, которую решает Lombok

Java-класс, описывающий сущность с несколькими полями, обрастает большим объёмом кода, не несущего смысловой
нагрузки: геттеры, конструкторы, `equals`/`hashCode`, `toString`. Этот код механически выводится из объявления полей,
но должен быть написан и поддерживаться вручную — при добавлении нового поля разработчик обязан не забыть обновить
все производные методы.

**Lombok** — библиотека, генерирующая такой код на этапе компиляции по аннотациям над классом или полями. Исходный
файл остаётся коротким, а сгенерированный байт-код содержит полноценные методы, неотличимые от написанных руками.
Генерация происходит через механизм annotation processing — специальный плагин компилятора, встраивающийся в процесс
сборки.

## 2. Подключение в проект

### 2.1. Maven

Добавить зависимость в `pom.xml` соответствующего модуля:

```xml
<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <version>1.18.36</version>
    <scope>provided</scope>
</dependency>
```

Область видимости `provided` означает, что библиотека нужна только на этапе компиляции (для генерации кода) и не
попадает в собранный артефакт — сгенерированные методы уже присутствуют в скомпилированных классах.

Компилятору нужно явно указать Lombok как annotation processor:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
                <version>1.18.36</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
```

### 2.2. IntelliJ IDEA

IDE обрабатывает файлы независимо от Maven и должна уметь показывать сгенерированные методы (автодополнение,
переход к определению, отсутствие ложных ошибок компиляции прямо в редакторе). Для этого требуются два независимых
шага:

1. **Плагин Lombok** — Settings → Plugins → найти «Lombok» → установить, перезапустить IDE.
2. **Annotation Processing** — Settings → Build, Execution, Deployment → Compiler → Annotation Processors → включить
   «Enable annotation processing».

Без обоих шагов IDE будет подчёркивать использование сгенерированных методов как ошибку, хотя `mvn compile`
отработает корректно — эти два процесса (компиляция Maven и подсветка в IDE) независимы друг от друга.

## 3. Основные аннотации

### 3.1. Геттеры и сеттеры

```java
public class Example {
    @Getter
    @Setter
    private String name;
}
```

`@Getter`/`@Setter` над полем генерируют `getName()`/`setName(String)`. Над классом — применяются сразу ко всем
полям. Модификатор доступа генерируемого метода можно сузить (`@Getter(AccessLevel.PROTECTED)`), а поле — исключить
из общей аннотации класса точечной аннотацией `@Setter(AccessLevel.NONE)` над конкретным полем.

### 3.2. Конструкторы

- `@NoArgsConstructor` — пустой конструктор.
- `@AllArgsConstructor` — конструктор со всеми полями класса, в порядке объявления.
- `@RequiredArgsConstructor` — конструктор только для `final`-полей и полей, помеченных `@NonNull`.

```java
@RequiredArgsConstructor
public class Instrument {
    private final String ticker;
    private final String name;
}
```

### 3.3. `toString`, `equals`, `hashCode`

`@ToString` генерирует читаемое строковое представление на основе полей (можно исключить конкретные поля через
`@ToString.Exclude`). `@EqualsAndHashCode` генерирует пару согласованных методов `equals`/`hashCode` на основе полей
класса (аналогично можно исключать отдельные поля).

### 3.4. Составные аннотации

- `@Data` — сокращение для `@Getter` + `@Setter` (на все поля) + `@ToString` + `@EqualsAndHashCode` +
  `@RequiredArgsConstructor`. Удобна для изменяемых DTO, но добавляет сеттеры без разбора — для классов с
  инвариантами (см. ниже) обычно излишня.
- `@Value` — неизменяемый аналог `@Data`: поля становятся `private final`, сеттеры не генерируются, класс — `final`.
- `@Builder` — генерирует паттерн Builder для пошагового конструирования объекта с именованными параметрами вместо
  длинного списка позиционных аргументов конструктора.

## 4. Ограничения и осторожности

**Валидация инвариантов.** Сгенерированные Lombok-конструкторы (`@AllArgsConstructor`, `@RequiredArgsConstructor`)
не содержат проверок — они лишь присваивают переданные значения полям. Если конструктор должен валидировать
аргументы (например, отклонять пустой тикер), такой конструктор нужно писать вручную — Lombok не заменяет логику
защиты инвариантов, только механическое связывание полей и параметров.

**`@Data` на классах с инвариантами.** Автоматически сгенерированные сеттеры позволяют менять состояние объекта в
обход какой-либо валидации — что подрывает инкапсуляцию, если у класса есть контракт на неизменность или
согласованность полей. Для таких классов предпочтительны точечные аннотации (`@Getter` без `@Setter`,
`@RequiredArgsConstructor` для `final`-полей) вместо `@Data`.

**Отладка.** Сгенерированный код не виден в исходном файле — при пошаговой отладке это может сбивать с толку, пока
не привыкнешь; большинство IDE умеют показывать деломбокированный (development-time) вид класса.

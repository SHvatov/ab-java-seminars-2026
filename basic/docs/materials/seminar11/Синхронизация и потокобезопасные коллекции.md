# Синхронизация и потокобезопасные коллекции

Пока потоки не делят изменяемое состояние, параллелизм безопасен. Как только они начинают менять одно и то же — общий
счётчик, общую коллекцию, — возникают гонки. Материал разбирает, что при этом ломается, и какими средствами это чинить:
`ConcurrentHashMap`, синхронизаторы, потокобезопасные коллекции.

## 1. Race condition и data race

**Race condition** — результат программы зависит от того, в каком порядке потоки успели выполнить действия. Классический
пример — списание денег: два потока читают баланс 100, каждый вычитает 100, оба записывают 0, хотя списано 200.

**Data race** — частный случай: несколько потоков обращаются к одной и той же памяти без синхронизации, и хотя бы одно
обращение — запись. Data race — не просто «неверное значение», а неопределённое поведение: структура данных может
повредиться.

Коварство гонок — в невоспроизводимости: «на одном потоке работает», «у меня не падает». Проявляются они только под
конкуренцией и зависят от планировщика.

---

## 2. Почему ломается общий HashMap

`HashMap` спроектирован для однопоточного доступа. При одновременной записи из нескольких потоков повреждается его
внутренняя структура — массив корзин и цепочки/деревья узлов внутри них. Наблюдаемые симптомы:

- **потерянные записи** — два потока пишут в одну корзину, одно обновление затирается; в кеше меньше элементов, чем
  уникальных ключей;
- **`ConcurrentModificationException`** — итерация замечает структурное изменение;
- **зависание** — при рехешировании конкурентная запись способна закольцевать цепочку узлов (исторически — бесконечный
  цикл).

Дополнительно — ошибка **check-then-act**: «если в кеше нет — сходить в сеть и положить». Проверка и вставка выполняются
двумя разными операциями; между ними вклинивается другой поток, и оба идут в сеть, а то и перезаписывают друг друга.

## 3. ConcurrentHashMap и computeIfAbsent

`ConcurrentHashMap` — потокобезопасная `Map` для конкурентного доступа. Простая замена типа устраняет data race:

```java
private final Map<String, Quote> cache = new ConcurrentHashMap<>();
```

Проблему check-then-act решает атомарный `computeIfAbsent` — проверка и вставка одной атомарной операцией:

```java
void example(Map<String, Quote> cache, String ticker, QuoteSource source) {
    Quote quote = cache.computeIfAbsent(ticker, t -> source.fetch(t).orElse(null));
}
```

Если функция вернёт `null`, запись не создаётся (значение просто не кешируется). Для нашего кеша котировок это ровно то,
что нужно: параллельные воркеры не портят структуру и не дублируют сетевые вызовы за одним тикером.

---

## 4. synchronizedMap против ConcurrentHashMap

`Collections.synchronizedMap(new HashMap<>())` тоже потокобезопасен — но оборачивает **каждую** операцию единым замком на
всю карту. Потоки выстраиваются в очередь даже за независимыми ключами, и параллелизм вырождается в последовательное
исполнение с накладными на блокировку.

`ConcurrentHashMap` блокирует не всю карту, а лишь отдельную корзину при записи (а чаще — обходится без блокировки
вовсе), чтение почти всегда идёт без блокировок. Поэтому под конкурентной нагрузкой он на порядки быстрее
`synchronizedMap`. Практическое правило: для конкурентного доступа — `ConcurrentHashMap`, а `synchronizedMap` — легаси.

## 5. Синхронизаторы

Синхронизаторы (`java.util.concurrent`) координируют потоки на более высоком уровне, чем ручные блокировки:

- **`CountDownLatch`** — дождаться N событий (одноразово): `countDown()` на каждое событие, `await()` пропускает при нуле.
- **`Semaphore`** — ограничить одновременность: `acquire()`/`release()` вокруг ограниченного ресурса (рейт-лимитер к API).
- **`CyclicBarrier`** — собрать N потоков в точке и продолжить вместе (многоразово).
- **`ReentrantLock`** — гибкая замена `synchronized` с `tryLock(timeout)`.

Сопоставление задачи и инструмента: «дождаться N» → `CountDownLatch`, «ограничить одновременность» → `Semaphore`,
«собрать в точке» → `CyclicBarrier`. Блокирующие операции применяют с таймаутом, иначе одна зависшая задача блокирует
систему.

## 6. Потокобезопасные коллекции

- **`ConcurrentHashMap`** — конкурентная `Map` (наш кеш).
- **`CopyOnWriteArrayList`** — «часто читаем, редко пишем»: чтение не блокируется (по снимку), запись копирует массив.
- **`BlockingQueue`** — очередь для producer/consumer: `put` ждёт на полной, `take` — на пустой очереди.

Коллекцию выбирают по профилю доступа: конкурентные записи по ключу → `ConcurrentHashMap`; много чтений, редкие записи →
`CopyOnWriteArrayList`; передача задач между потоками → `BlockingQueue`.

---

## 7. Другие проблемы: deadlock, livelock, starvation

- **Deadlock** — два потока держат по ресурсу и ждут ресурс друг друга; оба стоят вечно. Профилактика — единый порядок
  захвата блокировок и таймауты.
- **Livelock** — потоки не стоят, но и не продвигаются: реагируют друг на друга и бесконечно уступают.
- **Starvation** — поток не получает ресурс, потому что его вечно перехватывают другие (например, при
  несправедливых блокировках).

Средства выявления — профилировщики (thread dump показывает, кто на чём заблокирован) и мониторинг. Лучшая же защита —
минимизировать разделяемое изменяемое состояние: то, чего нет, не порождает гонок.

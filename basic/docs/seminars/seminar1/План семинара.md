### Этап 2. Теория: ООП (~15 мин)

Этап идёт по презентации (раздел «ООП в Java»). Цель — не пересказать учебник, а показать **зачем** и **как принципы
работают вместе**. Подробное изложение — в сопроводительном материале [ООП](../../materials/seminar1/ООП.md).

**Ключевые тезисы:**

- **Объект** — это сущность с состоянием и поведением. Объекты общаются через вызовы методов.
- **Инкапсуляция** — не просто геттеры и сеттеры. Это про сокрытие деталей реализации и защиту инвариантов объекта.
  Класс сам отвечает за то, чтобы его состояние всегда было корректным.
- **Наследование** — механизм повторного использования и установления отношения «является». Имеет цену: сильная
  связность. Альтернативы — композиция и агрегация.
- **Полиморфизм** — возможность работать с разными типами через общий интерфейс. Сегодня рассматриваем два вида:
  **полиморфизм подтипов** (переопределение методов) и **перегрузку**.

> **Важно:** показать, как принципы *дополняют* друг друга — инкапсуляция защищает состояние, наследование строит
> иерархии, полиморфизм позволяет писать обобщённый код. Именно эту взаимосвязь мы затем увидим в коде.

### Этап 3. Брейншторминг: моделируем домен (~10 мин)

Студенты совместно с семинаристом на доске (WhiteBoard или доска в Толке). Ребята набрасывают, семинарист фиксирует и
направляет.

**Задание:**

> Представьте, что вы проектируете MVP Market Pulse. Нам нужно минимально рабочее приложение на моках.
>
> **Подумайте по трём осям:**
> 1. **Сущности.** Какие объекты из мира Т-Инвестиций вам понадобятся?
> 2. **Связи.** Какие из них связаны и как именно (наследование «является», владение «часть-целое», ссылка)?
> 3. **Атрибуты и поведение.** Какие данные и какие операции у каждой сущности?

Семинарист направляет обсуждение так, чтобы студенты сами пришли примерно к следующей картине.

**Сущности и их атрибуты:**

- **Instrument** — финансовый инструмент. Общее: `ticker`, `name`, `currency`. Абстрактная сущность: «просто
  инструмента» не бывает, бывают его виды.
    - **Stock** (акция) — добавляет `sector`, дивидендную доходность.
    - **Bond** (облигация) — добавляет купон и год погашения.
    - **Etf** (биржевой фонд) — добавляет отслеживаемый индекс.
- **Quote** (котировка — инструмент с текущей рыночной ценой) — `price`, `changePercent`; ссылается на `Instrument`.
- **Portfolio** (портфель пользователя) — содержит список позиций.
    - **Position** (позиция: инструмент + количество) — существует только внутри портфеля.

**Связи между сущностями:**

```other
Instrument (абстрактный)
  ├── Stock          «является»  (наследование)
  ├── Bond           «является»  (наследование)
  └── Etf            «является»  (наследование)

Quote ──► Instrument             ссылка / агрегация (инструмент живёт сам по себе)

Portfolio ◆── Position           «часть-целое» / композиция (позиция живёт внутри портфеля)
Position  ──► Instrument         ссылка
```

> **Ремарка семинаристу:** цена (`price`) намеренно относится к `Quote`, а не к `Instrument`. Почему — разберём на
> этапе реализации: один и тот же инструмент имеет разные цены в разные моменты и на разных биржах.

#### 4.2. Разбираем данный класс `Instrument` — инкапсуляция

`Instrument` тоже уже есть в стартовом коде. Открываем его вместе со студентами и разбираем: почему поля `private
final`? Почему нет сеттеров? `ticker` не должен меняться — это инвариант, зафиксированный в конструкторе.

```java
// model/Instrument.java (уже в стартовом коде)
public abstract class Instrument {

    private final String ticker;
    private final String name;
    private final Currency currency;

    public Instrument(String ticker, String name, Currency currency) {
        if (ticker == null || ticker.isBlank()) {
            throw new IllegalArgumentException("Ticker cannot be blank");
        }
        this.ticker = ticker;
        this.name = name;
        this.currency = currency;
    }

    public String getTicker() {
        return ticker;
    }

    public String getName() {
        return name;
    }

    public Currency getCurrency() {
        return currency;
    }
}
```

> **Акцент на инкапсуляцию:** объект инициализируется через конструктор и валидируется там же. Инструмент нельзя
> создать в некорректном состоянии, а после создания — испортить снаружи.

#### 4.3. Задача 1: вывести описание инструмента по его типу (наивный подход) — *реализуют сами*

> **Задача:** мы хотим выводить человекочитаемое описание инструмента, различающееся в зависимости от его типа
> (у акции — сектор, у облигации — купон и погашение, у ETF — индекс).

Сначала студенты решают задачу **самостоятельно и «в лоб»** — без полиморфизма. Появляются первые подклассы (пока без
описания) и внешняя функция, определяющая тип через `instanceof` (или через вспомогательный `enum InstrumentType`):

```java
// util/InstrumentFormatter.java — наивный подход, который студенты пишут сами
public class InstrumentFormatter {

    // Чтобы получить описание, нам нужно знать тип — используем instanceof
    public static String describe(Instrument instrument) {
        if (instrument instanceof Stock stock) {
            return "Акция, сектор: " + stock.getSector();
        } else if (instrument instanceof Bond bond) {
            return "Облигация, купон: " + bond.getCouponRate() + "%, погашение: " + bond.getMaturityYear();
        } else if (instrument instanceof Etf etf) {
            return "ETF, индекс: " + etf.getTrackingIndex();
        }
        return "Неизвестный инструмент";
    }
}
```

> **Обсуждение:** что не так с таким решением? Добавим новый тип инструмента — придётся найти и обновить все такие
> if-цепочки по всей кодовой базе. Компилятор об этом не предупредит. Логика «как описать инструмент» размазана и живёт
> отдельно от самих инструментов.

#### 4.4. Рефакторинг — полиморфизм вместо `instanceof`

Переносим логику описания туда, где про инструмент известно всё, — в сам класс. Добавляем в `Instrument` абстрактный
метод `getDescription()` и реализуем его в каждом подклассе. `InstrumentFormatter` и `InstrumentType` удаляем.

```java
// model/Instrument.java — добавляем абстрактный метод и используем его в toString()
public abstract class Instrument {
    // ... поля, конструктор, геттеры ...

    public abstract String getDescription();

    @Override
    public String toString() {
        return getTicker() + " — " + getName() + " (" + getDescription() + ")";
    }
}
```

```java
// model/Stock.java
public class Stock extends Instrument {

    private final String sector;

    public Stock(String ticker, String name, Currency currency, String sector) {
        super(ticker, name, currency);
        this.sector = sector;
    }

    public String getSector() {
        return sector;
    }

    @Override
    public String getDescription() {
        return "Акция, сектор: " + sector;
    }
}
```

`Bond` и `Etf` пишутся по аналогии: своё поле (купон/погашение, индекс) и своя реализация `getDescription()`.

> **Акцент:** теперь добавление нового типа инструмента — это создание нового класса. Существующий код трогать не нужно.
> Компилятор проследит, чтобы `getDescription()` был реализован — в `Instrument` этот метод абстрактный.

#### 4.5. Почему `double` не подходит для денег

Прежде чем считать деньги, показываем на реальном для нас расчёте, чего стоит `double`. Возьмём акцию с ценой `278.50`
и дивидендной доходностью `6.5%` и посчитаем годовой дивиденд двумя способами:

```java
void example() {
    double price = 278.50;
    double yield = 6.5;
    System.out.println(price * yield / 100);   // 18.102500000000003 — «хвост» из ниоткуда

    BigDecimal exact = new BigDecimal("278.50")
            .multiply(new BigDecimal("6.5"))
            .divide(new BigDecimal("100"), 2, RoundingMode.HALF_UP);
    System.out.println(exact);                 // 18.10 — ровно столько, сколько нужно
}
```

`double` — тип с плавающей точкой, он не может точно представить большинство десятичных дробей. На одной акции разница
незаметна, но на портфеле и множестве операций ошибки накапливаются, а округления расходятся. Правильный инструмент —
`BigDecimal`: он хранит число точно.

> **Акцент:** `BigDecimal` создаётся через `new BigDecimal("278.50")`, а не `new BigDecimal(278.50)` — конструктор от
> `double` унаследует его неточность. Везде, где в модели появляется цена или доходность, используем `BigDecimal`, а при
> делении задаём `RoundingMode`.

#### 4.6. Задача 2: годовая дивидендная доходность — где ломается наследование (LSP)

> **Задача:** посчитать годовой дивиденд для любого инструмента из портфеля.

Соблазн — вынести `getDividends(BigDecimal currentPrice)` в базовый класс `Instrument`, чтобы «считать для всех сразу».
Смотрим, что из этого выходит в подклассах:

```java
// model/Stock.java — всё честно
@Override
public BigDecimal getDividends(BigDecimal currentPrice) {
    // Годовой дивиденд: цена × доходность / 100
    return currentPrice.multiply(dividendYield)
            .divide(BigDecimal.valueOf(100), RoundingMode.HALF_UP);
}
```

```java
// model/Bond.java и model/Etf.java — а здесь уже проблема
@Override
public BigDecimal getDividends(BigDecimal currentPrice) {
    return BigDecimal.ZERO;                       // Вариант 1: тихо врём
    // throw new UnsupportedOperationException(); // Вариант 2: ломаем контракт
}
```

> **Обсуждение:** оба варианта плохие. `BigDecimal.ZERO` — молчаливо искажает расчёты. `UnsupportedOperationException`
> нарушает **LSP**: код, работающий с `List<Instrument>`, не может безопасно вызвать метод, не проверяя конкретный тип.
> Это сигнал, что `getDividends` не принадлежит базовому классу — он специфичен только для `Stock`. Правильное решение:
> убрать метод из `Instrument`, оставить только в `Stock`.

#### 4.7. Задача 3: акция с ценой в момент времени — агрегация против наследования

> **Задача:** представить акцию с актуальной рыночной ценой на конкретный момент времени.

**Шаг 1. Первый порыв — через наследование (`StockSnapshot`).** Отнаследоваться от `Stock`, добавить поле `price` и
завести `getDividends()` без аргумента, раз цена уже внутри:

```java
// model/StockSnapshot.java — попытка через наследование
public class StockSnapshot extends Stock {

    private final BigDecimal price;

    public StockSnapshot(String ticker, String name, Currency currency,
                         String sector, BigDecimal dividendYield, BigDecimal price) {
        super(ticker, name, currency, sector, dividendYield);
        this.price = price;
    }

    // Перегружаем — удобно, цена уже вшита
    public BigDecimal getDividends() {
        return getDividends(this.price);
    }
}
```

Выглядит аккуратно, но `getDividends(BigDecimal price)` из `Stock` никуда не делся. Какой из методов выбрать при вызове?
И что писать в переопределении с аргументом?

```java
@Override
public BigDecimal getDividends(BigDecimal currentPrice) {
    // Вариант 1: игнорируем аргумент — зачем он тогда есть?
    return getDividends();
    // Вариант 2: используем аргумент — тогда зачем нам this.price?
}
```

> **Обсуждение:** оба варианта плохие. В первом метод молча игнорирует переданное — потребитель типа `Stock` передаст
> одну цену, получит результат по другой. Во втором `this.price` бессмысленен. Поведение зависит от того, через какой
> тип смотрит вызывающий код, — это снова нарушение LSP. Плюс: один и тот же `SBER` на двух биржах по разным ценам — это
> два разных объекта `StockSnapshot`? Что-то не так.

**Шаг 2. Меняем подход — `Quote` как агрегация.** Проблема в том, что `StockSnapshot` — не вид `Stock`, а `Stock` плюс
рыночная цена в момент времени. Переименовываем в `Quote` и убираем наследование: `Quote` хранит ссылку на `Instrument`,
но не является им.

```java
// model/Quote.java — агрегация вместо наследования
public class Quote {

    private final Instrument instrument;
    private final BigDecimal price;
    private final BigDecimal changePercent;

    public Quote(Instrument instrument, BigDecimal price, BigDecimal changePercent) {
        this.instrument = instrument;
        this.price = price;
        this.changePercent = changePercent;
    }

    public Instrument getInstrument() {
        return instrument;
    }

    public BigDecimal getPrice() {
        return price;
    }

    public BigDecimal getChangePercent() {
        return changePercent;
    }

    // Цена известна — считаем дивиденды честно; для инструментов без дивидендов возвращаем ZERO
    public BigDecimal getDividends() {
        if (instrument instanceof Stock stock) {
            return stock.getDividends(this.price);
        }
        return BigDecimal.ZERO;
    }

    @Override
    public String toString() {
        String direction = switch (changePercent.signum()) {
            case 1 -> "▲";
            case -1 -> "▼";
            default -> "▬"; // изменения нет — не выдаём его за движение вверх
        };
        return instrument.getTicker() + ": " + price + " " + instrument.getCurrency()
                + " " + direction + " " + changePercent.abs() + "%";
    }
}
```

> **Акцент на `instanceof` в `getDividends()`:** здесь проверка типа уместна — и это стоит подсветить студентам в
> контрасте с наивным `InstrumentFormatter` из задачи 1. Там `instanceof` подменял полиморфизм и размазывал логику по
> внешнему коду. Здесь `Quote` осознанно работает с инструментами любого типа, но дивиденды осмысленны только для
> `Stock` — проверка локальна и не растёт при добавлении новых инструментов. Альтернатива, если хочется убрать
> `instanceof` совсем, — сузить `Quote` до `Stock`; проговорить с ребятами, почему для нашей задачи это слишком жёстко
> (котировки нужны для всех инструментов, а не только акций).

> **Акцент на агрегацию:** один и тот же `SBER` теперь может участвовать в любом количестве котировок — на разных
> биржах, в разные моменты — и оставаться единственным объектом. Инструмент живёт сам по себе; удаление котировки его не
> затрагивает.

**Шаг 3. Композиция для контраста — `Portfolio` и `Position`.** Показываем другой тип отношения. `Portfolio` владеет
`Position`: позиция не имеет смысла в отрыве от портфеля и создаётся только внутри него.

```java
// model/Portfolio.java
public class Portfolio {

    // Position — внутренняя сущность, снаружи её не создать
    public static class Position {
        private final Instrument instrument;
        private final int quantity;

        private Position(Instrument instrument, int quantity) {
            this.instrument = instrument;
            this.quantity = quantity;
        }

        public Instrument getInstrument() {
            return instrument;
        }

        public int getQuantity() {
            return quantity;
        }
    }

    private final String name;
    private final List<Position> positions = new ArrayList<>();

    public Portfolio(String name) {
        this.name = name;
    }

    public void addPosition(Instrument instrument, int quantity) {
        positions.add(new Position(instrument, quantity));
    }

    public List<Position> getPositions() {
        return Collections.unmodifiableList(positions);
    }

    public String getName() {
        return name;
    }
}
```

> **Акцент:** разница между агрегацией и композицией — в семантике владения. Спросить студентов: что произойдёт с
> позициями, если портфель удалён? А с инструментом, если удалена котировка? Ответы разные — и в этом вся разница.

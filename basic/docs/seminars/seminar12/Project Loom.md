# Project Loom: виртуальные потоки

---

## Проблема платформенных потоков

Задачи `quotesFor` почти всё время **ждут сеть** (блокирующий HTTP), а не считают. Платформенный поток на время ожидания
простаивает, занимая поток ОС. Потоки ОС дороги (стек, переключение контекста), поэтому пул ограничен (например, 8
потоков) — и при десятках ждущих задач они выстраиваются в очередь.

---

## Виртуальные потоки

Виртуальные потоки (Java 21) — лёгкие потоки, которых можно создавать миллионы. Пока виртуальный поток ждёт I/O, он
«сходит» с потока ОС и не занимает его; когда I/O готов — возвращается и продолжает. Много виртуальных потоков
исполняются на немногих потоках ОС.

```java
void example(List<String> tickers) {
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        tickers.forEach(t -> executor.submit(() -> load(t)));   // виртуальный поток на задачу
    }
}
```

---

## Переход — одна строка

Так как задачи отделены от исполнителя (Executor Framework), перевод с пула платформенных потоков на виртуальные — замена
одной фабрики:

```text
Executors.newFixedThreadPool(8)              // было
Executors.newVirtualThreadPerTaskExecutor()  // стало
```

Код задач не меняется. Не нужно подбирать размер пула — каждый тикер получает свой виртуальный поток.

---

## Когда это выигрыш

Виртуальные потоки не делают вычисления быстрее — они снимают ограничение на число одновременно **ждущих** задач:

- **I/O-bound** (наш случай: много блокирующих сетевых вызовов) — огромный выигрыш: тысячи одновременных ожиданий на
  горстке потоков ОС.
- **CPU-bound** (тяжёлые вычисления) — выигрыша нет: считать всё равно нечем, кроме имеющихся ядер; здесь нужен пул по
  числу ядер.

Правило: I/O-bound с высокой одновременностью → виртуальные потоки; CPU-bound → пул по числу ядер. Честный аргумент —
замер, а не интуиция.

---

## Почему «синхронный код с асинхронной эффективностью»

Виртуальные потоки позволяют писать простой блокирующий код (`source.fetch(ticker)` — прямой вызов, не колбэк), но
получать эффективность неблокирующего I/O: рантайм сам снимает поток с носителя на время ожидания. Как это устроено под
капотом (mount/unmount, потоки-носители) — здесь опускается.

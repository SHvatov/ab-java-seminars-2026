### Этап 1. От ручных потоков к пулу: `ExecutorService` и `Future` (~30 мин)

Презентация по материалу [«Executor Framework»](./Executor%20Framework.md); полный разбор всех тем семинара
(Executor/Future/CompletableFuture/виртуальные потоки) — в deep-dive
[«Executor Framework, Future и виртуальные потоки»](../../materials/seminar12/Executor%20Framework,%20Future%20и%20виртуальные%20потоки.md).

В семинаре 10 `quotesFor` создавал по потоку на тикер вручную (`Thread[]` + `join`). Проблемы: поток — тяжёлый ресурс,
создавать его на каждую задачу расточительно; управление массивом потоков и `join` — рутина, которую легко написать с
ошибкой.

**Executor Framework** разделяет «что выполнить» (задача) и «как выполнить» (пул потоков). Потоки создаются заранее и
переиспользуются:

```java
public List<Quote> quotesFor(Collection<String> tickers, IntConsumer onProgress) {
    List<String> list = List.copyOf(tickers);
    AtomicInteger completed = new AtomicInteger();

    try (ExecutorService executor = Executors.newFixedThreadPool(8)) {   // пул из 8 потоков
        List<Future<Optional<Quote>>> futures = list.stream()
                .map(ticker -> executor.submit(() -> {
                    Optional<Quote> quote = cachedFetch(ticker);
                    onProgress.accept(completed.incrementAndGet());
                    return quote;
                }))
                .toList();

        return futures.stream()
                .map(this::get)                 // Future.get — дождаться результата
                .flatMap(Optional::stream)
                .toList();
    }   // close() дожидается завершения всех задач и гасит пул (try-with-resources, Java 21+)
}
```

- `submit(Callable)` ставит задачу в пул и сразу возвращает `Future` — «расписку» на будущий результат.
- `Future.get()` блокирует до готовности результата; `cancel`/`isDone` — управление и статус.
- `ExecutorService` реализует `AutoCloseable` (Java 21+): `close()` в try-with-resources дожидается задач и гасит пул —
  больше не нужно вручную звать `shutdown`/`awaitTermination`.

`cachedFetch` — обёртка над `cache.computeIfAbsent(...)` из семинара 11: результаты по-прежнему кешируются в
`ConcurrentHashMap`, прогресс — по-прежнему через `AtomicInteger`. Логика та же, ручное управление потоками ушло.

> **Акцент:** ключевая мысль фреймворка — задачи (`Callable`/`Runnable`) отделены от исполнителя (`ExecutorService`).
> Один и тот же код задач можно исполнить на пуле из 8 потоков, на одном потоке или на виртуальных — не меняя сами
> задачи. Это пригодится уже на этапе 3.

### Этап 2. `CompletableFuture`: асинхронные конвейеры (~30 мин)

Презентация по материалу [«CompletableFuture»](./CompletableFuture.md).

`Future.get()` — блокирующий: поток стоит и ждёт. `CompletableFuture` (Java 8+) позволяет описать, **что сделать с
результатом, когда он будет готов**, не блокируясь, и строить из этого конвейеры.

```java
List<CompletableFuture<Optional<Quote>>> futures = list.stream()
        .map(ticker -> CompletableFuture.supplyAsync(() -> cachedFetch(ticker), executor))
        .toList();

CompletableFuture.allOf(futures.toArray(CompletableFuture[]::new)).join();   // дождаться всех

return futures.stream().map(CompletableFuture::join).flatMap(Optional::stream).toList();
```

- `supplyAsync(supplier, executor)` — запустить задачу асинхронно, получить `CompletableFuture`.
- `thenApply`/`thenAccept` — преобразовать/использовать результат, когда он готов; `thenCombine` — объединить два;
  `exceptionally` — обработать ошибку в конвейере.
- `allOf(...)` — дождаться завершения всех.

> **Самостоятельно (студенты):** перевести `quotesFor` с `Future.get` на `CompletableFuture` и добавить
> `exceptionally`, чтобы сбой загрузки одного тикера не рушил весь пакет, а превращался в «пропуск» (пустой результат).

### Этап 3. Project Loom: виртуальные потоки (~30 мин)

Презентация по материалу [«Project Loom»](./Project%20Loom.md).

Задачи `quotesFor` почти всё время **ждут сеть** (блокирующий HTTP), а не считают. Платформенный поток на время ожидания
простаивает, занимая поток ОС, — поэтому пул и ограничен (8 потоков). **Виртуальные потоки** (Java 21) — лёгкие потоки,
которых можно создавать миллионы: пока виртуальный поток ждёт I/O, он «сходит» с потока ОС и не занимает его.

Благодаря тому, что задачи отделены от исполнителя (этап 1), переход — **одна строка**:

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // тот же код задач — по виртуальному потоку на тикер, без ограничения пулом
}
```

Для нашей задачи (много блокирующих сетевых вызовов) это идеальный случай: не нужно подбирать размер пула, каждый тикер
получает свой виртуальный поток, а потоков ОС используется ровно столько, сколько реально работает CPU.

> **Акцент:** виртуальные потоки не делают код «быстрее» сами по себе — они снимают ограничение на количество
> одновременно **ждущих** задач. Для CPU-bound работы выигрыша нет (считать всё равно нечем, кроме ядер); для
> I/O-bound (наш случай) — огромный. Замер до/после в продвинутом треке показывает это в цифрах.

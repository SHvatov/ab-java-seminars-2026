## Часть 1. Работа с файловой системой

### Этап 1. IO vs NIO: старое и новое API работы с файлами (~15 мин)

Презентация по материалу [«Java IO vs NIO»](./Java%20IO%20vs%20NIO.md).

До сих пор всё состояние приложения (каталог инструментов, watchlist, кеш котировок) жило в памяти и терялось при
перезапуске. Чтобы данные сохранялись, их нужно писать на диск. Java даёт для этого два поколения API:

- **Классический IO** (`java.io`, с Java 1.0): потоки байтов и символов — `FileInputStream`/`FileReader`,
  `BufferedReader`, ручное управление ресурсами. Ориентирован на последовательный поток.
- **NIO.2** (`java.nio.file`, с Java 7): `Path` (путь как объект), `Files` (статические операции над файлами и
  директориями), каналы. Компактнее, безопаснее по ресурсам, богаче по возможностям (обход дерева, атрибуты,
  копирование одной операцией).

```java
void example(Path file) throws IOException {
    // Классический IO — поток и ручная обёртка.
    try (BufferedReader reader = new BufferedReader(new FileReader(file.toFile()))) {
        String line = reader.readLine();
    }

    // NIO.2 — одна операция.
    String content = Files.readString(file);
    Files.writeString(file, content);
}
```

> **Акцент:** новый код проекта пишем на NIO.2 (`Path`/`Files`) — он лаконичнее и это современный стандарт. Классический
> IO показываем для контекста и понимания, что происходит под капотом высокоуровневых методов.

### Этап 2. Постоянное хранилище: инструменты и watchlist в JSON через NIO (~25 мин)

Задача: каталог инструментов и watchlist должны переживать перезапуск. Храним их на диске в JSON, в отдельных
директориях; читаем и пишем через NIO.

**Формат и сериализация.** Домен полиморфен (`Stock`/`Bond`/`Etf`) и использует `BigDecimal` для денег. В стандартной
библиотеке JSON-сериализатора нет, поэтому подключаем Jackson (`com.fasterxml.jackson.core:jackson-databind`). Полиморфизм
разрешается дискриминатором типа: в JSON пишется поле `type`, по нему при чтении выбирается конкретный класс.

```java
// Пример JSON одного инструмента (data/instruments/SBER.json)
// {
//   "type": "STOCK",
//   "ticker": "SBER",
//   "name": "Сбербанк",
//   "currency": "RUB",
//   "sector": "Banks",
//   "dividendYield": 6.5
// }
```

**Раскладка на диске.** Каждый инструмент — отдельный файл `data/instruments/<TICKER>.json`; watchlist — один файл
`data/watchlist.json` со списком тикеров. Директории создаются при первом сохранении (`Files.createDirectories`).

**Запись и чтение через NIO.** Новый класс `storage/InstrumentStorage` сохраняет и загружает каталог:

```java
public void save(Instrument instrument) throws IOException {
    Files.createDirectories(instrumentsDir);
    Path file = instrumentsDir.resolve(instrument.getTicker().toUpperCase() + ".json");
    byte[] json = mapper.writeValueAsBytes(instrument);
    Files.write(file, json);   // NIO: запись массива байтов в файл
}

public List<Instrument> loadAll() throws IOException {
    if (Files.notExists(instrumentsDir)) {
        return List.of();
    }
    try (Stream<Path> files = Files.list(instrumentsDir)) {   // NIO: обход директории
        return files
                .filter(path -> path.toString().endsWith(".json"))
                .map(this::readInstrument)
                .toList();
    }
}
```

При старте приложения репозиторий наполняется из `loadAll()`; команда `add` после добавления в репозиторий вызывает
`save(...)`. Так каталог переживает перезапуск.

> **Самостоятельно (студенты):** по образцу `InstrumentStorage` реализовать персистентность watchlist — сохранение
> набора тикеров в `data/watchlist.json` и загрузку при старте. Watchlist проще инструментов (это `Set<String>`), так
> что это посильная тренировка на тех же `Files.write`/`Files.readString` + Jackson.

> **Для семинариста:** обратите внимание на `try (Stream<Path> files = Files.list(...))` — стрим из `Files.list`/`walk`
> держит открытый дескриптор директории и должен закрываться (try-with-resources из семинара 4). Это частая ошибка:
> `Files.list(...)` без закрытия течёт ресурсами.

### Этап 3. Эффективная работа с диском (~10 мин)

Подробнее — в материале [«Эффективная работа с диском»](../../materials/seminar7/Эффективная%20работа%20с%20диском.md).
Ключевые тезисы:

- **Буферизация.** Дисковые операции дороги; читать/писать по одному байту — медленно. Буфер группирует много мелких
  операций в одну крупную. `Files.newBufferedReader`/`newBufferedWriter` дают буферизацию из коробки;
  `Files.readAllBytes`/`readString` читают файл целиком одной операцией — удобно для небольших файлов вроде наших JSON.
- **Целиком против потоково.** Маленький конфиг проще прочитать целиком (`readString`); большой файл (лог, выгрузку)
  читают потоково построчно (`Files.lines`), не загружая всё в память.
- **Меньше системных вызовов.** Каждое обращение к диску — переход в ядро. Одна запись массива байтов дешевле, чем сотня
  записей по строке; поэтому JSON инструмента формируется в памяти и пишется одним `Files.write`.

> **Акцент:** для наших данных (десятки небольших JSON) хватает `Files.write`/`readString`. Разговор про буферизацию и
> потоковое чтение — задел на будущее, когда данных станет много.

## Часть 2. Сетевое взаимодействие

### Этап 4. HTTP-протокол кратко (~10 мин)

Презентация по материалу [«HTTP-протокол»](./HTTP-протокол.md). Минимум, нужный для похода в API:

- **Запрос-ответ.** Клиент шлёт запрос (метод, URL, заголовки, тело), сервер отвечает (статус, заголовки, тело).
- **Методы.** `GET` — получить данные, `POST` — отправить данные/вызвать операцию. T-Invest REST API вызывается через
  `POST` с JSON-телом.
- **Статусы.** `2xx` — успех, `4xx` — ошибка клиента (`401` — нет/неверный токен, `429` — превышен лимит), `5xx` —
  ошибка сервера.
- **Заголовки.** `Authorization: Bearer <token>` — аутентификация, `Content-Type: application/json` — формат тела.

### Этап 5. Реальный T-Invest API через `HttpClient` (~30 мин)

Задача: заменить заглушку котировок реальными данными из T-Invest API
([developer.tbank.ru/invest](https://developer.tbank.ru/invest/intro/intro)). Котировки запрашиваются для инструментов,
которые отслеживает пользователь.

**Клиент.** Используем `java.net.http.HttpClient` (стандартная библиотека, без зависимостей). Новый источник котировок
`service/HttpQuoteSource` реализует тот же контракт, что и прежний стаб, но ходит в сеть:

```java
public Optional<Quote> fetch(String ticker) {
    HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create(endpoint))
            .header("Authorization", "Bearer " + token)
            .header("Content-Type", "application/json")
            .POST(HttpRequest.BodyPublishers.ofString(requestBody(ticker)))
            .build();
    HttpResponse<String> response = httpClient.send(request, HttpResponse.BodyHandlers.ofString());
    if (response.statusCode() != 200) {
        return Optional.empty();
    }
    return parseQuote(response.body(), ticker);   // Jackson: JSON ответа -> Quote
}
```

**Токен.** Секрет не хранится в репозитории — читается из переменной окружения (например, `TINVEST_TOKEN`). Без токена
приложение предупреждает об этом при старте, а сетевые команды возвращают пустой результат.

**Идентификатор и изменение цены.** T-Invest адресует инструменты не тикером, а внутренним идентификатором
(FIGI/instrumentId), поэтому перед запросом тикер разрешается в идентификатор через соответствующий метод API
(результат кешируется). Последнюю цену даёт `GetLastPrices`; изменение (`changePercent`) считается относительно цены
закрытия предыдущего дня (`GetClosePrices`) — одного значения последней цены для этого недостаточно.

**Интеграция.** `QuoteSource` становится интерфейсом, `HttpQuoteSource` — его реализацией; `QuoteService`
(очередь + кеш из семинара 5) теперь наполняется реальными котировками. Команды `stats`/`movers` агрегируют котировки
**отслеживаемых инструментов** (watchlist), а `compare` — переданных тикеров. Котировка строится только для
инструмента, уже добавленного в каталог (`add`): из него берутся тип и валюта, поэтому по неизвестному тикеру команда
вернёт пустой результат.

> **Для семинариста:** каждая котировка — это несколько отдельных запросов к API (резолв инструмента, последняя и
> закрытая цены), поэтому опрос большого watchlist упирается в лимит запросов (`429` из этапа 4). В реальном приложении
> такие запросы батчат (`GetLastPrices` принимает массив идентификаторов) и кешируют; здесь для простоты каждый
> инструмент опрашивается отдельно — фокус семинара на самом сетевом вызове, а не на оптимизации.

> **Самостоятельно (студенты):** реализовать метод `fetch` для одного эндпоинта T-Invest (получение последней цены по
> идентификатору инструмента): собрать `HttpRequest`, отправить, проверить статус, распарсить ответ в `Quote`.
> Резолв тикера и разбор JSON-структуры ответа семинарист показывает, сам сетевой вызов пишут студенты.

> **Для семинариста:** `HttpClient.send(...)` — блокирующий вызов (поток ждёт ответа). Для CLI-утилиты этого достаточно.
> Неблокирующий и асинхронный ввод-вывод (`sendAsync`, каналы, `Selector`) — тема продвинутого трека; здесь достаточно
> упомянуть, что существует и `HttpClient.sendAsync`, возвращающий `CompletableFuture`.

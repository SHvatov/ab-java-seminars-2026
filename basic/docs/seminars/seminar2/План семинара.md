### Этап 1. Теория: принципы SOLID (~20 мин)

**Задача этапа:** дать общий словарь для обсуждения качества кода, к которому семинарист будет возвращаться на всех
следующих этапах — Factory Method и Strategy обосновываются через OCP. Мини-лекция по материалу
[«Принципы SOLID»](../../materials/seminar2/Принципы%20SOLID.md), без пересказа целиком.

**Ключевые тезисы:**

- **LSP.** По итогам семинара 1 `getDividends(BigDecimal)` объявлен только в `Stock`
  ([`Stock.java#L36-L39`](../../../src/main/java/academy/backend/market_pulse/model/Stock.java)), а не в `Instrument`, —
  так LSP и не нарушается: `Bond`/`Etf` этот метод не переопределяют неправильно, потому что его для них вообще нет.
  Единственный пробел — эта договорённость нигде не названа явно, узнать о ней можно только прочитав исходный код
  `Stock`.
- **ISP.** Решение пробела выше — назвать способность явно: интерфейс
  [`DividendPaying`](../../../src/main/java/academy/backend/market_pulse/model/DividendPaying.java), реализуемый
  только `Stock`. Код, которому нужны дивиденды, зависит от узкого интерфейса, а не от конкретного класса.
- **SRP.** Класс должен меняться по одной причине. Смешение бизнес-логики и вывода в консоль — частая ошибка именно
  в CLI-командах, к которым семинар подходит на этапе 7.
- **OCP.** Переход от `instanceof`-цепочки к полиморфному `getDescription()` на семинаре 1 — уже пройденный пример
  OCP. Тот же принцип — база для Factory Method (этап 4) и Strategy (этап 6): новый тип или новое правило отбора
  добавляется новым классом, без правки существующего.
- **DIP, обзорно.** Модули верхнего уровня зависят от абстракций, а не от конкретных реализаций. Полноценное,
  автоматизированное применение — тема фреймворков с dependency injection (Spring), она за рамками этого курса и
  разбирается в следующем учебном году.
- **KISS и DRY** — как менее формальные, но практические ориентиры, дополняющие пять принципов SOLID.

### Этап 2. Подключение picocli (~10 мин)

**Задача этапа:** функциональные требования семинара (`search`, `add`, `list`) собираются в CLI — приложение должно
разбирать аргументы командной строки, а не жёстко закодированные вызовы в `demo.Main`. Писать парсер аргументов
вручную избыточно — подключается готовая библиотека
[picocli](https://picocli.info/): декларативное описание команд и опций через аннотации.

Перед добавлением зависимости — что вообще такое `pom.xml` и зачем он нужен (материал
[«Maven и pom.xml»](./Maven.md)).

```xml
<dependency>
    <groupId>info.picocli</groupId>
    <artifactId>picocli</artifactId>
    <version>4.7.7</version>
</dependency>
```

Обзор основных типов picocli, без отдельного демонстрационного примера: `@Command` — аннотация класса-команды;
`@Option`/`@Parameters` — именованный/позиционный аргумент; `Callable<Integer>` — интерфейс, реализуемый командой;
`CommandLine` — точка запуска, разбирающая `args` и вызывающая `call()` нужной команды.

### Этап 3. Обсуждение: какие паттерны GoF применимы к CLI (~15 мин)

**Задача этапа:** до того как писать код, понять, какие типовые задачи возникают при переходе к CLI, и узнать в них
уже знакомые (или новые) паттерны — вместо того чтобы придумывать решение с нуля на этапе 4.

Формат — открытое обсуждение с группой, а не лекция.

> **Подготовить заранее:** доску (WhiteBoard или доска в Толке) для фиксации таблицы «задача → паттерн-кандидат» по
> ходу обсуждения — по аналогии с доской для брейншторминга домена на семинаре 1.

Вопросы для обсуждения:

- Какие паттерны проектирования уже знакомы студентам?
- Как устроена обработка команды в CLI-приложении — что происходит, когда пользователь вводит `search AAPL`?
- Как создать `Stock`/`Bond`/`Etf`, когда тип инструмента приходит строкой, введённой пользователем, а не из кода?
- Как отфильтровать список инструментов по типу так, чтобы добавление нового типа не требовало правки кода фильтрации?
- Как перебрать все инструменты в хранилище, не раскрывая наружу, как именно они там хранятся?

Ожидаемое направление ответов:

| **Задача**                                                        | **Паттерн-кандидат** |
|--------------------------------------------------------------------|-----------------------|
| Обработка пользовательской команды                                 | Command               |
| Создание объекта инструмента по строковому типу                    | Factory Method        |
| Фильтрация списка инструментов без хрупкого сравнения по типу      | Strategy              |
| Обход инструментов в хранилище без раскрытия внутренней структуры   | Iterator              |

Обсуждается, что picocli уже частично реализует Command на уровне библиотеки — аннотированная `@Command` команда,
реализующая `Callable`, фактически объект-команда с методом `call()` в роли `execute()`. Command и Iterator в коде
живьём не пишутся — они уже реализованы к этому моменту (этапы 5 и 7 — показ готового решения).

После обсуждения — краткий показ материала [«Паттерны проектирования GoF»](./Паттерны%20GoF.md): что такое паттерн
проектирования, три группы, и какой из паттернов-кандидатов из таблицы выше к какой группе относится. Материал не
пересказывается целиком.

### Этап 4. Совместная реализация: Factory Method (~15 мин)

**Задача этапа:** команда `add` (этап 7) должна создавать `Stock`/`Bond`/`Etf` по типу, пришедшему строкой; код
создания не должен разрастаться в `if/else` при каждом новом типе инструмента.

- [`InstrumentFactory.java`](../../../src/main/java/academy/backend/market_pulse/factory/InstrumentFactory.java) —
  интерфейс фабрики.
- [`StockFactory.java`](../../../src/main/java/academy/backend/market_pulse/factory/StockFactory.java) — одна из
  трёх реализаций (аналогично `BondFactory`, `EtfFactory`).
- [`InstrumentFactories.java`](../../../src/main/java/academy/backend/market_pulse/factory/InstrumentFactories.java) —
  реестр: помимо Factory Method, это ещё и отдельный, тоже именованный паттерн — **Registry** (М. Фаулер, *Patterns
  of Enterprise Application Architecture*): глобальная точка доступа к объектам по ключу, вместо `new` в каждом
  месте использования.

> **Обсуждение:** реестр в `InstrumentFactories` заполняется самрегистрацией — каждая фабрика добавляет себя в
> `static`-блоке при загрузке своего класса (см. `static` в `StockFactory.java#L11-L13`), по аналогии с
> `DriverManager` в JDBC. Нюанс: `static`-блок выполняется только при загрузке класса JVM, поэтому
> `InstrumentFactories` форсирует загрузку всех трёх фабрик явно
> ([`InstrumentFactories.java#L17-L23`](../../../src/main/java/academy/backend/market_pulse/factory/InstrumentFactories.java))
> — тот же нюанс, что и с историческим `Class.forName("com.mysql.cj.jdbc.Driver")` до JDBC 4.0. Альтернатива, не
> усложняющая пример дальше словесного упоминания, — `ServiceLoader` (Java SPI): реализации регистрируются
> декларативно в файле `META-INF/services/...`, без ручного реестра вообще.

### Этап 5. Итератор по репозиторию — показ и разбор готовой реализации (~10 мин)

**Задача этапа:** команда `list` (этап 7) должна перебрать все инструменты `InstrumentRepository`, не раскрывая
наружу внутреннее хранение (массив фиксированного размера).

- [`InstrumentRepository.java`](../../../src/main/java/academy/backend/market_pulse/repository/InstrumentRepository.java) —
  хранилище реализует `Iterable<Instrument>`
  ([`L13`](../../../src/main/java/academy/backend/market_pulse/repository/InstrumentRepository.java)), `iterator()`
  возвращает анонимную реализацию `java.util.Iterator`
  ([`L32-L49`](../../../src/main/java/academy/backend/market_pulse/repository/InstrumentRepository.java)).

Показать и обсудить: реализация `Iterable<Instrument>` — условие, необходимое и достаточное для `for-each`; без него
компилятор не примет объект в `for (... : repository)`. Разобрать на паре эквивалентных фрагментов, что `for-each` —
синтаксический сахар над `Iterator`:

```java
void example(InstrumentRepository repository) {
    // то, что пишет программист
    for (Instrument instrument : repository) {
        System.out.println(instrument.getDescription());
    }

    // во что это разворачивается компилятором
    Iterator<Instrument> iterator = repository.iterator();
    while (iterator.hasNext()) {
        Instrument instrument = iterator.next();
        System.out.println(instrument.getDescription());
    }
}
```

### Этап 6. Самостоятельная работа: Strategy — фильтрация по типу (~15 мин)

**Задача этапа:** команда `list --type` (этап 7) должна фильтровать инструменты по типу без растущей цепочки `if` в
самой команде — добавление нового способа отбора (например, по диапазону цены) не должно требовать правки кода
команды.

**Функциональные требования:**

- ФТ1. Можно проверить, подходит ли инструмент под правило отбора.
- ФТ2. Есть правило «без отбора» — подходят все инструменты.
- ФТ3. Есть правило «по типу» — подходит инструмент, чей класс совпадает с переданным именем.

**Интерфейс для реализации:**
[`InstrumentFilter.java`](../../../src/main/java/academy/backend/market_pulse/filter/InstrumentFilter.java).

Итоговая реализация (для проверки после самостоятельной работы):
[`TypeFilter.java`](../../../src/main/java/academy/backend/market_pulse/filter/TypeFilter.java),
[`NoOpFilter.java`](../../../src/main/java/academy/backend/market_pulse/filter/NoOpFilter.java).

### Этап 7. CLI-команды — показ и разбор готовой реализации (Command) (~15 мин)

**Задача этапа:** собрать всё сделанное на предыдущих этапах в работающий CLI — команды `search`, `add`, `list` и
точку входа приложения.

- [`SearchCommand.java`](../../../src/main/java/academy/backend/market_pulse/cli/SearchCommand.java) — поиск по
  тикеру через `InstrumentRepository.findByTicker`.
- [`AddCommand.java`](../../../src/main/java/academy/backend/market_pulse/cli/AddCommand.java) — связывает Command и
  Factory Method: создание объекта остаётся ответственностью `InstrumentFactories` (этап 4), команда лишь разбирает
  аргументы и передаёт их дальше.
- [`ListCommand.java`](../../../src/main/java/academy/backend/market_pulse/cli/ListCommand.java) — использует
  итератор (этап 5, уже в форме `for-each`) и `InstrumentFilter` (этап 6) вместо прямого сравнения строк.
- [`MarketPulseCli.java`](../../../src/main/java/academy/backend/market_pulse/cli/MarketPulseCli.java),
  [`demo/Main.java`](../../../src/main/java/academy/backend/market_pulse/demo/Main.java) — корневая команда и точка
  входа: команды регистрируются вручную через `addSubcommand`
  ([`Main.java#L20-L23`](../../../src/main/java/academy/backend/market_pulse/demo/Main.java)), а не через атрибут
  `subcommands` аннотации `@Command` — у `SearchCommand`/`AddCommand`/`ListCommand` нет конструктора без аргументов,
  каждой нужен уже готовый `repository`.

> **Обсуждение:** `TypeFilter` внутри по-прежнему сравнивает `getClass().getSimpleName()` — Strategy убрал
> разрастание условий в `ListCommand`, но не саму хрупкость сравнения по имени класса. Более надёжная реализация
> (сверка через `InstrumentFactories` или явный признак типа на `Instrument`) может быть предложена студентам как
> самостоятельное улучшение за рамками занятия.

`InstrumentRepository` на данном этапе — заглушка с захардкоженным набором инструментов; подключение реального
источника данных запланировано на семинар 5.

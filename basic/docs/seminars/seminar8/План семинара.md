### Этап 1. Зачем тесты и как устроен JUnit 5 (~15 мин)

Презентация по материалу [«JUnit 5 и Mockito»](./JUnit%205%20и%20Mockito.md), вводная часть.

До сих пор корректность кода проверялась запуском вручную. Это не масштабируется: при каждом изменении перепроверять все
сценарии руками невозможно, а значит рефакторинг опасен. Автоматический тест фиксирует ожидаемое поведение в коде и
перезапускается за секунды.

**Пирамида тестирования.** Много быстрых **unit**-тестов (одна единица логики в изоляции), меньше **интеграционных**
(несколько компонентов вместе), совсем немного медленных **end-to-end**. Основа — unit-тесты; на них и сосредоточимся.

**JUnit 5.** Стандарт тестирования в Java. Тест — метод с аннотацией `@Test`; проверки — статические методы
`Assertions`:

```java
class QuoteTest {

    @Test
    void растущаяКотировкаПоказываетСтрелкуВверх() {
        Quote quote = new Quote(
                new Stock("SBER", "Сбербанк", Currency.RUB, "Banks", new BigDecimal("6.5")),
                new BigDecimal("250.00"), new BigDecimal("1.20"));

        assertTrue(quote.toString().contains("▲"));   // Arrange — Act — Assert
    }
}
```

Ключевые ассерты: `assertEquals(ожидаемое, фактическое)`, `assertTrue/assertFalse`, `assertThrows(Type.class, ...)`,
`assertNull`. Общая подготовка выносится в метод с `@BeforeEach`; человекочитаемое имя даёт `@DisplayName`.

> **Акцент:** структура теста — **Arrange-Act-Assert**: подготовить данные, выполнить действие, проверить результат.
> Один тест проверяет одно поведение и читается как утверждение о коде.

### Этап 2. Unit-тесты доменной модели (~25 мин)

Пишем тесты на чистую логику домена — она детерминирована и тестируется без всякого окружения. Часть показывает
семинарист, часть пишут студенты.

**Деньги и форматирование (семинарист).** `Quote.toString()` различает рост/падение/ноль, `Stock.getDividends` считает
дивиденды:

```java
@Test
void дивидендыЭтоЦенаУмноженнаяНаДоходность() {
    Stock stock = new Stock("SBER", "Сбербанк", Currency.RUB, "Banks", new BigDecimal("10"));
    // 250.00 * 10 / 100 = 25.00
    assertEquals(new BigDecimal("25.00"), stock.getDividends(new BigDecimal("250.00")));
}

@Test
void нулевоеИзменениеПоказываетсяНейтральнымЗнаком() {
    Quote quote = new Quote(anyStock(), new BigDecimal("100"), BigDecimal.ZERO);
    assertTrue(quote.toString().contains("▬"));
}
```

> **Обсуждение:** сравнение `BigDecimal` через `assertEquals` учитывает масштаб: `new BigDecimal("25.00")` не равен
> `new BigDecimal("25.0")` по `equals`. Это повод проговорить, что тест на деньги фиксирует и точность тоже.

**Watchlist и репозиторий (студенты).** Уникальность и нормализация тикеров, регистронезависимый поиск:

```java
@Test
void watchlistНеДобавляетДубликатНезависимоОтРегистра() {
    Watchlist watchlist = new Watchlist();
    assertTrue(watchlist.add("SBER"));
    assertFalse(watchlist.add("sber"));   // тот же тикер в другом регистре
    assertEquals(1, watchlist.tickers().size());
}
```

Аналогично — тест на `InstrumentRepository`: `findByTicker("sber")` находит добавленный `SBER`, а второй `add` того же
тикера уже проверяется на этапе 3.

### Этап 3. Тестирование ошибок и изоляция зависимостей (Mockito) (~25 мин)

**Тестируем ошибки.** Исключения — часть контракта, их проверяют `assertThrows`:

```java
@Test
void неизвестныйТипИнструментаБросаетИсключение() {
    assertThrows(IllegalArgumentException.class,
            () -> InstrumentFactories.create("CRYPTO", "BTC", "Bitcoin", Currency.RUB));
}

@Test
void повторныйТикерБросаетDuplicateTickerException() {
    InstrumentRepository repository = new InstrumentRepository();
    repository.add(sber());
    assertThrows(DuplicateTickerException.class, () -> repository.add(sber()));
}
```

**Изоляция зависимости (Mockito).** `QuoteService` зависит от `QuoteSource`, который в реальности ходит в сеть. Тест
не должен требовать токена и сети, поэтому источник **подменяется заглушкой** (mock): мы задаём, что он вернёт, и
проверяем поведение `QuoteService` в изоляции.

```java
@Test
void quoteForВозвращаетКотировкуИзИсточника() {
    QuoteSource source = mock(QuoteSource.class);              // подменяем сетевой источник
    Quote sberQuote = new Quote(sber(), new BigDecimal("250"), new BigDecimal("1.2"));
    when(source.fetch("SBER")).thenReturn(Optional.of(sberQuote));

    QuoteService service = new QuoteService(source);
    assertEquals(Optional.of(sberQuote), service.quoteFor("SBER"));
    verify(source).fetch("SBER");                              // источник действительно вызван
}
```

> **Для семинариста:** это главный приём семинара. `mock(...)` создаёт объект-заглушку по интерфейсу; `when(...).thenReturn(...)`
> программирует ответ; `verify(...)` проверяет факт вызова. Тестируемый класс не отличает заглушку от настоящего
> источника. Интерфейс `QuoteSource` (семинар 7) ровно для этого и был нужен — граница, которую можно подменить.

### Этап 4. Тестирование CLI-команд и запуск в CI (~25 мин)

**Что тестировать в CLI.** Команда — это разбор аргументов (picocli) плюс логика. Тестируют результат (`exit code`,
эффект на репозиторий, вывод), а не точное форматирование каждой строки. Запуск через `CommandLine.execute(...)`
проверяет и парсинг аргументов, и логику:

```java
@Test
void listФильтруетПоТипу() {
    InstrumentRepository repository = new InstrumentRepository();
    repository.add(new Stock("SBER", "Сбербанк", Currency.RUB, "Banks", new BigDecimal("6.5")));
    repository.add(new Bond("OFZ", "ОФЗ", Currency.RUB, new BigDecimal("8"), 2030));

    String output = captureStdout(() ->
            new CommandLine(new ListCommand(repository)).execute("--type", "Stock"));

    assertTrue(output.contains("Акция"));
    assertFalse(output.contains("Облигация"));
}
```

Вспомогательный `captureStdout` временно подменяет `System.out` на буфер (`System.setOut`) — так проверяют консольный
вывод. Разбор такого хелпера — в сопроводительном материале.

> **Самостоятельно (студенты):** написать тест ещё на одну команду (`SearchCommand` — найденный и ненайденный тикер,
> `exit code` 0 и 1).

**Запуск в CI.** Тесты полезны, когда прогоняются автоматически при каждом изменении. Continuous Integration — сервер,
который на каждый push собирает проект и запускает `mvn test`; красный билд виден сразу. Пример конфигурации (GitHub
Actions) и разбор — в материале [«Тестирование в Java»](../../materials/seminar8/Тестирование%20в%20Java.md).

> **Для семинариста:** свяжите с семинаром 6 — там говорилось про «безопасный рефакторинг». Теперь у проекта есть
> тесты, и обещание закрывается: рефакторинг безопасен, потому что тесты сразу покажут сломанное поведение. Это же —
> мост к семинару про рефакторинг.

# Слоистая архитектура и вертикальные слайсы

---

## Слоистая архитектура (packaging by layer)

Самый распространённый способ организовать код — разложить его по **техническим слоям**, каждый в своём пакете:

```
cli        — представление: разбор команд и вывод
service    — прикладная логика
repository — доступ к данным в памяти
storage    — персистентность на диск
model      — доменные сущности
```

Слои упорядочены по уровню: представление наверху, домен внизу. Внутри слоя — код одной ответственности.

---

## Направление зависимостей

Ключевое свойство слоёв — зависимости направлены сверху вниз: `cli` знает про `service` и `repository`, те знают про
`model`, а `model` не знает ни про кого. Верхний слой зависит от нижнего, но не наоборот.

Нарушение направления — архитектурный запах. Если бы `model` импортировал что-то из `cli`, домен оказался бы привязан к
способу отображения — и переиспользовать его вне CLI стало бы невозможно. Здоровая слоистая система — это ацикличный
граф зависимостей, направленный к домену.

---

## Слабость слоёв

Слоистая структура понятна и привычна, но у неё есть цена: **одна фича размазана по всем слоям**. Чтобы добавить команду
`stats`, правишь `cli` (команда), `service` (логика), иногда `model`. Файлы одной задачи лежат в разных пакетах — чтобы
понять фичу целиком, приходится прыгать между слоями.

---

## Вертикальные слайсы (packaging by feature)

Альтернатива — группировка **по фиче**. Всё, что относится к «котировкам» (команда, сервис, источник), лежит в одном
пакете-слайсе; всё про «каталог» — в другом. Слайс режет приложение вертикально, через все слои сразу:

```
quotes/    — QuoteCommand, StatsCommand, QuoteService, QuoteSource
catalog/   — AddCommand, ListCommand, InstrumentRepository, InstrumentStorage
model/     — общие доменные сущности
```

- **Плюс:** фича локализована — вся в одном месте, легко понять и изменить.
- **Минус:** общий код между слайсами (домен, утилиты) нужно выносить аккуратно, чтобы слайсы не начали дублировать друг
  друга.

---

## Что выбрать

Для маленького приложения (как наш CLI) слоёв достаточно — фич немного, прыгать между пакетами недорого. Вертикальные
слайсы выигрывают с ростом числа фич и размера команды: слайс можно развивать и понимать независимо. Общий принцип —
структура пакетов должна отражать то, как код меняется: если чаще «по фичам» — слайсы, если по техническим слоям — слои.

### Этап 1. Зачем рефакторинг и что такое техдолг (~15 мин)

Презентация по материалу [«Рефакторинг и чистый код»](./Рефакторинг%20и%20чистый%20код.md); подробный разбор всех тем
семинара — в deep-dive [«Рефакторинг и архитектура приложения»](../../materials/seminar9/Рефакторинг%20и%20архитектура%20приложения.md).

Рефакторинг — изменение внутренней структуры кода без изменения его поведения (тема кратко звучала на семинаре 6).
Цель — не добавить функциональность, а снизить стоимость будущих изменений: читаемость, отсутствие дублирования, ясные
границы. **Технический долг** — накопленные компромиссы «сделали быстро, но не чисто»: каждый по отдельности терпим, но
вместе они замедляют развитие и повышают риск ошибок. Рефакторинг — способ гасить этот долг.

> **Акцент:** «работает» — необходимое, но не достаточное условие. Код читают и меняют куда чаще, чем пишут; рефакторинг
> оптимизирует именно это. Но менять структуру безопасно можно только тогда, когда поведение чем-то зафиксировано — и
> здесь на руку играют тесты семинара 8.

### Этап 2. Безопасный рефакторинг с тестами (~30 мин)

**Находим дублирование.** Три команды получают котировки по набору тикеров одинаковым конвейером:

```text
// StatsCommand, MoversCommand, CompareCommand — один и тот же кусок
... .stream()
    .map(quoteService::quoteFor)      // String -> Optional<Quote>
    .flatMap(Optional::stream)        // отбрасываем ненайденные
    ...
```

Дублирование — классический повод для рефакторинга «Extract Method»: одинаковую логику выносят в одно место.

**Рефакторим (студенты).** В `QuoteService` появляется метод «котировки по набору тикеров»:

```java
public List<Quote> quotesFor(Collection<String> tickers) {
    return tickers.stream()
            .map(this::quoteFor)
            .flatMap(Optional::stream)
            .toList();
}
```

Команды сводятся к вызову: `quoteService.quotesFor(watchlist.tickers())` (для `stats`/`movers`) и
`quoteService.quotesFor(tickers)` (для `compare`). Логика получения котировок теперь в одном месте.

**Тесты как страховка.** До и после рефакторинга прогоняем `mvn test`: тесты семинара 8 (`QuoteServiceTest`,
`ListCommandTest`) остаются зелёными — значит поведение не изменилось. На `quotesFor` добавляется отдельный тест
(пропуск ненайденных, сохранение порядка).

**Плохой рефакторинг ломает тест (демонстрация).** Намеренно вносим ошибку — заменяем `flatMap(Optional::stream)` на
`map(Optional::get)`:

```text
.map(this::quoteFor)
.map(Optional::get)     // упадёт на первом же ненайденном тикере
```

Тест `quotesForПропускаетНенайденныеИСохраняетПорядок` немедленно краснеет (`NoSuchElementException`). Без теста эта
ошибка всплыла бы только в проде на первом отсутствующем тикере.

> **Для семинариста:** это кульминация связки семинаров 8–9. Тесты — не бюрократия, а то, что превращает рефакторинг из
> риска в рутину. Дайте студентам самим сломать код и увидеть красный тест: страх «а вдруг я что-то сломал» снимается
> именно так.

### Этап 3. Слоистая архитектура проекта (~25 мин)

Презентация по материалу [«Слоистая архитектура и вертикальные слайсы»](./Слоистая%20архитектура%20и%20вертикальные%20слайсы.md).

Проект уже разложен по пакетам, и это — **слоистая архитектура** (packaging by layer): пакеты соответствуют техническим
слоям.

```
cli        — представление: разбор команд, вывод (picocli)
service    — прикладная логика: QuoteService
repository — доступ к данным в памяти
storage    — персистентность на диск (NIO, Jackson)
model      — доменные сущности (Instrument, Quote, Watchlist)
factory    — создание инструментов
```

**Направление зависимостей.** `cli` зависит от `service`/`repository`, те — от `model`; `model` не зависит ни от кого
(почти — см. техдолг ниже). Это здоровое направление: верхние слои знают о нижних, но не наоборот. Нарушение этого
направления (например, если бы `model` знал про `cli`) — архитектурный запах.

> **Обсуждение:** слоистая структура понятна и привычна, но у неё есть слабость: одна фича размазана по всем слоям.
> Чтобы добавить команду, правишь `cli`, `service`, иногда `model` — файлы одной задачи лежат в разных пакетах.

### Этап 4. Вертикальные слайсы и реестр техдолга (~20 мин)

**Вертикальные слайсы.** Альтернатива слоям — группировка **по фиче**: всё, что относится к «котировкам» (команда,
сервис, источник), лежит рядом; всё про «каталог» — в другом слайсе. Слайс режет приложение вертикально, через все слои.
Плюс — фича локализована; минус — общий код между слайсами приходится выносить аккуратно. Для маленького CLI слои
достаточны; слайсы выигрывают на росте числа фич.

**Реестр техдолга.** Честный разбор того, что в проекте осталось не идеальным:

- **Точка входа в пакете `demo`.** `Main` лежит рядом с демонстрационными классами — по смыслу это отдельный слой
  приложения (`app`), а не демо.
- **Домен знает про Jackson.** `Instrument` и подклассы несут аннотации `@JsonTypeInfo`/`@JsonCreator` — доменная модель
  зависит от библиотеки сериализации. Компромисс ради простоты; в продвинутом треке разбирается, как его убрать.
- **Незакрытый контракт API.** `HttpQuoteSource` помечен `// API:` — контракт T-Invest не выверен по докам.

> **Для семинариста:** цель этапа — не переписать всё, а научить **видеть** техдолг и формулировать его списком, а не
> ощущением «код какой-то не такой». Осознанный техдолг с планом погашения — норма; неосознанный — проблема.

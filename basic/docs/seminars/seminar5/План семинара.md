### Этап 1. Обзор Java Collection Framework (~15 мин)

Презентация по материалу [«Java Collection Framework»](./Java%20Collection%20Framework.md), разделы про иерархию
интерфейсов и обзор реализаций.

До сих пор единственной «коллекцией» в проекте был сырой массив `Instrument[100]` внутри репозитория: фиксированный
размер, ручной счётчик `size`, линейный поиск. Массив — примитивная структура; стандартная библиотека даёт готовый
набор структур данных под разные задачи. Это и есть Java Collection Framework (JCF).

**Иерархия интерфейсов.** Две независимые вершины:

```
Iterable
 └── Collection
      ├── List   — упорядоченная последовательность, допускает дубликаты (ArrayList, LinkedList)
      ├── Set    — множество уникальных элементов (HashSet, LinkedHashSet, TreeSet)
      └── Queue  — очередь, обработка по дисциплине FIFO/LIFO (ArrayDeque, LinkedList)

Map          — отображение «ключ → значение», НЕ наследует Collection (HashMap, LinkedHashMap, TreeMap)
```

> **Для семинариста:** ключевой момент, который стоит проговорить, — `Map` **не** является `Collection`. Это отдельная
> иерархия: у `Map` нет `iterator()`, перебирается она через `keySet()`, `values()` или `entrySet()`. Причина — `Map`
> хранит пары, а не отдельные элементы, и не вписывается в контракт `Collection<E>`.

**Общий контракт `Iterable` и метод `iterator()`.** Всё, что реализует `Collection`, реализует и `Iterable` — значит,
перебирается циклом for-each и отдаёт `Iterator`. С `Iterable`/`Iterator` уже работали на семинаре 2, когда
репозиторий сам реализовывал `Iterable<Instrument>` поверх массива. Сегодня к итераторам вернёмся подробнее на этапе 5
— как через них не только обходить, но и **изменять** коллекцию.

**Метод `stream()`.** У любой коллекции есть метод `stream()` — вход в Stream API, декларативную обработку данных.
Сегодня он не используется: все операции пишутся через `for-each` и явные циклы, чтобы структуры данных были видны без
дополнительного слоя абстракции. Stream API — тема следующего семинара, где этот же код будет отрефакторен.

### Этап 2. Из требований к структурам данных: List, Set, Queue, Map (~15 мин)

Вместо того чтобы перебирать реализации коллекций по справочнику, идём от требований проекта. Market Pulse на этом
семинаре обзаводится двумя новыми обязанностями:

1. **Хранить, какие инструменты интересны пользователю** — его личный watchlist. Пока список живёт прямо в коде;
   в будущем (семинар 7) он переедет на диск.
2. **Получать котировки по запросу пользователя** — по «внешнему API». Реального сетевого взаимодействия ещё нет
   (появится на семинаре 7), поэтому источник котировок — заглушка с заранее заготовленными данными.

> **Обсуждение с группой (~5 мин):** прежде чем показывать готовое решение, разбираем вместе, какая структура данных
> подходит под каждую задачу и почему. Наводящие вопросы ниже.

Раскладываем требования на конкретные задачи и подбираем структуру под каждую:

| Задача | Что важно | Структура |
|--------|-----------|-----------|
| Индекс инструментов: найти по тикеру за один шаг, не допускать дубликатов | быстрый поиск по ключу, уникальность ключа | `Map<String, Instrument>` |
| Watchlist: набор тикеров, которые отслеживает пользователь | уникальность, быстрая проверка «есть ли» | `Set<String>` |
| Очередь запросов котировок: обработать по порядку поступления | порядок FIFO, добавление в хвост, извлечение из головы | `Queue<String>` |
| Кеш полученных котировок: тикер → последняя котировка | поиск по ключу | `Map<String, Quote>` |
| Результат `list`: упорядоченный вывод, с возможными повторами при агрегации | порядок, индексный доступ | `List<Instrument>` |

**Почему именно так — сложность операций.** Главный критерий выбора — во сколько обходится ключевая операция при росте
данных:

- Поиск в `ArrayList` по значению — линейный, `O(n)`: как раз то, что делает нынешний `findByTicker` перебором массива.
- Поиск в `HashMap`/`HashSet` по ключу — в среднем `O(1)`, не зависит от размера.
- Добавление в конец `ArrayList` и в `HashSet`/`HashMap` — амортизированно `O(1)`.

Именно поэтому индекс инструментов и watchlist переезжают на hash-структуры: операция поиска перестаёт зависеть от
количества инструментов.

> **Для семинариста:** подробную таблицу сложности операций по реализациям — см. материал
> [«Java Collection Framework»](../../materials/seminar5/Java%20Collection%20Framework.md), раздел про сложность
> операций. На семинаре достаточно трёх фактов выше.

**Выбор конкретной реализации.** Под интерфейс `Map`/`Set` есть несколько реализаций; берём `LinkedHashMap` и
`LinkedHashSet` вместо `HashMap`/`HashSet` — они дают ту же `O(1)`-сложность, но дополнительно **сохраняют порядок
добавления**. Для `list` и watchlist предсказуемый порядок вывода важнее минимальной экономии памяти.

### Этап 3. Практика: индекс инструментов на Map, watchlist на Set (~25 мин)

Эту часть семинарист реализует вживую вместе с группой.

**3.1. Репозиторий инструментов переезжает с массива на `Map`.** Массив `Instrument[100]` с ручным `size` заменяется
на `LinkedHashMap<String, Instrument>`, где ключ — тикер:

```java
public class InstrumentRepository implements Iterable<Instrument> {

    private final Map<String, Instrument> instruments = new LinkedHashMap<>();

    public void add(Instrument instrument) {
        String key = instrument.getTicker().toUpperCase();
        if (instruments.containsKey(key)) {
            throw new DuplicateTickerException(instrument.getTicker());
        }
        instruments.put(key, instrument);
    }

    public Optional<Instrument> findByTicker(String ticker) {
        return Optional.ofNullable(instruments.get(ticker.toUpperCase()));
    }

    @Override
    public Iterator<Instrument> iterator() {
        return instruments.values().iterator();
    }
}
```

Что изменилось по сравнению с версией на массиве:

- `findByTicker` больше не перебирает все элементы — `Map.get` находит инструмент по ключу за `O(1)`. Линейный поиск
  из семинара 4 ушёл.
- Проверка дубликата (`DuplicateTickerException` из семинара 4) теперь `containsKey` вместо повторного линейного
  `findByTicker` — тоже `O(1)`.
- Исчезли фиксированный размер `100` и ручной счётчик `size`: `Map` растёт сам.
- `iterator()` больше не пишется руками через анонимный класс — делегируется `instruments.values().iterator()`.
  Контракт `Iterable<Instrument>` сохранён, весь код CLI (`ListCommand`, `SearchCommand`), который перебирает
  репозиторий, продолжает работать без изменений.

> **Для семинариста:** обратить внимание на нормализацию ключа `toUpperCase()`. Массивная версия искала тикер через
> `equalsIgnoreCase` — регистронезависимо. У `Map` равенство ключей **точное** (`equals`/`hashCode` строки
> чувствительны к регистру), поэтому, чтобы сохранить прежнее поведение, ключ приводится к верхнему регистру и при
> записи, и при чтении. Это типовая ловушка при переходе на `Map`: строковый ключ надо нормализовать в одном месте.

**3.2. Watchlist на `Set`.** Список тикеров, которые отслеживает пользователь. Важна уникальность (один тикер в
watchlist не имеет смысла держать дважды) и быстрая проверка «отслеживается ли»:

```java
public class Watchlist {

    private final Set<String> tickers = new LinkedHashSet<>();

    public boolean add(String ticker) {
        return tickers.add(ticker.toUpperCase());
    }

    public boolean contains(String ticker) {
        return tickers.contains(ticker.toUpperCase());
    }

    public Set<String> tickers() {
        return Collections.unmodifiableSet(tickers);
    }
}
```

> **Акцент:** `Set.add` возвращает `boolean` — `true`, если элемент действительно добавлен, `false`, если такой уже
> был. Не нужно предварительно проверять `contains` перед `add`: множество само отвергает дубликат. Это отличает
> семантику `Set` от `List`, куда `add` всегда добавляет и всегда возвращает `true`.

Метод `tickers()` отдаёт наружу неизменяемое представление через `Collections.unmodifiableSet` — тот же приём, что и
`Collections.unmodifiableList` в `Portfolio` (семинар 1): внутреннее множество не должно меняться в обход `Watchlist`.

`Watchlist` подключается к приложению CLI-командой `watch` (`cli/WatchCommand`): `market-pulse watch SBER` добавляет
тикер в watchlist, `market-pulse watch` без аргумента показывает текущий список. Команда регистрируется в `Main` с
общим на приложение экземпляром `Watchlist` — так же, как команды семинара 2 получают общий `repository`.

**3.3. Базовый Collections API.** Утильные классы `java.util.Collections` дают готовые операции над коллекциями —
показать самые ходовые на примере списка результатов:

```java
void example(List<Instrument> instruments, Instrument target) {
    Collections.sort(instruments, Comparator.comparing(Instrument::getTicker)); // сортировка на месте
    Instrument max = Collections.max(instruments, Comparator.comparing(Instrument::getTicker));
    int count = Collections.frequency(instruments, target); // сколько раз встречается элемент
    List<Instrument> readOnly = Collections.unmodifiableList(instruments); // неизменяемое представление
}
```

> **Для семинариста:** `Collections.sort(list, cmp)` сортирует список **на месте** и требует изменяемого списка —
> отличие от `list.stream().sorted(...)`, который вернёт новый (Stream API — следующий семинар). Сортировку по
> `Comparator` студенты уже видели в `ListCommand` (семинар 3, `matched.sort(...)`); `Collections.sort` — тот же
> механизм в виде статической утилиты.

Подробнее об утилитах `java.util.Collections`, разнице `unmodifiable*` и фабрик `List.of`/`Map.of`, а также кратком
обзоре сторонних библиотек — в материале
[«Вспомогательные средства для работы с коллекциями»](../../materials/seminar5/Вспомогательные%20средства%20для%20работы%20с%20коллекциями.md).

### Этап 4. Самостоятельная задача: очередь запросов и кеш котировок (~20 мин)

Эту часть студенты реализуют самостоятельно; семинарист задаёт условие и разбирает решение в конце.

**Условие.** Пользователь запрашивает котировки сразу по нескольким тикерам. Запросы нужно обработать по порядку
поступления (FIFO), а полученные котировки — сложить в кеш, чтобы повторный запрос не ходил к источнику снова.
Источник котировок на этом семинаре — заглушка `QuoteSource` с заранее заготовленными данными (реальная сеть —
семинар 7).

**Что дано.** Заглушка источника (её реализовывать не нужно):

```java
public class QuoteSource {

    private final Map<String, Quote> data;

    public QuoteSource(Map<String, Quote> data) {
        this.data = data;
    }

    public Optional<Quote> fetch(String ticker) {
        return Optional.ofNullable(data.get(ticker.toUpperCase()));
    }
}
```

**Задача.** Реализовать `QuoteService`, который:

1. хранит очередь запрошенных тикеров (`Queue<String>`) и кеш полученных котировок (`Map<String, Quote>`);
2. метод `request(String ticker)` — кладёт тикер в очередь (в хвост);
3. метод `processAll()` — обрабатывает всю очередь: извлекает тикеры из головы, тянет котировку из `QuoteSource`,
   кладёт в кеш; уже закешированные не запрашивает повторно;
4. метод `cached(String ticker)` — возвращает котировку из кеша (`Optional`).

Опорный каркас:

```java
public class QuoteService {

    private final QuoteSource source;
    private final Queue<String> pending = new ArrayDeque<>();
    private final Map<String, Quote> cache = new HashMap<>();

    public QuoteService(QuoteSource source) {
        this.source = source;
    }

    public void request(String ticker) {
        pending.offer(ticker.toUpperCase());
    }

    public void processAll() {
        while (!pending.isEmpty()) {
            String ticker = pending.poll();
            if (cache.containsKey(ticker)) {
                continue;
            }
            source.fetch(ticker).ifPresent(quote -> cache.put(ticker, quote));
        }
    }

    public Optional<Quote> cached(String ticker) {
        return Optional.ofNullable(cache.get(ticker.toUpperCase()));
    }
}
```

> **Акцент при разборе:** `Queue` работает через пару методов `offer` (добавить в хвост) / `poll` (извлечь из головы,
> `null` на пустой очереди). Есть и бросающие исключение аналоги — `add`/`remove`; для очереди-буфера, где пустота —
> нормальная ситуация, удобнее не бросающие `offer`/`poll`. `ArrayDeque` — рекомендованная реализация `Queue` общего
> назначения (быстрее `LinkedList`, меньше накладных расходов).

> **Обсуждение:** зачем очередь, а не сразу тянуть котировку в `request`? Разделение «положить запрос» и «обработать
> запросы» — заготовка под асинхронную обработку: на будущих семинарах очередь запросов сможет разгребать отдельный
> поток. Пока обработка синхронная, но структура данных для этого уже правильная.

`QuoteService` подключается к приложению CLI-командой `quote` (`cli/QuoteCommand`): `market-pulse quote SBER GAZP`
кладёт оба тикера в очередь, обрабатывает её (`processAll`) и печатает полученные котировки. Источник в `Main` —
`QuoteSource`, засеянный несколькими заготовленными котировками (заглушка «внешнего API в виде простых объектов»;
реальный сетевой источник придёт на семинаре 7).

> **Для семинариста:** к концу семинара в CLI появляются две новые рабочие команды — `watch` и `quote`, — и это и есть
> проверка, что сегодняшний код встроен в приложение, а не написан «в стол». Хорошая точка показать всю картину живьём:
> `market-pulse quote SBER GAZP` печатает котировки, `market-pulse watch SBER` — ведёт watchlist.

### Этап 5. Итераторы: обход, удаление, fail-fast (~15 мин)

Презентация по материалу [«Java Collection Framework»](./Java%20Collection%20Framework.md), раздел про итераторы и
fail-fast.

На семинаре 2 `Iterator` использовался только для обхода. Но у него есть и метод `remove()` — единственный безопасный
способ удалить элемент из коллекции **во время** её перебора.

**Проблема: удаление из коллекции во время for-each.** Попытка удалить элемент напрямую из коллекции, пока идёт цикл
for-each по ней, роняет программу:

```java
void example(List<String> tickers) {
    for (String ticker : tickers) {
        if (ticker.startsWith("T")) {
            tickers.remove(ticker); // ConcurrentModificationException
        }
    }
}
```

`for-each` под капотом — это `Iterator`, а коллекции JCF работают по принципу **fail-fast**: если коллекция
структурно изменилась в обход итератора (напрямую через `tickers.remove`), итератор это замечает и на следующем шаге
бросает `ConcurrentModificationException`, а не молча продолжает с испорченным состоянием. Имя обманчиво — речь не
обязательно о многопоточности: одного потока, меняющего коллекцию мимо итератора, достаточно.

**Решение: `Iterator.remove()`.** Чтобы удалять по ходу перебора, нужно работать с итератором явно и удалять через
него — тогда итератор знает об изменении и остаётся согласованным:

```java
void example(List<String> tickers) {
    Iterator<String> it = tickers.iterator();
    while (it.hasNext()) {
        String ticker = it.next();
        if (ticker.startsWith("T")) {
            it.remove(); // безопасно: удаляет последний возвращённый next() элемент
        }
    }
}
```

> **Для семинариста:** проговорить связку «`for-each` = сахар над `Iterator`». Именно поэтому прямой `remove` по
> коллекции в цикле for-each и падает — цикл держит итератор, о чужом изменении не подозревающий. `Iterator.remove()`
> удаляет последний элемент, возвращённый `next()`; вызвать его до `next()` или дважды подряд — `IllegalStateException`.
> Начиная с Java 8 у коллекций есть и `removeIf(predicate)` — компактная альтернатива для случая «удалить всё,
> подходящее под условие», внутри использующая тот же итератор.

**Итоги семинара.** Массив-заглушка ушёл: репозиторий инструментов теперь на `Map` с `O(1)`-поиском, watchlist — на
`Set`, обработка запросов котировок — на `Queue` с кешем на `Map`. Под каждую задачу подобрана структура данных исходя
из того, какая операция на ней частая и во сколько обходится. Разобрано, как безопасно изменять коллекцию во время
обхода и почему прямое удаление в for-each падает с `ConcurrentModificationException`.

Следующий семинар — Stream API: тот же код обработки коллекций будет переписан в декларативном стиле, а ручные циклы
`for-each` уступят место `stream()`.

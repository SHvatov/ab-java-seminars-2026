### Этап 1. Задача «в лоб»: сводка каталога через `forEach` (~15 мин)

Новое функциональное требование: команда `stats` — сводка по доступным котировкам. Нужно посчитать, сколько инструментов
каждого типа и каждой валюты, и среднее изменение цены (доходность) по всем котировкам. Данные берутся из заглушки
источника `QuoteSource` (семинар 5), в которую на этом семинаре засеян более широкий набор котировок.

Сначала решаем задачу так, как умеем после семинара 5 — императивным перебором со вспомогательными коллекциями:

```java
void printStats(Collection<Quote> quotes) {
    Map<String, Integer> byType = new HashMap<>();
    Map<Currency, Integer> byCurrency = new HashMap<>();
    BigDecimal changeSum = BigDecimal.ZERO;
    BigDecimal priceSum = BigDecimal.ZERO;

    for (Quote quote : quotes) {
        Instrument instrument = quote.getInstrument();
        String type = instrument.getClass().getSimpleName();
        byType.merge(type, 1, Integer::sum);
        byCurrency.merge(instrument.getCurrency(), 1, Integer::sum);
        changeSum = changeSum.add(quote.getChangePercent());
        priceSum = priceSum.add(quote.getPrice());
    }

    BigDecimal avgChange = quotes.isEmpty()
            ? BigDecimal.ZERO
            : changeSum.divide(BigDecimal.valueOf(quotes.size()), 2, RoundingMode.HALF_UP);

    byType.forEach((type, count) -> System.out.println(type + ": " + count));
    byCurrency.forEach((currency, count) -> System.out.println(currency + ": " + count));
    System.out.println("Средняя доходность: " + avgChange + "%");
    System.out.println("Суммарная цена инструментов: " + priceSum);
}
```

Код работает, но читается плохо: четыре аккумулятора, объявленные заранее и мутируемые в цикле; логика «что считаем»
размазана по телу цикла; чтобы понять, что здесь четыре независимых агрегата, нужно вычитать весь метод. Это отправная
точка — к концу занятия тот же результат будет выражен отдельными декларативными конвейерами.

> **Для семинариста:** акцент — не «цикл плохой», а «намерение спрятано». В императивном коде мы описываем *как*
> накапливать; в стримовом — *что* агрегировать. Держите этот пример открытым: к нему возвращаемся на этапе 3.

> **Обсуждение:** попросите студентов назвать, сколько здесь на самом деле независимых операций (четыре: два подсчёта
> группировкой, усреднение и сумма). В цикле они переплетены; это и есть корень нечитаемости.

### Этап 2. Stream API: стрим, операции, коллекторы (~20 мин)

Презентация по материалу [«Stream API»](./Stream%20API.md). Ключевые тезисы:

- **Что такое стрим.** Stream — не структура данных, а конвейер обработки последовательности элементов. Он не хранит
  данные и не изменяет источник, а описывает набор операций над ним.
- **Переход от коллекции к стриму.** Метод `stream()` есть у любой `Collection`; из массива — `Arrays.stream(...)`.
  Обратно в коллекцию — терминальной операцией (`toList()`, `collect(...)`).
- **Два типа операций.** *Промежуточные* (`filter`, `map`, `sorted`, `limit`, `distinct`) возвращают новый стрим и
  соединяются в цепочку; *терминальные* (`forEach`, `toList`, `count`, `reduce`, `collect`) запускают конвейер и дают
  результат или побочный эффект. Стрим завершается ровно одной терминальной операцией.
- **Холодность (ленивость).** Промежуточные операции не выполняются, пока не вызвана терминальная. До этого стрим —
  лишь описание конвейера; ни один элемент не обработан. Это позволяет, например, `limit` останавливать обработку, не
  проходя весь источник.
- **Коллекторы.** `collect(...)` собирает результат конвейера. `Collectors.toList()` — в список; `groupingBy(...)` —
  в `Map` по ключу группировки, часто со вторым коллектором (`counting()`, `averagingDouble(...)`); `joining(...)` — в
  строку.

> **Для семинариста:** подчеркните, что стрим одноразовый — повторный вызов терминальной операции на том же стриме
> бросит `IllegalStateException`. И что стрим не меняет источник: `list.stream().sorted()` не сортирует `list`.

Подробнее — в материале [«Stream API»](../../materials/seminar6/Stream%20API.md).

### Этап 3. Практика вместе: `stats` и `compare` на стримах (~25 мин)

Реализуем это вместе; часть шагов проговаривает семинарист, часть предлагается студентам по ходу.

**3.1. `stats` на стримах (семинарист).** Возвращаемся к методу из этапа 1 и переписываем каждый агрегат отдельным
конвейером:

```java
void printStats(Collection<Quote> quotes) {
    Map<String, Long> byType = quotes.stream()
            .collect(Collectors.groupingBy(
                    quote -> quote.getInstrument().getClass().getSimpleName(),
                    Collectors.counting()));

    Map<Currency, Long> byCurrency = quotes.stream()
            .collect(Collectors.groupingBy(
                    quote -> quote.getInstrument().getCurrency(),
                    Collectors.counting()));

    double avgChange = quotes.stream()
            .mapToDouble(quote -> quote.getChangePercent().doubleValue())
            .average()
            .orElse(0.0);

    // Денежная сумма — reduce над BigDecimal, а не mapToDouble().sum(): точность сохраняется.
    BigDecimal totalPrice = quotes.stream()
            .map(Quote::getPrice)
            .reduce(BigDecimal.ZERO, BigDecimal::add);

    byType.forEach((type, count) -> System.out.println(type + ": " + count));
    byCurrency.forEach((currency, count) -> System.out.println(currency + ": " + count));
    System.out.printf("Средняя доходность: %.2f%%%n", avgChange);
    System.out.println("Суммарная цена инструментов: " + totalPrice);
}
```

Каждый агрегат теперь самодостаточен и читается как одно предложение: «сгруппировать по типу и посчитать». Аккумуляторы
исчезли — их роль взял на себя коллектор.

> **Обсуждение:** сравните две агрегации. Средняя доходность идёт через `mapToDouble` (перевод `BigDecimal` в `double`
> теряет точность, но для отображаемого процента это приемлемо), а суммарная цена — через `reduce` над `BigDecimal`,
> потому что это деньги, и точность здесь важна. Один и тот же конвейер, но выбор терминальной операции диктуется
> доменным правилом семинара 1: стримы его не отменяют.

**3.2. Команда `compare` (семинарист).** Функциональное требование из плана курса: сравнить доходность нескольких
инструментов. `compare SBER GAZP LKOH` берёт котировки по тикерам, ранжирует по доходности и печатает по убыванию:

```java
@Override
public Integer call() {
    tickers.stream()
            .map(quoteService::quoteFor)          // тикер -> Optional<Quote>
            .flatMap(Optional::stream)            // отбрасываем ненайденные
            .sorted(Comparator.comparing(Quote::getChangePercent).reversed())
            .forEach(quote -> System.out.println(quote));
    return 0;
}
```

Здесь три идеи сразу: `map` (тикер → котировка), `flatMap(Optional::stream)` (аккуратно отбросить отсутствующие, не
проверяя null), `sorted` с `Comparator.reversed()`. `quoteFor` — тонкая обёртка над `QuoteService`, отдающая
`Optional<Quote>` (запрос + чтение из кеша).

> **Для семинариста:** `flatMap(Optional::stream)` — идиома «стрим значений, которые есть». Проговорите её отдельно:
> `Optional.stream()` даёт пустой стрим для `Optional.empty()` и одноэлементный — для присутствующего значения.

> **Для семинариста:** обратите внимание, что `quoteFor` внутри `map` — операция с побочным эффектом (кладёт запрос в
> очередь и пишет в кеш `QuoteService`). Это осознанное исключение: стрим последовательный, а кеш — локальное состояние
> сервиса, поэтому безопасно. Хороший момент проговорить общее правило: промежуточные операции стрима держат чистыми, а
> побочные эффекты (тем более в `parallel`-стриме) — избегают; здесь допустимо именно из-за последовательности и
> локальности состояния.

### Этап 4. Самостоятельная задача: `movers` и рефакторинг `ListCommand` (~20 мин)

Эти две задачи студенты делают сами; семинарист задаёт условие и разбирает решения в конце.

**4.1. Команда `movers` (студенты).** Требование: показать топ инструментов, сильнее всего выросших (или упавших) в
цене. `movers --top N` — N самых растущих по `changePercent`; флаг `--losers` меняет направление. Ожидаемый конвейер:

```java
quotes.stream()
        .sorted(losers
                ? Comparator.comparing(Quote::getChangePercent)
                : Comparator.comparing(Quote::getChangePercent).reversed())
        .limit(top)
        .forEach(quote -> System.out.println(quote));
```

Акцент задачи — `sorted` + `limit`: за счёт ленивости стрим не сортирует «весь мир» без нужды, а `limit` завершает
конвейер после N элементов.

**4.2. Рефакторинг `ListCommand` (студенты).** В `ListCommand` (семинар 3–5) отбор инструментов собран вручную:
`Predicate` строится комбинацией опций, затем ручной цикл наполняет `ArrayList` подходящими элементами. Задача —
заменить этот императивный цикл на конвейер:

```java
// Было: ручной цикл наполнения
List<Instrument> matched = new ArrayList<>();
for (Instrument instrument : repository) {
    if (filter.test(instrument)) {
        matched.add(instrument);
    }
}

// Стало: конвейер с тем же Predicate
List<Instrument> matched = repository.stream()
        .filter(filter)
        .collect(Collectors.toList());
```

Чтобы у репозитория появился потоковый доступ, ему добавляется метод `stream()` над значениями внутренней `Map`.
Сортировка по тикеру и «топ-N» (`InstrumentUtils.topByTicker` — обобщённый метод из темы Generics) остаются как есть:
их можно было бы тоже выразить через `sorted().limit()`, но здесь цель — показать замену именно императивного цикла
отбора, не переписывая переиспользуемую утилиту.

> **Для семинариста:** `Predicate`, собранный из опций (`--type`, `--currency`), остаётся прежним — меняется только
> способ его применения. Это важный вывод: стримы не отменяют наработки семинара 3, а дают им более чистую оправу.

### Этап 5. Рефакторинг: менять код, ничего не ломая (~10 мин)

Короткая теория по материалу [«Рефакторинг»](./Рефакторинг.md). Рефакторинг — изменение внутренней структуры кода без
изменения его внешнего поведения. Сегодняшние переписывания `stats`, `movers`, `ListCommand` — ровно такой случай:
наблюдаемый результат команд не меняется, меняется читаемость.

Основные принципы безопасного рефакторинга:

- **Не менять поведение и структуру одновременно.** Сначала переписать реализацию при неизменном контракте метода,
  убедиться, что вывод тот же, и лишь потом, отдельным шагом, менять контракт при необходимости.
- **Малые шаги.** Крупное переписывание разбивается на серию мелких эквивалентных преобразований, каждое из которых
  оставляет код рабочим.
- **Опора на проверку.** Уверенность, что поведение сохранилось, даёт повторяемая проверка — прогон команды на тех же
  входных данных до и после, а в перспективе — автоматические тесты.

> **Для семинариста:** здесь достаточно обозначить идею и показать на примере `stats` (до/после дают одинаковый вывод).
> Подробный разговор про рефакторинг и роль тестов — впереди, отдельным семинаром; сейчас — только базовая гигиена.

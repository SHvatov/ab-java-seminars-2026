### Этап 1. Мотивация и виды потоков (~20 мин)

Презентация по материалу [«Потоки в Java»](./Потоки%20в%20Java.md).

**Мотивация — на реальной боли проекта.** `QuoteService.quotesFor` (семинар 9) ходит за котировками **последовательно**:
на каждый тикер — до трёх блокирующих HTTP-вызовов (резолв инструмента, последняя цена, цена закрытия). Для watchlist из
10 инструментов это десятки round-trip'ов подряд — команда `stats` «висит» несколько секунд, хотя запросы независимы и
могли бы идти параллельно.

**Виды потоков.** Классические (platform) потоки — обёртка над потоком ОС; daemon-потоки — JVM не ждёт их завершения.
Виртуальные потоки упоминаются как «лёгкие» — к ним вернёмся в семинаре про Executor Framework. Создание — через билдер
`Thread.ofPlatform()`:

```java
void example(Runnable task) {
    Thread thread = Thread.ofPlatform().name("worker").start(task);
}
```

> **Акцент:** поток — тяжёлый ресурс (стек, привязка к потоку ОС). Плодить по потоку на каждую мелкую задачу нельзя;
> сегодня их немного (по одному на тикер), а управление пулом потоков — тема семинара про Executor Framework.

### Этап 2. Параллельная загрузка котировок: поток на тикер (~30 мин)

Распараллеливаем `quotesFor`: каждый тикер загружается в своём потоке, результаты собираются после `join`.

**Ключевая идея безопасности — каждый поток пишет в свою ячейку.** Результаты складываются в массив по индексу тикера;
два потока никогда не пишут в одну ячейку, поэтому общее изменяемое состояние не появляется и синхронизация не нужна
(что будет, если полезть в общий кеш, — тема следующего семинара).

```java
public List<Quote> quotesFor(Collection<String> tickers) {
    List<String> list = List.copyOf(tickers);
    Quote[] results = new Quote[list.size()];        // каждый поток пишет в свой индекс
    Thread[] threads = new Thread[list.size()];

    for (int i = 0; i < list.size(); i++) {
        int index = i;
        threads[i] = Thread.ofPlatform().start(() ->
                source.fetch(list.get(index)).ifPresent(quote -> results[index] = quote));
    }
    for (Thread thread : threads) {
        join(thread);                                // ждём завершения всех
    }
    return Arrays.stream(results).filter(Objects::nonNull).toList();
}
```

`join` дожидается завершения потока. Порядок результатов сохраняется (индексация), ненайденные отсеиваются — поведение
то же, что у последовательной версии, поэтому тест `quotesForПропускаетНенайденныеИСохраняетПорядок` (семинар 8)
остаётся зелёным. Замер до/после наглядно показывает выигрыш на сетевых задержках.

> **Для семинариста:** проговорите, почему это безопасно без единого `synchronized`: нет разделяемого изменяемого
> состояния — каждый поток владеет своей ячейкой. Это лучший старт в многопоточку: сначала показать, что параллелизм
> без общего состояния безопасен, а уже потом (семинар 11) — что бывает, когда состояние общее.

> **Самостоятельно (студенты):** обернуть `join` в аккуратную обработку `InterruptedException` (см. этап 4) и добавить
> замер времени выполнения через `System.nanoTime` до и после.

### Этап 3. Прогресс-бар через атомарный счётчик (~20 мин)

Пока идёт загрузка, пользователь не должен смотреть в «зависший» терминал — покажем ASCII-прогресс. Каждый воркер по
завершении увеличивает общий счётчик, а команда отрисовывает полоску по мере готовности.

**Атомарный счётчик.** Счётчик увеличивают несколько потоков одновременно — обычный `int++` здесь не годится (почему —
подробно в следующем семинаре). Пока достаточно знать, что `AtomicInteger.incrementAndGet()` выполняет инкремент
атомарно, без потери обновлений:

```java
public List<Quote> quotesFor(Collection<String> tickers, IntConsumer onProgress) {
    AtomicInteger completed = new AtomicInteger();
    // ... в теле воркера, после загрузки:
    onProgress.accept(completed.incrementAndGet());
    // ...
}
```

Отрисовка живёт в CLI-слое (не в `QuoteService` — логика и вывод не смешиваются): команда передаёт колбэк, который
перерисовывает строку `[####----] 4/8`. Прежняя сигнатура `quotesFor(Collection)` сохраняется как обёртка с пустым
колбэком — команды, которым прогресс не нужен, не меняются.

> **Обсуждение:** это простой producer/consumer — воркеры «производят» события завершения, рендерер их «потребляет».
> Почему `AtomicInteger`, а не `int`, и что именно ломается в обычном счётчике — форвард-референс на семинар про Java
> Memory Model и атомарность.

### Этап 4. Прерывание и корректное завершение (~20 мин)

Что если пользователь нажал Ctrl+C или одна из загрузок зависла? Поток нельзя «убить» насильно — его можно только
**попросить** завершиться через механизм прерывания.

- `thread.interrupt()` выставляет потоку флаг «пора останавливаться».
- Блокирующие методы (`sleep`, `join`, сетевые ожидания) реагируют на флаг, бросая `InterruptedException`.
- После броска `InterruptedException` флаг **сбрасывается** — поэтому его восстанавливают: `Thread.currentThread().interrupt()`.

```java
private void join(Thread thread) {
    try {
        thread.join();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // восстанавливаем флаг — не проглатываем прерывание
    }
}
```

Именно так `HttpQuoteSource` из семинара 7 уже обрабатывает `InterruptedException` (восстанавливает флаг) — теперь
понятно, зачем. Корректное прерывание — это graceful-завершение: поток получает шанс освободить ресурсы, а не
обрывается на полуслове.

> **Акцент:** прерывание — это кооперация, а не приказ. Код, игнорирующий флаг прерывания, невозможно корректно
> остановить; проглоченный `InterruptedException` — классическая ошибка.

# Потоки в Java

---

## Что такое поток

Поток (thread) — независимая последовательность исполнения внутри программы. Несколько потоков работают «одновременно»:
на многоядерном процессоре — действительно параллельно, на одном ядре — чередуясь. Классический поток в Java — тонкая
обёртка над потоком операционной системы.

Зачем: пока один поток ждёт (например, ответа по сети), другие могут работать. Наш `quotesFor` ходит за котировками по
одному тикеру за раз, и почти всё время потоки ждут сеть — идеальный случай для распараллеливания.

---

## Виды потоков

- **Платформенные (platform)** — классические потоки, обёртка над потоком ОС. Тяжёлые: свой стек, привязка к потоку ОС.
- **Daemon-потоки** — фоновые; JVM не ждёт их завершения и может выключиться, оборвав их. Годятся для вспомогательных
  задач (например, фоновая отрисовка), но не для того, что обязано доработать.
- **Виртуальные (virtual)** — лёгкие потоки (Java 21), которых можно создавать миллионы. К ним вернёмся в семинаре про
  Executor Framework.

## Создание и запуск

Современный способ — билдер `Thread.ofPlatform()`:

```java
void example(Runnable task) {
    Thread thread = Thread.ofPlatform().name("worker-1").start(task);   // создать и сразу запустить
    Thread unstarted = Thread.ofVirtual().unstarted(task);              // создать, но не запускать
}
```

- `start()` — создаёт и запускает поток; тело — переданный `Runnable`.
- `unstarted()` — создаёт, но не запускает (запуск потом, через `start()`).
- `name`, `daemon(true)`, `priority(...)` — настройки до запуска.

Приоритет потока — `int` от 1 до 10; подсказка планировщику ОС, а не гарантия. К нему прибегают редко и осознанно.

## Ожидание завершения: join

`join()` блокирует текущий поток, пока целевой не завершится. Так собирают результаты после параллельной работы:

```java
void example(Thread[] threads) throws InterruptedException {
    for (Thread thread : threads) {
        thread.join();   // ждём завершения каждого
    }
    // здесь все потоки точно закончили
}
```

## Параллелизм без общего состояния

Самый безопасный параллелизм — когда потоки не делят изменяемое состояние. Если каждый поток пишет только в свою ячейку
результата, гонок нет в принципе и синхронизация не нужна:

```java
void example(List<String> tickers, Quote[] results) {
    Thread[] threads = new Thread[tickers.size()];
    for (int i = 0; i < tickers.size(); i++) {
        int index = i;
        threads[i] = Thread.ofPlatform().start(() ->
                results[index] = load(tickers.get(index)));   // каждый — в свою ячейку
    }
    // ... join всех
}
```

Общее изменяемое состояние (один счётчик, одна коллекция на всех) — источник большинства многопоточных ошибок; что при
этом ломается и как чинить — тема следующего семинара.

## Прерывание потока

Поток нельзя «убить» насильно — его можно только **попросить** остановиться через механизм прерывания (кооперативный):

```java
void example(Thread worker) {
    worker.interrupt();   // выставляем флаг «пора остановиться»
}
```

- `interrupt()` выставляет потоку флаг прерывания.
- Блокирующие методы (`sleep`, `join`, сетевые ожидания) реагируют, бросая `InterruptedException`.
- После броска `InterruptedException` флаг **сбрасывается** — поэтому его восстанавливают:

```java
void example() {
    try {
        Thread.sleep(1000);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // восстанавливаем флаг — не проглатываем прерывание
    }
}
```

Проглоченный `InterruptedException` (пустой `catch`) — классическая ошибка: такой поток нельзя корректно остановить.

## Атомарный счётчик

Когда несколько потоков увеличивают один счётчик (например, «сколько котировок загружено» для прогресс-бара), обычный
`int++` теряет обновления. `AtomicInteger` выполняет инкремент атомарно:

```java
void example() {
    AtomicInteger completed = new AtomicInteger();
    // из любого потока:
    int done = completed.incrementAndGet();   // атомарно: +1 и вернуть новое значение
}
```

Почему обычный `int` здесь ломается и как это устроено внутри — подробнее в семинаре про модель памяти.

### Этап 1. Добавляем общий кеш в параллельную загрузку (~15 мин)

В семинаре 10 параллельный `quotesFor` был безопасен by construction: каждый поток писал только в свою ячейку массива,
общего изменяемого состояния не было. Но есть неэффективность: если тикер встречается повторно (в этом же запросе или в
следующей команде), мы каждый раз заново ходим в сеть.

Напрашивается **общий кеш**: перед сетевым вызовом заглянуть в него, а результат — положить, чтобы другие воркеры и
последующие команды переиспользовали. Именно здесь появляется то, чего в семинаре 10 не было, — **общее изменяемое
состояние, в которое пишут несколько потоков одновременно.**

```java
private final Map<String, Quote> cache = new HashMap<>();   // общий на все потоки

// в теле воркера:
Quote quote = cache.get(ticker);
if (quote == null) {
    quote = source.fetch(ticker).orElse(null);
    if (quote != null) {
        cache.put(ticker, quote);            // сюда одновременно пишут несколько потоков
    }
}
```

### Этап 2. Data race: как ломается общий `HashMap` (~25 мин)

Презентация по материалу [«Синхронизация и потокобезопасные коллекции»](./Синхронизация%20и%20потокобезопасные%20коллекции.md);
подробный разбор (включая deadlock/livelock/starvation) — в deep-dive
[«Синхронизация и потокобезопасные коллекции»](../../materials/seminar11/Синхронизация%20и%20потокобезопасные%20коллекции.md).

Запускаем параллельную загрузку с общим `HashMap` под нагрузкой (много тикеров, повторные запуски) — и код ломается:
теряются записи (в кеше меньше элементов, чем уникальных тикеров), а иногда прилетает `ConcurrentModificationException`
или программа вовсе зависает. `HashMap` не рассчитан на конкурентную запись: одновременный `put` может испортить его
внутреннюю структуру.

Две проблемы наложились:

- **Data race.** Несколько потоков пишут в `HashMap` без синхронизации — его внутреннее состояние (корзины, связи)
  повреждается.
- **Check-then-act.** «Проверить `get`, потом `put`» — не атомарно: два потока увидят `null` и оба сходят в сеть, а то
  и перезапишут друг друга.

> **Для семинариста:** это кульминация связки семинаров 10–11. В семинаре 10 параллелизм был безопасен, потому что не
> было общего состояния; стоило его завести — и код сломался. Запустите сломанную версию вживую: «работает у меня на
> одном потоке» и «падает под нагрузкой» — ровно то, чем страшна многопоточка.

### Этап 3. Починка: `ConcurrentHashMap` и `computeIfAbsent` (~20 мин)

Меняем `HashMap` на `ConcurrentHashMap` — потокобезопасную реализацию `Map`, рассчитанную на конкурентный доступ. А
проблему check-then-act решает атомарный `computeIfAbsent`: «если ключа нет — вычислить и положить, всё за одну
атомарную операцию».

```java
private final Map<String, Quote> cache = new ConcurrentHashMap<>();

// в теле воркера — одна атомарная операция вместо get + put:
Quote quote = cache.computeIfAbsent(ticker, t -> source.fetch(t).orElse(null));
```

После этого тест конкурентной загрузки стабильно зелёный: в кеше ровно столько записей, сколько уникальных найденных
тикеров, потерь нет.

Почему не `Collections.synchronizedMap`? Он заворачивает каждую операцию в единый замок — потоки выстраиваются в
очередь, и параллелизм вырождается. `ConcurrentHashMap` блокирует не всю карту, а лишь отдельные корзины (а чтение
вовсе почти без блокировок), поэтому масштабируется под нагрузкой.

> **Акцент:** «корректный синхронизатор» — это не просто «навесить `synchronized` на всё». Правильный инструмент
> (`ConcurrentHashMap` + атомарный `computeIfAbsent`) чинит гонку и сохраняет параллелизм; грубая блокировка чинит
> корректность, но убивает производительность.

### Этап 4. Обзор синхронизаторов и коллекций + самостоятельная работа (~30 мин)

`ConcurrentHashMap` — один инструмент из большого набора `java.util.concurrent`. Кратко обозреваем остальные (детали —
в сопроводительном материале):

- **Синхронизаторы** — координируют потоки: `CountDownLatch` (ждать завершения N событий), `Semaphore` (ограничить число
  одновременных участников), `CyclicBarrier` (собрать потоки в точке), `ReentrantLock` (гибкая замена `synchronized` с
  таймаутом).
- **Потокобезопасные коллекции** — `CopyOnWriteArrayList` (частые чтения, редкие записи), `BlockingQueue`
  (producer/consumer).

**Самостоятельная работа.** Даны тесты, каждый описывает сценарий координации потоков (например: «главный поток должен
дождаться, пока N воркеров закончат подготовку данных» или «к внешнему API нельзя обращаться более чем 3 потокам
одновременно»). В тестах оставлены пропуски — студенты выбирают и подключают **корректный синхронизатор** под сценарий,
чтобы тест стал зелёным.

> **Для семинариста:** цель самостоятельной работы — не вызубрить API, а научиться сопоставлять задачу координации с
> подходящим инструментом: «дождаться N» → `CountDownLatch`, «ограничить одновременность» → `Semaphore`, «собрать всех в
> точке» → `CyclicBarrier`. Разбор — по каждому тесту в конце.

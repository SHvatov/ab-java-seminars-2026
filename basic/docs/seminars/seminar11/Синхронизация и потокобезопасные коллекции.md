# Синхронизация и потокобезопасные коллекции

---

## Когда появляется проблема

В семинаре 10 параллельная загрузка была безопасна: каждый поток писал в свою ячейку массива, общего изменяемого
состояния не было. Проблемы начинаются, когда несколько потоков одновременно меняют **одно и то же** — общий счётчик,
общую коллекцию. Пример: параллельные воркеры складывают котировки в общий кеш, чтобы не ходить в сеть повторно.

---

## Data race на обычном HashMap

`HashMap` не рассчитан на конкурентную запись. Если несколько потоков одновременно вызывают `put`, его внутренняя
структура (корзины, связи между узлами) повреждается:

```java
void example(Map<String, Quote> cache, String ticker, QuoteSource source) {
    Quote quote = cache.get(ticker);
    if (quote == null) {
        quote = source.fetch(ticker).orElse(null);
        if (quote != null) {
            cache.put(ticker, quote);   // из нескольких потоков — data race
        }
    }
}
```

Под нагрузкой это проявляется как потерянные записи (в кеше меньше элементов, чем ожидалось),
`ConcurrentModificationException` или зависание. Причём «на одном потоке работает» — гонки проявляются только под
конкуренцией, поэтому их так легко не заметить.

Здесь две отдельные проблемы:

- **Data race** — незащищённая одновременная запись портит структуру `HashMap`.
- **Check-then-act** — «проверить `get`, потом `put`» не атомарно: два потока увидят `null`, оба сходят в сеть, один
  перезапишет другого.

## ConcurrentHashMap

`ConcurrentHashMap` — потокобезопасная реализация `Map`, рассчитанная на конкурентный доступ. Замена решает data race:

```java
private final Map<String, Quote> cache = new ConcurrentHashMap<>();
```

А проблему check-then-act решает атомарный `computeIfAbsent` — «если ключа нет, вычислить и положить, всё одной
атомарной операцией»:

```java
void example(Map<String, Quote> cache, String ticker, QuoteSource source) {
    Quote quote = cache.computeIfAbsent(ticker, t -> source.fetch(t).orElse(null));
}
```

**Почему не `Collections.synchronizedMap`?** Он оборачивает каждую операцию единым замком — потоки выстраиваются в
очередь, и параллелизм теряется. `ConcurrentHashMap` блокирует не всю карту, а лишь отдельные корзины (а чтение — почти
без блокировок), поэтому масштабируется под нагрузкой.

## Синхронизаторы

Синхронизаторы из `java.util.concurrent` — утилиты координации потоков, дающие более высокий уровень абстракции, чем
низкоуровневые примитивы:

- **`CountDownLatch`** — «дождаться N событий». Замок инициализируется числом; каждое событие вызывает `countDown()`;
  ожидающие на `await()` продолжают, когда счётчик дошёл до нуля. Одноразовый.
- **`Semaphore`** — ограничение числа одновременных участников. `acquire()` занимает разрешение (ждёт, если их нет),
  `release()` возвращает. Естественный рейт-лимитер: «не более 3 потоков к API одновременно».
- **`CyclicBarrier`** — точка сбора: N потоков ждут друг друга и продолжают вместе. Многоразовый.
- **`ReentrantLock`** — гибкая замена `synchronized`: `tryLock(timeout)` позволяет не ждать блокировку вечно.

Правило: блокирующие операции — по возможности с таймаутом (`tryLock`, `tryAcquire`), иначе рискуем зависанием всей
системы.

## Потокобезопасные коллекции

- **`ConcurrentHashMap`** — конкурентная `Map`; наш случай (кеш).
- **`CopyOnWriteArrayList`** — список для сценария «часто читаем, редко пишем»: чтение никогда не блокируется (работает
  по снимку), но каждая запись копирует весь массив.
- **`BlockingQueue`** (`LinkedBlockingQueue`, `ArrayBlockingQueue`) — очередь для связи producer/consumer: `put`
  блокирует, если очередь полна, `take` — если пуста. Основа паттерна «производитель-потребитель».

Выбор коллекции — по профилю доступа: много конкурентных записей по ключу → `ConcurrentHashMap`; много чтений, редкие
записи → `CopyOnWriteArrayList`; передача задач между потоками → `BlockingQueue`.
